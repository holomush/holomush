inventory** (PORTAL-03), and the **name normalization policy** (PORTAL-07).

Purpose: these three are one problem seen from three angles. Retire must not release the name
*because* names are denormalized into surfaces no rename can reach, and whether two names are "the
same" is decided by a normalization policy that does not exist yet. Fixing them in one plan is what
keeps the three answers consistent.

</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| player-supplied character name -> the uniqueness key | untrusted Unicode input crossing into an impersonation-relevant identity |
| retired character -> character selection and admin surfaces | a lifecycle read that fails open lets a retired or idle character back into play |
| rename -> already-published archives | a write on one side of a boundary no update path crosses |
| a future value added to the lifecycle CHECK -> existing readers | a non-exhaustive reader silently permits the new value |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-14 | Spoofing | Section 6 character-name normalization | high | mitigate | Mandate NFKC plus format-character stripping plus a concretely named confusable/mixed-script rule, with a stored normalized column as the uniqueness key — today's normalization does none of these, so a visually identical name impersonates freely. |
| T-01-15 | Spoofing | Section 4 retire and name release | high | mitigate | State normatively that retire MUST NOT release the name; a released name is an impersonation vector against the denormalized historical names section 5 inventories. |
| T-01-16 | Elevation of privilege | Section 4 lifecycle reads | high | mitigate | Mandate an exhaustive switch with a denying default plus a Phase-2 test that constructs the unreachable state directly, so the day-one third value cannot fail open when it becomes reachable. |
| T-01-17 | Tampering | Section 5 append-only capture sites | medium | mitigate | Prohibit any mass update of captured names and state the stale-name outcome as an accepted, documented consequence rather than leaving it to be discovered. |
| T-01-18 | Repudiation | Section 5 verdict ambiguity | medium | mitigate | Require exactly one verdict per site and state the tie-break, so no site is silently treated as live by one phase and historical by another. |
| T-01-19 | Denial of service | Section 6 duplicate-name resolution job | low | accept | Detection plus a one-shot job before the unique index is sequential work on a live table; the alternative (an in-migration backfill) is forbidden by the migration rules. |
