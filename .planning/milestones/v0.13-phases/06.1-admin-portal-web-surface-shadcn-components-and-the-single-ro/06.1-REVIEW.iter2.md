### WR-02: The depth-0 `@reference` directive is a BARE specifier, and a test case that can never run pins it as correct

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:219-229`, `:242-246`

**Issue:** The WR-05 repair replaced one wrong directive with another. For a file directly
under `web/src`, `depth` is 0 and `strings.Repeat("../", 0) + "app.css"` yields
`@reference "app.css";` — a **bare** specifier, not a relative one.

This repo proves bare specifiers are package-resolved in exactly this pipeline:
`web/src/app.css:1` is `@import "tailwindcss";`, which resolves out of `node_modules`, not
as a sibling file. Tailwind v4's `@reference` goes through the same Vite id resolver. So a
future `web/src/probe.svelte` that follows this census's demand will most likely fail the
build looking for a package named `app.css` — precisely the "puzzling build error that names
a path nobody wrote" the repair's own comment (`:216-218`) says it exists to prevent.

The pinning test makes it worse: `:242-246` asserts the depth-0 answer using
`path: "web/src/app.css"` — app.css referencing *itself*, a case that can never occur, so
the expected value can never be checked against a real build. The other three cases are all
depth ≥ 1 and pass for the same reason they always did.

**Fix:** emit an explicitly relative specifier at depth 0, and pin it with a plausible path:

```go
dir := filepath.ToSlash(filepath.Dir(rel))
if dir == "." {
    return `@reference "./app.css";`
}
depth := strings.Count(dir, "/") + 1
```

```go
{
    name: "a file directly under web/src references app.css as a sibling, explicitly relative",
    path: "web/src/probe.svelte",
    want: `@reference "./app.css";`,
},
```

`./app.css` is unambiguous under both the CSS `@import` rule and Vite's resolver; `app.css`
is not.

### WR-03: The marker slice NARROWED the containing-block assertion — a cell-relative rule added below the end marker is no longer caught

**File:** `web/src/lib/components/admin/CharacterTable.svelte.test.ts:290-313`,
`web/src/lib/components/admin/CharacterTable.svelte:398-402`

**Issue:** The replaced implementation walked braces from the media block's opening `{` to
its matching `}`, so **every** rule inside `@media (width < theme(--breakpoint-md))` was
scanned. The marker slice runs from the start-marker comment's `*/` to the end-marker
comment's `/*` — a strict sub-region of that block.

Concrete regression: add, inside the phone media block but *after* the end marker at
`CharacterTable.svelte:398`,

```css
    :global(.chartable .cell-name) {
      position: relative;
    }
```

`.rowbtn::after`'s containing block becomes the Name cell instead of the row, so on a phone a
tap on Player, Status or Last active hits nothing — the exact failure the test's own docstring
names. Old test: RED. New test: **GREEN**, because the offending selector is outside the
slice. The only thing standing in the way is the prose at `:399-402` ("keep the
containing-block declarations between the two"), which is a comment, not an assertion.

The browser-level `tapRowOutsideNameCell` (`admin-portal.spec.ts:47-70`) would still catch it,
so this is defence-in-depth loss rather than an open hole — but the unit guard the repair was
strengthening now covers less than it did before the repair.

**Fix:** keep the markers for the *anchor* and restore whole-block reach for the
*prohibition*. Take the slice as today for the positive assertions, and additionally walk
braces outward from `sliceFrom` to the enclosing media block's close for the
"`position: relative` on no cell" clause:

```ts
// The prohibition is a property of the WHOLE media block, not of the marked region:
// a cell-relative rule anywhere inside it breaks the overlay.
let depth = 1;
let i = sliceFrom + 2;
while (depth > 0 && i < src.length) {
  if (src[i] === '{') depth++;
  else if (src[i] === '}') depth--;
  i++;
}
const wholeBlock = src.slice(sliceFrom + 2, i).replace(/\/\*[\s\S]*?\*\//g, '');
for (const selector of [...wholeBlock.matchAll(/([^{}]+)\{[^{}]*position:\s*relative/g)].map(
  (m) => m[1].replace(/\s+/g, ' ').trim(),
)) {
  expect(selector).toMatch(/charrow/);
  expect(selector).not.toMatch(/\btd\b|cell/);
}
```

### WR-04: The browser-floor guard reads the LAST duplicate per browser, but browserslist unions its queries — a lowered floor passes green

**File:** `test/meta/web_browser_floor_test.go:204`, `:211-228`

**Issue:** `declared[strings.ToLower(name)] = version` overwrites on each entry, and nothing
rejects a repeated browser. browserslist evaluates its array as a **union**: the effective
supported set is the OR of every query, so the real floor is the *lowest* value declared for
a browser, not the last one written.

Concrete scenario — a support request lands and someone appends one line:

```json
"browserslist": [
  "chrome >= 111",
  "edge >= 111",
  "firefox >= 128",
  "safari >= 16.4",
  "ios_saf >= 16.4",
  "safari >= 15"
]
```

The published contract now claims Safari 15, which cannot parse the range-syntax media
queries in the shipped stylesheet **and** cannot honour its 59 unguarded `@property` rules.
`declared["safari"]` reads `"15"` here so this particular ordering fails — but reverse the two
lines (`"safari >= 15"` before `"safari >= 16.4"`, which is the order a tidy alphabetical or
append-at-top edit produces) and `declared["safari"]` reads `"16.4"`, `versionAtLeast` passes,
and the guard reports success over a contract the CSS cannot honour. The guard's own doc
comment (`:208-210`) says a false support contract is "the defect class this whole guard
exists to prevent".

**Fix:** reject duplicates outright, or keep the minimum:

```go
if prior, dup := declared[strings.ToLower(name)]; dup {
    require.Failf(t, "duplicate browserslist floor",
        "%s declares %q twice (%s and %s). browserslist UNIONS its queries, so the "+
            "effective floor is the LOWER of the two — declare one entry per browser.",
        webPackageJSON, name, prior, version)
}
declared[strings.ToLower(name)] = version
```

### WR-05: The browser-floor guard's premise is misattributed — Tailwind v4 already emitted range syntax repo-wide, so reverting the sixteen rules would not license lowering the floor

**File:** `test/meta/web_browser_floor_test.go:26-38`, `:159-164`

**Issue:** The guard's rationale is that the sixteen authored viewport rules made the floor a
derived value: *"That made the supported browser floor a DERIVED value — an unnamed
consequence of whichever CSS spelling the last conversion happened to pick."* That is false.
Tailwind v4 emits range syntax for **every** responsive utility, independently of anything
this phase authored. From the shipped build
(`web/build/_app/immutable/assets/0.THubD8Pl.css`):

```
width>=28rem  (×4)   width>=40rem  (×2)   width>=48rem  (×4)
width>=64rem  (×1)   width>=80rem  (×1)   width>=96rem  (×1)
```

`40rem`/`64rem`/`80rem`/`96rem` are Tailwind's `sm`/`lg`/`xl`/`2xl` variants — nothing under
`web/src` authors those widths (verified: `rg 'min-width: 40rem' web/src` is empty). Tailwind
v4 independently documents Chrome 111 / Safari 16.4 / Firefox 128 as its own required floor,
which is the same triple this file re-derives from Vite's baseline plus `@property`.

The declared numbers are therefore **right**; the *reason* is wrong, and the wrong reason has
a wrong action attached to it. A future reader who reverts the sixteen authored rules to
`min-width`/`max-width` — a plausible move if an old-browser bug report arrives — will read
this comment, conclude the floor was a consequence of that spelling, and lower
`browserslist`. Every `md:`/`lg:` Tailwind utility in the app still requires it, so the
support contract breaks with the guard green (the `@property` clause at `:211-228` is what
catches the Firefox/Safari half; Chrome and Edge are deliberately unpinned at `:120-124` and
would drop silently).

**Fix:** state the real source. Replace the "conversion made this a derived value" paragraph
with: the floor is Tailwind v4's own (`@theme` responsive variants compile to range syntax
for every utility, and Tailwind documents Chrome 111 / Safari 16.4 / Firefox 128), raised
where the shipped stylesheet binds higher. Add a sentence saying explicitly that reverting the
sixteen authored rules does **not** lower the floor.

### WR-06: "sixteen authored `@media` rules reading `theme(--breakpoint-md)`" is false — thirteen do; the other three read `--breakpoint-lg`

**File:** `web/src/lib/hooks/mediaQuery.svelte.ts:6-7`, `web/e2e/admin-band-root-font.spec.ts:6-8`

**Issue:** Both files state that `DESKTOP_MEDIA_QUERY`'s counterpart is *"sixteen authored
`@media` rules reading `theme(--breakpoint-md)`"*. Measured:

```
rg -c 'theme\(--breakpoint-md\)' web/src -g '*.svelte'  →  13
rg -c 'theme\(--breakpoint-lg\)' web/src -g '*.svelte'  →   3
```

Sixteen is the md **and** lg total — which is what the census says correctly at
`web_phone_band_breakpoint_census_test.go:279-280` ("seventeen authored sites — sixteen
`@media` rules plus one matchMedia query string", covering both tokens). The two files above
attribute all sixteen to the md token.

This is load-bearing prose in exactly the place it does damage: `mediaQuery.svelte.ts` is the
definition of the JS half, and the claim tells a reader that `DESKTOP_MEDIA_QUERY` is the
complement of all sixteen. It is not — the three `--breakpoint-lg` rules
(`SectionRail.svelte:262`, `admin/+layout.svelte:190`, `AdminNav.svelte:125`) are a different
boundary with **no** JS half at all. A maintainer adding a JS consumer for the lg band, or
"fixing" a perceived md/lg mismatch, is being pointed the wrong way by a comment that reads as
measured fact. This is the fourth false load-bearing comment found in these files.

**Fix:** in both files, replace "sixteen … reading `theme(--breakpoint-md)`" with "thirteen
authored `@media` rules reading `theme(--breakpoint-md)` (three further rules read
`--breakpoint-lg`, a boundary with no JS half)".

### WR-07: The census calls itself "the census of EVERY such rule" while nothing fails when a banded rule is added outside it

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:46-47`, `:456-463`

**Issue:** `bandedViewportRules` is documented as *"the checked-in census of every such rule
under webSrcDir"* (`:46-47`), but the only assertion that touches the corpus size is
`require.GreaterOrEqual(bandRelevant, ruleCensusOccurrences)` — a **floor**. Add a
seventeenth banded rule to any file without adding a census entry and `bandRelevant` rises to
19 while the claim stays 16: green.

The consequence is not cosmetic. `TestEveryBandedViewportRuleDerivesItsWidthFromTheTailwindToken`
only iterates the enumerated set, so the unlisted rule gets neither the occurrence-equality
check (WR-04's fix) nor the `@reference` directive check. Deleting it later — the accidental
path the floor's own comment (`:441-451`) admits it cannot see — is then caught by nothing at
all. The "every such rule" claim is the one property that would make the occurrence check
complete, and it is the one property unasserted.

**Fix:** make the tally an equality against the census plus the allowlist, which converts the
floor into a completeness check without loosening anything:

```go
allowlistLines := 0
for _, n := range allowlistHits {
    allowlistLines += n
}
require.Equal(t, ruleCensusOccurrences+allowlistLines, bandRelevant,
    "the walk reached %d band-relevant line(s) but this census claims %d rule occurrence(s) "+
        "plus %d allowlisted symbol line(s). A rule added WITHOUT a census entry is covered "+
        "by nothing: not the occurrence check, not the @reference check. Enumerate it.",
    bandRelevant, ruleCensusOccurrences, allowlistLines)
```

### WR-08: A mutation whose response carries no character closes the Sheet with no row change and no receipt — indistinguishable from success

**File:** `web/src/routes/(authed)/admin/characters/+page.svelte:144-157`, `:175-178`

**Issue:** In `saveEdit`, the order is `selected = null` (which unmounts the Sheet) and *then*
`if (!updated) return;`. When `updateAdminCharacter` resolves with `undefined` — the wrapper's
declared return type is `Promise<CharacterRow | undefined>`
(`web/src/lib/admin/client.ts:226`, because `res.character` is an optional proto message) —
the Sheet has already closed, `applyRow` never runs, no row flashes, and no toast fires. The
operator sees their edit form disappear with the row unchanged and zero feedback: exactly the
reading of "it worked" for something the page could not confirm.

`applyLifecycle` (`:175-178`) has the same shape, with a sharper consequence: a retire whose
response carries no character closes the confirmation, leaves the row reading `active`, and
fires no receipt — so there is no `Undo` and no statement of what happened.

The guard's own comment (`:145-150`) is explicit that a receipt must not assert an
unconfirmed mutation, which is right; what is missing is that *silence* asserts the same
thing to a human. The failure vocabulary this page already owns (`failure = 'load' | 'search'`,
`LifecycleConfirmDialog.FAILURE_COPY`) has no member for it.

**Fix:** treat an absent post-write row as a failure rather than as a quiet return — keep the
overlay open and let its existing authored copy render:

```ts
const updated = await updateAdminCharacter({ characterId: id, ...args });
if (!updated) {
  // No confirmed post-write row: this is not a success, and closing on it reads as one.
  throw new Error('no post-write row');   // the Sheet's catch renders GENERIC_COPY
}
selected = null;
applyRow(updated);
toast(...);
```

and the same in `applyLifecycle`, whose rejection the confirmation dialog already renders
(`LifecycleConfirmDialog.svelte:78-86`).

### IN-02: A debounced keystroke can re-apply a stale term after "Clear filters"

**File:** `web/src/lib/components/admin/CharacterFilterBar.svelte:53-57`,
`web/src/routes/(authed)/admin/characters/+page.svelte:304-310`

**Issue:** `clearFilters()` resets `term`, `status`, `playerId` and reloads, but it does not
cancel the filter bar's in-flight 250ms debounce timer. Type into the search box and click
**Clear filters** within 250ms: the timer fires afterwards with the stale raw string,
`onsearch` sets `term` back and issues another read. The list ends up filtered again with the
input repopulated. Narrow window and self-correcting, hence Info.

**Fix:** expose a `reset()` from the filter bar (or accept `term` as `$bindable` and clear the
timer in a `$effect` keyed on it) and call it from `clearFilters`.
