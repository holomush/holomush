## Skipped Issues

### WR-02 (the substantive half): "the depth-0 `@reference` directive is a BARE specifier and will fail the build"

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:219-229`
**Reason: the finding's central claim is empirically false.** The proposed fix
(`app.css` → `./app.css`) was **not** applied.

WR-02 states that `@reference "app.css";` is package-resolved and *"will most
likely fail the build looking for a package named `app.css`"*. I tested this
against a real build rather than reasoning about it:

- Created `web/src/probe-tmp.svelte` — a genuine depth-0 component — carrying
  `@reference "app.css";` and one `@media (width < theme(--breakpoint-md))` rule,
  and imported it into `+error.svelte` so Vite actually compiled it.
- `task web:build` **succeeded**, and the emitted CSS contains
  `@media not all and (width>=48rem){.probe-tmp…}` — so `theme()` **resolved**.
  @tailwindcss/vite resolves the bare specifier relative to the importing file.
- Switching the probe to `./app.css` builds **identically**.

Both spellings work. Changing a working value on a disproven rationale, and
writing a comment asserting an ambiguity my own evidence contradicts, would be
worse than leaving it. The build evidence is recorded on `referenceDirectiveFor`
so the argument is not re-litigated from first principles, and the *legitimate*
half of the finding — a pinning case that could never be exercised — was fixed
(see above).

The one residual argument for `./` that my probe does **not** settle: a package
literally named `app.css` in `node_modules` could in principle shadow the bare
specifier. No such package exists, and this is hypothetical rather than the
failure WR-02 asserted.

### IN-01: `$app/stores` is the deprecated import for page state

**File:** `web/src/routes/(authed)/admin/+layout.svelte:6`, `:19`
**Reason: repo-wide deprecation, not a phase-06.1 defect; fixing one of eight
call sites would violate a CLAUDE.md MUST.**

`$app/stores` is used by **eight** files under `web/src`, uniformly:

```
src/routes/c/[id]/+page.svelte:6
src/routes/(authed)/+layout.svelte:6
src/routes/(authed)/characters/[id]/+page.svelte:6
src/routes/(authed)/admin/+layout.svelte:6      <- the one in scope
src/routes/(authed)/scenes/[id]/+page.svelte:7
src/routes/reset/confirm/+page.svelte:7
src/lib/components/TopBar.svelte:7
src/lib/components/scenes/ScenesShell.svelte:19
```

Converting only the admin layout leaves two idioms in sibling layouts
(`(authed)/+layout.svelte` on `$app/stores`, `(authed)/admin/+layout.svelte` on
`$app/state`), which CLAUDE.md's *"MUST match conventions — follow existing
project patterns"* forbids and which is more confusing to a future reader than
uniform deprecation. Converting all eight touches seven files this review did
not examine and is a migration in its own right.

Nothing is failing today: SvelteKit is 2.69.3 (well past 2.12, so `$app/state`
is available), the deprecation is warn-only, removal is scheduled for SvelteKit
3, and `task web:test`'s svelte-check pass reports 0 errors with none of its 19
warnings relating to `$app/stores`.

**Recommendation:** file a single repo-wide migration converting all eight sites
in one change, rather than absorbing one of them here.
