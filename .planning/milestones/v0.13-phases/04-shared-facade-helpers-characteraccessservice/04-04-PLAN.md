Extend `GetCharacterProfile` to build the profile from the composition 01-SPEC
section 8.5.1 requires and plan 04-01 stubbed out.

After the reachability check succeeds, enumerate the character's property rows
through `characterAccessWorldReader.ListPropertiesByParent` with
`world.HumanCaller(viewerSubject)`, parent type `character`, and the character
ULID. That call applies **term B only** — it evaluates `read` on
`property:<id>` and nothing else.

**Walk that slice ONCE and build two things from it** (this is the fix for review
finding HIGH-5 and it is not optional — writing only the first of the two
produces a profile whose every field is empty):

  1. `byID map[string]*world.EntityProperty`, keyed on the row id string — the
     **value source**;
  2. `[]profilevis.Property`, each carrying that same row id and the row name —
     the **evaluator input**.

Then call `characterAccessProfileVisibility.VisibleAttributes` with the same
viewer subject and character id. That call re-evaluates reachability first, then
per row evaluates term A (`read_profile_attribute`) **and** term B (`read`).

**The returned `map[string]profilevis.Property` is the ADMISSIBILITY SET, not the
value source.** `profilevis.Property` is `{ID, Name}` and nothing else
(`internal/access/profilevis/profilevis.go:106-114`); it carries no value, no
image payload and no gallery entry by design, and its `Name` doc comment explains
why the type stays that narrow. Build the response by iterating the visible map
and, for each entry, looking its `ID` up in `byID` to obtain the value. A field is
emitted only when it appears in the visible map; its value comes only from the
row the same enumeration returned.

This is **not** a second read and it does **not** weaken criterion 5. `byID` is
built from the identical term-B-filtered slice that fed the evaluator — one call
to `ListPropertiesByParent`, one pass, two views of the same rows. Do **not**
"fix" the missing values by calling `ListPropertiesByParent` a second time, by
widening `profilevis.Property`, or by reaching for a property repository: the
last of those does not compile (the facade's narrow interfaces name no
`ListByParent`, D-79) and the first two are the unfiltered-source improvisation
criterion 5 forbids. Say all of this in a comment at the join.

An id present in the visible map but absent from `byID` is an **error**, not a
skip: both sets are derived from one slice, so a divergence means the evaluator
returned an id the enumeration never supplied. Return `codes.Internal` through
the same `errutil.LogErrorContext` path an evaluation failure takes; never emit
the field with a zero value and never drop it silently.

Term B is deliberately evaluated twice under this composition. Accept the
redundancy: `A and B and B` is `A and B`, both gates are shipped, and the
alternative — enumerating with a non-viewer caller — either requests the system
bypass (which would hand the facade every row and contradict criterion 5
outright) or removes the compile fence's meaning. Record the choice in a comment
at the call site.

Do **not** collapse `profilevis`'s two evaluations into one. Its package doc
warns that doing so silently reopens the hole section 8.5.1.1 exists to close and
that the hole has no symptom of its own; plan 02-08 shipped a regression test
that turns red if term B is dropped.

Map the two `profilevis` outcomes exactly as plan 04-01 established: the
unreachable code takes the uniform not-found path, the evaluation-failed code
becomes `codes.Internal` with a generic message after
`errutil.LogErrorContext`. An enumeration error from `ListPropertiesByParent`
takes the same `Internal` path — an infrastructure failure must never surface as
a legitimately sparse profile.

`projectPublic` takes the joined result — the admitted `(name, value)` pairs
produced above — as its input, and emits nothing the join did not admit. Give it
the joined pairs rather than the raw `[]*world.EntityProperty` slice, so the
projection function cannot reach a value the conjunction did not permit. A row
whose value is the empty string (or whose `Value` pointer is nil) is **omitted**,
not emitted — a blank field and a withheld field must look identical on the wire
(01-SPEC section 7.5). Fill
`primary_image` from `profile.image.primary` and `gallery` from the ten
zero-padded slot names when those rows are present and visible; v0.13 seeds none,
so both stay empty in practice. Emit gallery entries in ascending slot-name
order, and sort any other repeated or map-derived output deterministically, so
Go's map-iteration order never reaches the projection. Add no visibility hint,
mask, flag map or hidden-field list to any message.

**Say the determinism claim precisely (review finding MEDIUM-D).** The property
this plan owns is that the **projection** is deterministic — the same inputs
produce the same logical message, with no dependence on Go map-iteration order.
It is **not** that ordinary protobuf encoding of a `map<string, string>` field is
byte-stable: `google.golang.org/protobuf v1.36.11` (`go.mod:58`) documents
`MarshalOptions.Deterministic` as the **opt-in** that carries "repeated
serialization of the same message will return the same bytes"
(`proto/encode.go:25-40`), and plain `proto.Marshal` promises nothing about map
field ordering. So:
  - assert the two responses with `proto.Equal` first — that is the real claim;
  - then encode both with `proto.MarshalOptions{Deterministic: true}.Marshal(...)`

    byte comparison meaningful rather than lucky;
  - assert the gallery **element order** on `GetGallery()` directly, since that
    one genuinely is a wire-order property of a repeated field.
This does **not** touch Task 2's sentinel byte-scan: byte *absence* is not an
ordering property, so `assert.NotContains` over a plain `proto.Marshal` result
stays correct there. Leave it as plain `proto.Marshal` and note why in a comment,
so a later reader does not "unify" the two and conclude determinism is
load-bearing for absence.

Write `internal/grpc/characteraccess_profile_test.go` in the same package,

hand-built policy set, with fakes for the world reader only.
