# Phase 01.1: Migration framework — adopt goose for Go migrations - Research

**Researched:** 2026-08-02
**Domain:** Database schema migration tooling (Go / PostgreSQL) — framework replacement + recorded-state cutover
**Confidence:** HIGH (every load-bearing goose behavior below was executed against `postgres:18-alpine` in this session, not read from docs)

## Summary

Every open question in this phase's `Raised but not discussed` list is now answered, and the answers are
mostly *simplifying*. goose v3.27.3's `Provider` API is the current, non-deprecated surface, it is what
`WithSessionLocker` attaches to, and it maps cleanly onto all six `holomush migrate` verbs except `force` —
which has **no analogue because goose does not have a dirty state at all**: goose writes the bookkeeping row
*inside the same transaction* as the migration body, so the failure mode `force` exists to repair cannot occur.
That is a genuine capability upgrade over golang-migrate, whose `SetVersion` is a separate transaction from
`Run` (`golang-migrate@v4.19.1/database/pgx/v5/pgx.go:340-370` vs `:252-268`).

The conversion itself is lower-risk than the phase framing suggests. I converted the real `000001_baseline`
(1,000+ lines, 24 tables, a `DO $$` block, and a bcrypt `$2a$10$…` literal) and the real `000005` pair to
goose single-file format and applied them through `goose.NewProvider` against a live Postgres 18: both applied
cleanly, byte-for-byte data intact. I audited all 88 files for the four ways goose's line-based splitter can
silently mangle SQL — trailing-semicolon absence, a `+goose` token in a comment, a line-terminating semicolon
inside a string literal, and a non-`$$` dollar-quote tag — and **all four are clean**. The `DO $$` handling is
the only real work, and it is smaller than stated: **17 files but only 9 of the 44 version pairs**, carrying
**24 blocks total** (`000052` alone has 9).

Three findings actively change the plan. (1) `goose_db_version` has a **fourth column**, `id integer PRIMARY
KEY GENERATED BY DEFAULT AS IDENTITY`, and `ListMigrations` orders by `id DESC` — so **the adopt seed MUST
insert rows in ascending version order** or `migrate down` rolls back in the wrong order; I reproduced the
breakage. (2) goose inserts a **version-0 row** when it creates the table, which the hand-written adopt DDL
must mirror. (3) `pg_dump --schema-only -T public.schema_migrations -T public.goose_db_version` removes *all*
bookkeeping including the identity-sequence DDL — D-15's third exclusion (`goose_db_version_id_seq`) is
unnecessary, verified by dump diff.

**Primary recommendation:** Build on `goose.NewProvider(goose.DialectPostgres, *sql.DB, fs.Sub(migrationsFS,
"migrations"), WithSessionLocker(...), WithSlog(...))` over `pgx/v5/stdlib` (already in the dep graph). Keep
`store.Migrator` as the wrapper type and re-point its body; the CLI, bootstrap, and ~25 call sites then need
zero shape change except `force`. Run the adopt seed inside the provider's own advisory lock via
`lock.NewPostgresSessionLocker()` *before* handing control to `Up()`, seeding version 0 plus every embedded
version `<=` the recorded `schema_migrations.version`, in ascending order.

## User Constraints (from CONTEXT.md)

### Locked Decisions

Reproduced from `.planning/phases/01.1-.../01.1-CONTEXT.md` §Implementation Decisions. Full rationale lives
there; this is the constraint set the plan must honor.

**Recorded-state cutover**
- **D-01:** Seeded row set is **derived from the embedded FS at cutover time**: read `schema_migrations.version`,
  insert one row per embedded migration version `<=` that value. Reuses `allMigrationVersions()`
  (`internal/store/migrate.go:177`). Rejected: a hardcoded 44-version list.
- **D-02:** Adopt is **automatic, guarded by the presence of both tables**: if `schema_migrations` exists AND
  `goose_db_version` is absent/empty, seed then proceed, in one transaction. No operator step. Rejected: an
  explicit `holomush migrate adopt` verb.
- **D-03:** The seed is wrapped in goose's **`WithSessionLocker`** (Postgres advisory lock) and re-reads
  `goose_db_version` emptiness **inside the lock** before seeding. Rejected: a bare transaction + emptiness
  check; adding a `UNIQUE` index to `goose_db_version.version_id`.
- **D-04:** After seeding, the old table is **renamed to `schema_migrations_pre_goose`** inside the adopt
  transaction. Rejected: leaving it untouched; dropping it. Reversibility: one-way.
- **D-05:** When `schema_migrations.dirty = true`, adopt **refuses and aborts boot**, naming the dirty version.
  Rejected: seeding up to but excluding the dirty version; seeding it with a warning.
- **D-06:** Adopt performs **no schema verification** — it trusts the version, guarded only by D-05.
  Compensating control is D-16's rehearsal. Rejected: a sentinel-object check; a full golden-dump diff.

**Go/SQL interleaving**
- **D-07:** Criterion 4's proof is an **integration test with a fixture chain** — a small SQL→Go→SQL chain in a
  testcontainer, Go step observing the prior SQL step's effect. Nothing permanent added to the real chain.
  Rejected: shipping a throwaway no-op Go migration; hunting for real Go-requiring work.
- **D-08:** Go migrations live in the **same directory, mixed**: `internal/store/migrations/` holds both
  `000053_x.sql` and `000054_y.go` as package `migrations`, blank-imported by `internal/store`.
  `//go:embed migrations/*.sql` unaffected. Rejected: a separate `gomigrations` package; registering from
  `internal/store` itself. Reversibility: costly.
- **D-09:** A Go migration whose effect cannot be reverted has a **down that returns an error** naming why.
  Rejected: a documented no-op down; forbidding irreversible work from being a migration.
- **D-10:** Go migrations are **transactional by default** (`AddMigrationContext`);
  `AddMigrationNoTxContext` requires a comment naming the statement that forbids a transaction. D-22 requires
  the backfill to roll back on collision, which only holds inside a transaction.

**Converting the corpus**
- **D-11:** The 88 files become 44 via a **script plus a mechanical byte-equality proof**: converter merges each
  pair (one SPDX header, `-- +goose Up` / `-- +goose Down`), flags every `$$`-containing body for explicit
  `StatementBegin`/`StatementEnd`, then a verification step re-splits each converted file and asserts
  byte-identity against the originals **before** they are deleted. Rejected: human-reviewed diff;
  hand-converting all 44.
- **D-12:** New migrations **stay sequential numeric** (`000054`, …); the existing 44 are **not renumbered**.
  Reversibility: one-way in practice.
- **D-13:** A **meta-test enforces `$$` ↔ `StatementBegin`/`StatementEnd` pairing** across
  `internal/store/migrations/*.sql`, failing CI otherwise. The existing files are its first passing fixtures.
  Rejected: documenting the rule only; a converter-time check with nothing durable.
- **D-14:** The converter is **throwaway** — it and the equality proof run once during the PR, the result is
  recorded in the PR description, neither is committed. Rejected: committing it under `scripts/`; keeping the
  verification as a test pinned to a historical commit.

**Proof and rollout**
- **D-15:** Criterion 1's proof is a **one-time `pg_dump --schema-only` diff with the bookkeeping objects
  excluded** (`schema_migrations`, `goose_db_version`, `goose_db_version_id_seq`), pre- vs post-conversion,
  which must be empty; bookkeeping end-state asserted separately (`goose_db_version` present with 44 rows, no
  `schema_migrations`). Recorded in the PR, nothing committed. Rejected: a committed golden dump plus CI gate;
  whole-dump diff with an allowlisted delta.
- **D-16:** Rollout takes a **fresh `pre-deploy:` Kopia snapshot immediately before the cutover deploy, and
  rehearses on it first** via `sandbox-restore.md` "Restore path A". Rejected: rehearsing against the most
  recent existing snapshot; treating the integration test as sufficient.
- **D-17:** The **cutover ships alone** — no new migrations in the release that performs it. Rejected: shipping
  Phase 2's migrations alongside; enforcing isolation only for the sandbox. Reversibility: reversible, but
  reversing it forfeits D-18.
- **D-18:** The rollback procedure goes in **`sandbox-restore.md` with an explicit expiry note and a tracked
  removal issue**. Valid for exactly one deploy window. Rejected: PR description only; a permanent section
  with no expiry.

### Pattern 1: Provider construction (the D-03-implied API)

```go
// Source: goose@v3.27.3/provider.go:58, provider_options.go:74,225; lock/postgres.go:71
// EXECUTED against postgres:18-alpine 2026-08-02 — applies migrations, Status/GetDBVersion OK.
import (
    "database/sql"
    "io/fs"

    _ "github.com/jackc/pgx/v5/stdlib"
    "github.com/pressly/goose/v3"
    "github.com/pressly/goose/v3/lock"
)

func newProvider(db *sql.DB, logger *slog.Logger) (*goose.Provider, error) {
    sub, err := fs.Sub(migrationsFS, "migrations") // goose globs "*.sql" at fsys ROOT, non-recursive
    if err != nil {
        return nil, err
    }
    locker, err := lock.NewPostgresSessionLocker()
    if err != nil {
        return nil, err
    }
    return goose.NewProvider(
        goose.DialectPostgres, db, sub,
        goose.WithSessionLocker(locker), // D-03
        goose.WithSlog(logger),          // structured logging; see WithVerbose caveat below
    )
}
```

Notes that matter:
- **`fs.Sub` is required.** `collectFilesystemSources` calls `fs.Glob(fsys, "*.sql")` and `fs.Glob(fsys,
  "*.go")` at the fsys root and does **not** recurse (`provider_collect.go:38-45`). Passing `migrationsFS`
  raw yields zero sources → `ErrNoMigrations`. This replaces golang-migrate's `iofs.New(migrationsFS,
  "migrations")` (`internal/store/migrate.go:66`).
- **No scheme rewrite.** goose takes a `*sql.DB`, so the `postgres:// → pgx5://` rewrite at
  `internal/store/migrate.go:71-78` **disappears**. `sql.Open("pgx", url)` accepts `postgres://` and
  `postgresql://` directly. Two existing tests assert the rewrite and must be deleted or restated:
  `TestNewMigratorPostgresqlSchemeIsConvertedToPgx5` (`internal/store/migrate_test.go:28`) and the
  golang-migrate "unknown driver" error paths at `cmd/holomush/main_test.go:150` and
  `cmd/holomush/core_test.go:138`.
- **`WithSlog` / `WithVerbose`.** goose's `logf` is a **no-op unless `WithVerbose(true)`**
  (`provider_run.go:71-73`: `if !p.cfg.verbose { return }`). If per-migration progress logging is wanted at
  boot, `WithVerbose(true)` is mandatory alongside `WithSlog`. `WithSlog` and `WithLogger` are mutually
  exclusive (`provider_options.go:202-237`).
- **Pool sizing.** goose documents a deadlock: Go migrations receive `*sql.DB` while the session lock is held
  on a `*sql.Conn`; with `MaxOpenConns == 1` a `NoTx` Go migration deadlocks. goose guards it with an error
  (`provider_run.go:43-53`). Do **not** set `db.SetMaxOpenConns(1)` on the migrator's pool.

### Pattern 2: The adopt gate (D-01..D-06) — the shape the mechanics force

```go
// Ordering, zero-row, and DDL below are all VERIFIED by execution; see §Common Pitfalls 1-3.
```

Sequence, inside `pg_try_advisory_lock` (same lock id goose uses — `lock.DefaultLockID`):

1. `to_regclass('public.schema_migrations') IS NULL` → **skip** (fresh DB: CI, testcontainers, new deploy).
2. Re-read `goose_db_version` emptiness **inside the lock** → non-empty ⇒ **skip**, log, return nil.

3. `SELECT version, dirty FROM schema_migrations` → `dirty = true` ⇒ **abort**, `oops.Code(...)` naming the
   version (D-05).
4. `BEGIN`
   - `CREATE TABLE goose_db_version (…)` — or call `database.NewStore(database.DialectPostgres,
     "goose_db_version").CreateVersionTable(ctx, tx)` to avoid duplicating the DDL string.
   - `Insert(version 0)`, then **every embedded version `<= recorded`, in ASCENDING order**. Prefer
     `store.Insert(ctx, tx, database.InsertRequest{Version: v})` over hand SQL — it is the exported seam
     (`goose@v3.27.3/database/store.go:33`).
   - `ALTER TABLE schema_migrations RENAME TO schema_migrations_pre_goose` (D-04).
   - `COMMIT`
5. Release lock; hand off to `provider.Up(ctx)` (which re-acquires — the locker is re-entrant per call, not
   held across).

`allMigrationVersions()` (`internal/store/migrate.go:179-190`) already returns ascending
(`sort.Slice` at `:232`) — reuse it directly and **do not** route through a `map` on the way to the INSERT.

### Pattern 3: Go migrations and the `*sql.Tx` ergonomics wrapper

goose's Go-migration contract, verbatim (`goose@v3.27.3/register.go:10-52`):

```go
type GoMigrationContext      func(ctx context.Context, tx *sql.Tx) error   // transactional  (D-10 default)
type GoMigrationNoTxContext  func(ctx context.Context, db *sql.DB) error   // non-transactional (needs comment)

func AddMigrationContext(up, down GoMigrationContext)          // version from runtime.Caller(1) filename
func AddMigrationNoTxContext(up, down GoMigrationNoTxContext)
```

A `000055_backfill_names.go` in `internal/store/migrations/` therefore looks like:

```go
// SPDX-License-Identifier: Apache-2.0
// Copyright 2026 HoloMUSH Contributors

package migrations

import (
    "context"
    "database/sql"

    "github.com/pressly/goose/v3"
)

func init() {
    goose.AddMigrationContext(upBackfillNames, downBackfillNames) // D-10: transactional by default
}

func upBackfillNames(ctx context.Context, tx *sql.Tx) error { /* … */ }

func downBackfillNames(ctx context.Context, tx *sql.Tx) error {
    // D-09: irreversible → refuse, do not silently succeed.
    return oops.Code("MIGRATION_IRREVERSIBLE").
        Errorf("000055 backfilled normalized names in place; the pre-normalization values are not recoverable")
}
```

**On the requested helper (CONTEXT "raised but not discussed" item 1).** The honest finding is that the gap is
smaller than feared, and the *minimal* wrapper is the right one:

- `*sql.Tx` already has `QueryContext` / `QueryRowContext` / `ExecContext` with `$1` placeholders and
  Postgres-native types via the pgx stdlib driver. Phase 2's backfill is `SELECT id, name … / UPDATE … SET
  normalized_name = $1 WHERE id = $2` — plain `database/sql` handles that with no ceremony. I executed exactly
  this shape (§Pattern 4 below).
- What `database/sql` **does not** give you that the repo's pgx code relies on: `pgx.CollectRows` / typed row
  scanning, `pgtype` for `bytea`/`jsonb`/array columns, and `CopyFrom`. If Phase 2's backfill touches only
  `TEXT` and `ULID`-as-`TEXT` columns (`internal/store/session_store.go:974` documents ULIDs are `TEXT`),
  none of these are needed.
- **Recommended minimal wrapper** — a `migrations.eachRow[T]` helper (generic scan-into-slice with
  `rows.Err()` checked) plus a `migrations.batchUpdate` that batches `UPDATE … WHERE id = ANY($1)`. That is
  ~40 lines, keeps `rows.Close()`/`rows.Err()` discipline out of every migration, and adds no new dependency.
- **Explicitly do NOT** try to hand Phase 2 a `pgx.Tx`. `stdlib.UnwrapConn`/`stdlib.Conn.Conn()` can reach the
  underlying `*pgx.Conn`, but the pgx conn is *inside* goose's `*sql.Tx` — issuing pgx-level statements on it
  while a `database/sql` transaction is open produces two views of the same session and is a footgun. The
  `*sql.Tx` **is** the transaction that D-22 depends on rolling back; keep everything inside it.

### Anti-Patterns to Avoid

- **Seeding `goose_db_version` from a `map` or an unordered set.** `id` is an identity column and
  `ListMigrations` orders by `id DESC`. Insertion order *is* rollback order. Reproduced below.
- **Passing `migrationsFS` to `NewProvider` without `fs.Sub`.** Silent `ErrNoMigrations`.
- **Reaching for the legacy globals** (`goose.Up(db, dir)`, `goose.SetTableName`, `goose.SetBaseFS`). They
  cannot take a `SessionLocker`, and `goose.SetSequential` (`create.go:23`) affects **only** `goose create`
  file generation — see §Contradictions C2.
- **Treating `-- +goose NO TRANSACTION` as per-direction.** It is a parser-level flag encountered before
  direction filtering, so one occurrence turns off the transaction for **both** up and down of that file.
- **Adding a Go migration file without an `init()` registration.** Because `//go:embed migrations/*.sql` never
  embeds `.go`, goose's own "unregistered Go migration" guard (`provider_collect.go:129-147`) **cannot fire** —
  the file is silently absent from the chain. This is a real gap; see §Open Questions Q3.
- **Grepping the converter's stdout for success.** Repo rule: judge by exit code
  (`.claude/rules/search-tools.md`).

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: The adopt seed's INSERT order silently determines rollback order — REPRODUCED

**What goes wrong:** `migrate down` rolls back the wrong migration first and fails with a confusing error.
**Why it happens:** `goose_db_version.id` is `integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY`
(`internal/dialects/postgres.go:19-27`) and `ListMigrations` is `SELECT version_id, is_applied from %s ORDER BY
id DESC` (`:44-47`). `Provider.down` walks that list in order (`provider.go:454-464`). Version order is never
consulted.

**Reproduction** (fixture: v1 creates `access_audit_log`, v5 alters it):

```
# seed inserted DESCENDING: (0), (5), (1)  →  id order 1,2,3 = versions 0,5,1
$ downcheck … DownTo(0)
DOWN ERR: partial migration error (type:sql,version:5): ERROR: relation "access_audit_log" does not exist (SQLSTATE 42P01)

# seed inserted ASCENDING (normal goose application order)
$ downcheck … DownTo(0)
ROLLED BACK v=5
ROLLED BACK v=1
```

**How to avoid:** insert ascending. `allMigrationVersions()` already sorts ascending (`migrate.go:232`) — feed
its slice directly to the INSERT loop; never route through a `map[uint]struct{}`.
**Warning signs:** a down-migration integration test that passes on a freshly-migrated DB but fails on an
adopted one. **The plan needs a test that adopts and then rolls all the way down** — a pure adopt-then-`Up()`
test cannot catch this. `[VERIFIED: executed 2026-08-02]`

### Pitfall 2: goose bootstraps the version table with a **version-0 row**

**What goes wrong:** an adopt that creates the table and seeds only real versions diverges from what goose
itself would produce; and an *empty* table hard-errors.
**Why it happens:** `tryEnsureVersionTable` does `CreateVersionTable` **and** `store.Insert(…{Version: 0})` in
one transaction (`provider_run.go:396-403`). `Provider.up` and `Provider.down` both return
`errMissingZeroVersion` when `len(dbMigrations) == 0` (`provider.go:389-391`, `:442-444`).
**Measured nuance:** I seeded `(1),(5)` **without** version 0 and `Up`/`Status`/`GetDBVersion` all worked —
the error fires only on a *completely empty* table. Nevertheless, seed version 0: it costs one row, it matches
goose's own bootstrap byte-for-byte, and criterion 1's "goose_db_version present with 44 rows" assertion should
be restated as **45 rows (44 + the zero row)** or explicitly scoped to `version_id > 0`.
`[VERIFIED: executed 2026-08-02]`

### Pitfall 3: `goose_db_version` has FOUR columns, not three

CONTEXT.md records it as `(version_id, tstamp, is_applied)`. The real DDL in v3.27.3 is:

```sql
CREATE TABLE goose_db_version (
	id integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
	version_id bigint NOT NULL,
	is_applied boolean NOT NULL,
	tstamp timestamp NOT NULL DEFAULT now()
)
```

Note `tstamp` is `timestamp` (**without** time zone) — which is why the D-15 exclusion matters doubly: it would
otherwise trip `task lint:no-timestamptz` (`Taskfile.yaml:899-917` matches `\bTIMESTAMP\b`). The lint scans
`internal/store/migrations/*.up.sql` only, so goose's own table is out of its reach — but a converter that
emits `*.sql` **changes that glob's match set to zero**. See §Which Meta-Tests Break, row L1.
`[VERIFIED: goose@v3.27.3/internal/dialects/postgres.go:19-27]`

### Pitfall 4: `-T` exclusion for D-15 — only **two** flags needed, and it works

**What I expected to go wrong:** the identity sequence `goose_db_version_id_seq` dumping as a separate
`CREATE SEQUENCE` that `-T` on the table would not remove.
**What actually happens:** pg_dump 18 emits the identity as
`ALTER TABLE public.goose_db_version ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY (SEQUENCE NAME
public.goose_db_version_id_seq …);` — attached to the table, and removed by `-T`. Verified by dumping a DB
carrying `schema_migrations`, `goose_db_version`, and an app table:

```
$ pg_dump --schema-only                                              # 3 tables + identity ALTER + 3 PKs
$ pg_dump --schema-only -T public.schema_migrations -T public.goose_db_version
CREATE TABLE public.app_thing ( … );
ALTER TABLE public.app_thing OWNER TO postgres;
ALTER TABLE ONLY public.app_thing ADD CONSTRAINT app_thing_pkey PRIMARY KEY (id);
# → zero goose/schema_migrations lines remain
```

**Consequence for D-15:** the exclusion list is `schema_migrations` and `goose_db_version`. The third named
object (`goose_db_version_id_seq`) is **not needed** — see §Contradictions C1.
`[VERIFIED: executed against postgres:18-alpine 2026-08-02]`

### Pitfall 5: `DO $$` without `StatementBegin`/`StatementEnd` — the failure is LOUD, not silent

D-13's rationale says an unwrapped `$$` migration "may apply *partially without erroring*". I tested this.
Converting the real `000005` **without** the wrappers and running `Up()`:

```
UP ERR: partial migration error (type:sql,version:5): ERROR: unterminated dollar-quoted string
        at or near "$$ BEGIN IF EXISTS ( … ALTER TABLE access_audit_log RENAME COLUMN policy_id TO event_id;"
        (SQLSTATE 42601)
# goose_db_version: 0, 1   ← version 5 NOT recorded
# access_audit_log columns: policy_id, policy_name, timestamp   ← nothing applied, tx rolled back
```

Under the **default transactional mode** the tear is atomic and loud. The silent-partial risk D-13 describes is
real but **conditional on `-- +goose NO TRANSACTION`**, or on a torn block whose leading fragment happens to be
valid standalone SQL. D-13's meta-test is still the right call — the reasoning in the doc rewrite should just
state the accurate failure mode so a future reader does not conclude the guard is unnecessary when they see a
loud error in practice.

The correctly-wrapped version applies cleanly:
```
APPLIED v=1 type=sql / APPLIED v=5 type=sql
columns: component, event_id, event_name, message, source, timestamp
goose_db_version: id 1|v0, id 2|v1, id 3|v5
```
`[VERIFIED: executed 2026-08-02]`

### Pitfall 6: The converter's dollar-quote detector must not match `$2a$` (bcrypt)

`internal/store/migrations/000001_baseline.up.sql:386` contains
`VALUES ('01KDVDNA…', 'testuser', '$2a$10$N9qo8uLOickgx2ZMRZoMye')`. A naive dollar-quote regex
`\$[A-Za-z0-9_]*\$` matches `$2a$`; the correct form requires an identifier start,
`\$([A-Za-z_][A-Za-z0-9_]*)?\$`. Postgres itself is not fooled (a dollar-quote tag cannot begin with a digit),
so this is purely a converter-tooling hazard — but a converter that mis-wraps line 386 in
`StatementBegin`/`StatementEnd` would silently swallow the rest of the baseline's semicolons into one giant
statement.
**Verified safe end-to-end:** I converted the real `000001_baseline` pair (wrapping only its one `DO $$`
block), applied it via goose, and got **24 tables** with the bcrypt literal round-tripping exactly:
`$2a$10$N9qo8uLOickgx2ZMRZoMye`. `[VERIFIED: executed 2026-08-02]`

### Pitfall 7: `extractAnnotation` treats ANY comment containing `+goose` as an annotation — and errors on unknowns

`parser.go:127` triggers on `strings.HasPrefix(TrimSpace(line), "--") && strings.Contains(line, "+goose")`;
`extractAnnotation` then does `strings.ReplaceAll(line, "--", "")` (removing *all* `--`, not just the prefix)
and rejects anything not in the supported set (`parser.go:319-351`). A doc comment like
`-- see the +goose docs` becomes a hard parse error.
**Corpus is clean:** `rg -l '\+goose' internal/store/migrations/` → zero matches. But the rewritten
`.claude/rules/database-migrations.md` should warn about it, since the doc rewrite itself will be full of the
token. `[VERIFIED: rg over internal/store/migrations/, 2026-08-02]`

### Pitfall 8: `task test` will look green while integration is broken

`task test` does not compile `//go:build integration` files (`CLAUDE.md` §Testing). This phase changes
`store.Migrator`'s method set (`Migrate(uint)` and `Force(int)` have no direct goose analogue) and **~15
integration files consume it**. Every task touching `Migrator` must gate on `task test:int`, not `task test`.

### Pitfall 9: `WithSlog` alone logs nothing

`Provider.logf` returns immediately unless `cfg.verbose` (`provider_run.go:71-73`). If the plan wants
"applying migration N" lines at boot (the current CLI prints "Applying migrations…" itself, so this may be
optional), it must pass `WithVerbose(true)` in addition to `WithSlog`.

## Contradictions With Locked Decisions

Flagged rather than worked around, per instruction. None are blocking; all are small corrections.

**C1 — D-15's third excluded object is unnecessary.** D-15 names three objects to exclude:
`schema_migrations`, `goose_db_version`, `goose_db_version_id_seq`. Verified by dump: `pg_dump --schema-only
-T public.schema_migrations -T public.goose_db_version` already removes the identity-sequence DDL, because
pg_dump attaches it to the column via `ALTER TABLE … ADD GENERATED BY DEFAULT AS IDENTITY (SEQUENCE NAME …)`
rather than emitting a standalone `CREATE SEQUENCE`. A third `-T public.goose_db_version_id_seq` is harmless
but will not match anything. **Recommendation: keep D-15's intent, drop the third flag, note why.**

**C2 — `SetSequential` is not a load-bearing surface for D-12.** CONTEXT §Canonical References lists
`SetSequential` among the "load-bearing surfaces confirmed via Context7". In v3.27.3 it is a package-level
setter used **only** by `goose create` / `CreateWithTemplate` file generation (`create.go:19-31`; grep for
`sequential` in `goose/*.go` returns only `create.go` and `fix.go`). It has **no effect** on how existing
migrations are read or ordered, and the Provider API has no equivalent option. Since HoloMUSH authors
migration files by hand and does not wrap `goose create`, D-12 ("new migrations stay sequential numeric") is
satisfied by convention + the M1 filename meta-test, not by `SetSequential`. **If** the plan adds a
`holomush migrate create` helper, `SetSequential(true)` becomes relevant. D-12's *decision* is unaffected;
only its cited mechanism is wrong.

**C3 — "17 of the 44 migrations contain `DO $$`" is 17 of the 88 *files*, i.e. 9 of the 44 *pairs*.** D-11's
prose and CONTEXT §Corpus facts both say "17 files contain `DO $$`" (correct) but D-11 phrases it as
"**17 of the 44** migrations". After merging, **9** of the 44 single-file migrations will carry
`StatementBegin`/`StatementEnd`, containing **24** blocks. The converter's scope is unchanged; only the count
in the doc rewrite and the PR description should be stated correctly.

**C4 — criterion 1's "goose_db_version present with 44 rows".** goose's own bootstrap inserts a version-0 row,
so a correctly-adopted or freshly-migrated database has **45** rows. Restate as "44 rows with `version_id > 0`,
plus goose's version-0 bootstrap row", or the assertion will fail against a correct database. (See Pitfall 2.)

**C5 — D-13's stated failure mode.** "a future `$$` migration without the wrapper is torn at semicolons and
may apply *partially without erroring*". Measured: under goose's default transactional mode the tear produces
`ERROR: unterminated dollar-quoted string` and the whole migration rolls back — loud and atomic. The silent
variant requires `-- +goose NO TRANSACTION`. The decision stands; the rationale text should be corrected so a
future reader does not delete the guard after observing a loud failure.

## Shape of the Conversion Commit (CONTEXT "raised but not discussed" item 3)

No external best practice governs this; it is a judgement call. Grounded recommendation:

**Recommended: three commits on one PR, in this order.**

1. **`refactor(store): swap golang-migrate for goose`** — `go.mod`/`go.sum`, `internal/store/migrate.go`
   rewrite, `migrate_adopt.go`, `cmd/holomush/migrate.go` `force` decision, all test rework (M7, S2, S5).
   **Migrations untouched — still 88 `.up.sql`/`.down.sql` files.** This commit is *not* green on its own:
   goose cannot parse `.up.sql`/`.down.sql`. That is the fundamental problem with any staging attempt.
2. **`refactor(store)!: convert 44 migration pairs to goose single-file format`** — the 88→44 file change plus
   `migrate.go`'s suffix filters (M2), `Taskfile.yaml:899` (L1), `migrate_embed_test.go` (M1),
   `MigrationSectionForTest` (M6) and its three callers (M3–M5).
3. **`docs(migrations): rewrite the migration rule and contributor guide for goose`** — S6, S7, S8, plus D-18's
   `sandbox-restore.md` rollback section with its expiry note and tracked issue.

**Bisectability, honestly assessed.** Commits 1 and 2 are **not independently green** in either order — the
engine and the file format must change together. Splitting them buys reviewability (an 88-file rename diff is
unreadable next to a 300-line engine rewrite), not bisectability. The repo squash-merges every PR
(`CLAUDE.md` §Protected Branch Policy), so `git bisect` on `main` sees **one** commit regardless; the
intermediate red state never reaches `main`. **Recommendation: split for review, state plainly in the PR body
that commits 1–2 are a unit, and do not attempt to make each individually green** — the alternatives
(shipping a temporary dual-format reader, or `git mv`-ing files in a third commit) add real code to buy an
illusory property.

**Reject the single-88-file-commit option** on review grounds only: `git` will render 44 deletes + 44 adds
rather than 44 renames (content changes exceed the similarity threshold once the annotations are inserted), so
the diff is unreviewable either way — but at least commit 2 in isolation contains *nothing but* that noise,
letting a reviewer read commit 1 cleanly and validate commit 2 by the byte-equality proof instead of by eye.
That is exactly what D-11's proof exists to enable, and D-17's "cutover ships alone" already guarantees the
release-level isolation.

## Open Questions

1. **What should `holomush migrate force` become?**
   - *What we know:* goose has no dirty state, so `force`'s purpose is gone. Three options: remove the
     subcommand (honest, breaks any operator muscle memory / runbook); keep it as a non-zero-exit guidance
     message (preserves the command surface, is not a lie); keep it and implement raw `goose_db_version`
     surgery via `database.Store` (preserves the capability, but hands operators a foot-gun for a problem that
     no longer exists).
   - *What's unclear:* whether any operator runbook or `sandbox-operations.md` procedure references
     `migrate force`. Worth one grep during planning.
   - *Recommendation:* **keep-with-guidance**. It satisfies criterion 3's spirit, requires ~10 lines, and its
     message is the natural place to explain why the dirty state is gone. Removal is defensible; silent
     surgery is not.

2. **Should `Migrator.Version()` keep its `dirty bool` return?**
   - *What we know:* 6 call sites read it (`cmd/holomush/migrate.go:206-217` prints "Status: DIRTY"; the rest
     discard it with `_`). Under goose it is permanently `false`.
   - *Recommendation:* keep the signature for this release with a doc comment stating it is always `false`, and
     have `migrate status` stop printing the DIRTY branch. Drop the return in a follow-up. Changing it now
     bloats an already-large diff.

3. **Should the two new mechanical guarantees become registry invariants?**
   - *What we know:* `.claude/rules/invariants.md` says register a guarantee when "violating it is a
     *regression in a guarantee* rather than a *missing feature*". Two candidates qualify:
     (a) the adopt seed inserts in ascending version order (silently breaks rollback if violated);
     (b) every `.go` file in `internal/store/migrations/` registers itself in `init()` (goose's own
     unregistered-Go guard **cannot** fire here, because the embed globs `*.sql` only — see §Anti-Patterns).
   - *What's unclear:* the right scope. `INV-STORE-N` is the obvious home (`invariants.yaml` already has
     INV-STORE-1..9 per `internal/store/spec_meta_test.go:47-60`).
   - *Recommendation:* register both as `INV-STORE-*` with `binding: bound`, asserted by C2d and a new
     registration meta-test respectively. Guard (b) does not exist in any form today and is a genuine hole
     Phase 2 will walk into.

4. **Does criterion 1's "44 rows" become "45"?**
   - See §Contradictions C4. Needs a one-word decision from the planner before the assertion is written.

5. **Does `test/testutil/postgres.go:308` (the shared-template migrator) need a lock-related change?**
   - *What we know:* it calls `store.NewMigrator(tmplConnStr)` + `Up()` inside a `sync.Once` to build a
     template database. With a session locker attached this now takes a `pg_try_advisory_lock` — harmless, but
     it serializes template creation across parallel test binaries hitting the same shared Postgres.
   - *What's unclear:* whether that measurably slows `task test:int`. Probably not (it is already inside a
     `sync.Once`), but worth watching.
   - *Recommendation:* no pre-emptive change; measure.

6. **Nothing found on `-- +goose ENVSUB`.** goose supports `ENVSUB ON`/`ENVSUB OFF` annotations that
   interpolate environment variables into migration SQL (`parser.go:185-191, 211-217`). No migration uses it
   and nothing in this phase needs it, but the doc rewrite should say so explicitly — an env-var-interpolating
   migration is a supply-chain/config-injection surface the repo should decide against on purpose rather than
   by omission.
