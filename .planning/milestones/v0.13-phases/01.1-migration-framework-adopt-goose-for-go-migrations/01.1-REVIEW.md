# Phase 01.1: Code Review Report

**Reviewed:** 2026-08-02
**Depth:** deep
**Files Reviewed:** 30
**Status:** issues_found

## Summary

The adopt gate (`internal/store/migrate_adopt.go`) is the highest-stakes file in
the diff and it holds up under the concurrency and atomicity questions it was
asked to answer. Every probe runs inside the session advisory lock on a pinned
`*sql.Conn`; the seed, the bootstrap top-up, and the archive rename all run in
one `BeginTx` on that same connection; every error path returns before the
commit with the rollback deferred; the dirty refusal writes nothing. I verified
against goose v3.27.3 source that `database.store.CreateVersionTable`
(`database/dialects.go:91-97`) does **not** insert a version-0 row — so the
`!gooseExists ⇒ bootstrapPresent = false ⇒ Insert(0)` path at
`migrate_adopt.go:236-246` cannot duplicate the bootstrap row, and that
`Provider.Close` (`provider.go:213-215`) closes the `*sql.DB`, so
`Migrator.Close` releases the handle adopt borrows. I found no defect in the
lock/transaction story.

The one real defect is elsewhere: the phase's whole guard architecture rests on
a single 11-line annotation recognizer, `gooseAnnotation`, and that recognizer
does not match goose's actual parser. goose compares annotations with
`strings.EqualFold` and tolerates a tab separator; the repo's recognizer is
case-sensitive and requires a literal space. Two guards — the ENVSUB
config-injection-into-DDL refusal and the dollar-quote `StatementBegin/End`
wrapping check — go silently blind on inputs the engine happily applies. The
code comment justifying the exact-match approach asserts the opposite of what
goose does.

Beyond that: three exported up-paths bypass the adopt gate, and `migrate up
--dry-run` prints an actively wrong preview on exactly the database an operator
would preview before the cutover.

Test quality is unusually high — non-vacuity floors, paired positive controls,
set equality over counts, ordering asserted through the identity column goose
actually consults. I found no assertion that passes against broken code, and
the ACE naming and integration-file conventions (`package store_test`,
integration tag, no local `RunSpecs`) hold across the new files.

`session_store.go:974` changed for one reason only: a doc-comment path citation
of `migrations/000001_baseline.up.sql:227` that no longer exists. Correct and
intended (see IN-04 for the incomplete sweep).

## Critical Issues

### CR-01: `gooseAnnotation` does not match goose's parser — the ENVSUB and dollar-quote guards fail open

**File:** `internal/store/migrations_export_test.go:125-135`
**Also affects:** `internal/store/migrations_format_test.go:30-35`, `:65-101`, `:242-270`

`gooseAnnotation` recognizes an annotation only when the line carries the exact
byte sequence `+goose ` (literal single space) and returns the remainder
**case-preserved**, which is then compared for exact equality against
`envsubOn = "ENVSUB ON"` / `envsubOff = "ENVSUB OFF"`
(`migrations_format_test.go:37-38`) and against the literal strings
`"StatementBegin"` / `"StatementEnd"` (`migrations_format_test.go:66,77`).

goose v3.27.3's `extractAnnotation`
(`internal/sqlparser/parser.go:319-350`) does neither:

```go
cmd := strings.ReplaceAll(line, "--", "")        // :325
cmd = strings.Replace(cmd, "+goose", "", 1)      // :328
cmd = strings.TrimSpace(cmd)                     // :336
for s := range supportedAnnotations {
    if strings.EqualFold(string(s), string(a)) { // :345  <-- case-INSENSITIVE
        return s, nil
    }
}
```

Two concrete inputs goose applies and the repo's scan reports as clean:

1. **Case variant.** A migration containing

   ```sql
   -- +goose Up
   -- +goose envsub on
   CREATE TABLE tenant_cfg (dsn text NOT NULL DEFAULT '${HOLOMUSH_ADMIN_DSN}');
   -- +goose envsub off
   ```

   goose reaches `EqualFold("ENVSUB ON", "envsub on")` → true → interpolation is
   enabled and the process environment is substituted into DDL.
   `gooseAnnotation` returns `"envsub on"`, which matches neither `envsubOn` nor
   `envsubOff`, so the `case envsubOn, envsubOff:` arm at
   `migrations_format_test.go:87` never fires and
   `TestEveryDollarQuotedMigrationBodyIsWrappedInStatementBeginEnd` passes.

2. **Tab separator.** `-- +goose\tENVSUB ON` (or
   `-- +goose\tStatementBegin`): goose's `ReplaceAll`/`TrimSpace` chain yields
   `ENVSUB ON`; `gooseAnnotation`'s `strings.HasPrefix(rest, "+goose ")` at
   `:131` is false against a tab, so it returns `""`.

The consequence for `StatementBegin`/`StatementEnd` is a correctness failure,
not only a policy one: a lowercase or tab-separated `StatementBegin` leaves
`inBlock` false, so the block-tracking at `migrations_format_test.go:59-113`
mis-attributes every dollar-quote inside the block and (in the reverse case,
where goose sees a block the scanner does not) lets a `$$` body that goose will
tear apart at internal semicolons pass as wrapped. Under `-- +goose NO
TRANSACTION` that tears without a rollback.

This is a fail-open security/correctness control, and the code's own
justification for the exact-match design is factually wrong against the pinned
version. `migrations_format_test.go:33-35` states:

> "goose compares the extracted annotation against its constants by equality and
> hard-errors on anything else ("unknown annotation"), so a differently-spelled
> variant is a migration that cannot apply at all."

It compares with `EqualFold`, not equality. `gooseAnnotation`'s own doc comment
at `migrations_export_test.go:121-124` ("matching goose's own lenient parse") is
also backwards in the other direction: goose *rejects* leading whitespace
(`parser.go:320-322`) while `gooseAnnotation` `TrimSpace`s it away.

Note the exposure is bounded to `StatementBegin`/`StatementEnd`/`ENVSUB`.
`Up`/`Down` are independently pinned by exact-string assertions in
`migrate_embed_test.go:48-51`, so a case-variant `-- +goose up` is caught there.

**Fix:** make the recognizer mirror the engine — tokenize the same way and fold
case at the comparison site:

```go
// migrations_export_test.go
func gooseAnnotation(line string) string {
	trimmed := strings.TrimSpace(line)
	if !strings.HasPrefix(trimmed, "--") || !strings.Contains(trimmed, "+goose") {
		return ""
	}
	// Mirror goose's internal/sqlparser.extractAnnotation (v3.27.3:319-350):
	// strip every "--", strip the first "+goose", collapse whitespace.
	cmd := strings.ReplaceAll(trimmed, "--", "")
	cmd = strings.Replace(cmd, "+goose", "", 1)
	return strings.Join(strings.Fields(cmd), " ")
}
```

and fold case where the result is matched:

```go
// migrations_format_test.go — inside statementBlockViolations
switch strings.ToUpper(gooseAnnotation(line)) {
case "STATEMENTBEGIN": ...
case "STATEMENTEND":   ...
case envsubOn, envsubOff: ...   // constants are already upper-case
}
```

`migrationSection` (`migrations_export_test.go:69-118`) needs the same fold for
its `"Up"`/`"Down"`/`"StatementBegin"`/`"StatementEnd"` switches. Add table
rows to `TestStatementBlockViolationsFlagsDollarQuotesOutsideStatementBlocks`
(`migrations_format_test.go:129-207`) for `-- +goose envsub on` and
`-- +goose\tENVSUB ON` — both must go RED before the fix. Correct the two
factually wrong comments in the same change.

## Warnings

### WR-01: `Migrate()` and `Steps(n>0)` are upward migration paths that bypass the adopt gate

**File:** `internal/store/migrate.go:173-198`, `internal/store/migrate.go:204-234`

`Up()` is documented (`migrate.go:137-140`) as "the ONLY entry point that fires
the one-shot cutover", and the design decision that read-only verbs must not
trigger it is settled and correct. But `Migrate()` and `Steps(n)` are neither
read-only nor gated: both are exported methods on the production `Migrator` that
run migrations **upward** — `Migrate` via `UpTo` at `:225`, `Steps` via
`UpByOne` at `:186` — with no `adoptFromGolangMigrate` call on either path, and
no word about it in either doc comment.

Concrete failure: any caller invoking `Migrate(53)` (or `Steps(5)`) against a
pre-adopt production database gets `GetDBVersion → 0`, falls into `current <
target`, and goose begins applying version 1 against a database that already
carries the full schema — failing with `partial migration error (type:sql,
version:1): relation "holomush_system_info" already exists`. That is the exact
failure the phase's own regression test documents at
`migrate_adopt_integration_test.go:292-294` as the reason the `version_id > 0`
probe filter exists.

Nothing in production reaches these today (`bootstrap.AutoMigrator` is
`{Up, Close}` only, `internal/bootstrap/migration.go:16-19`, and the CLI exposes
only up/down/status/version). The hazard is a latent trap for the next caller —
a `migrate to <version>` verb, or an operator tool — where the failure surfaces
against a real production database.

**Fix:** either route both through the gate, or make the omission explicit and
enforced. Minimum:

```go
// Steps applies n migrations. ...
//
// Steps does NOT fire the golang-migrate adopt gate. Against a database whose
// bookkeeping has not been adopted, a positive n re-applies migration 1 and
// fails. Call Up() first, or use Up() instead. See adoptFromGolangMigrate.
func (m *Migrator) Steps(n int) error {
```

Preferred: call `m.adoptFromGolangMigrate(ctx)` at the head of the `n > 0`
branch and at the head of `Migrate`'s `current < target` branch, matching
`Up()`'s unwrapped-return convention at `migrate.go:147-149`.

### WR-02: `migrate up --dry-run` reports a false preview on a pre-adopt database

**File:** `cmd/holomush/migrate.go:34-66`; contract comment at `internal/store/migrate.go:78-82`

`runMigrateUpDryRun` is built entirely from `Version()` and
`PendingMigrations()`, both of which read goose's ledger. Against a
not-yet-adopted database that ledger is empty, so the command prints:

```
Dry run - the following migrations would be applied:
  - 000001_baseline
  ... (44 entries)
Current version: 0
Target version: 53
```

The subsequent `migrate up` applies **zero** of them: adopt seeds the ledger and
goose finds nothing pending. The dry run's output is not merely stale, it is the
opposite of what will happen.

The code's own enumeration of the affected verbs (`migrate.go:79-82`) names only
"migrate status, migrate version". The operator runbook's
`#### migrate status before the cutover reports version 0`
(`site/src/content/docs/operating/how-to/database.md:87-98`) likewise covers
only those two — while `--dry-run` is listed at `database.md:27-28` as "Preview
migrations without executing", i.e. precisely the pre-deploy check an operator
runs before an irreversible cutover.

Concrete failure: an operator previews the cutover on production, reads
"44 migrations would be applied / Target version: 53" against a database that is
already at 53, concludes the binary has lost the migration history, and either
aborts the deploy or intervenes manually in a database that needed nothing done.

**Fix:** teach the dry run to detect the pre-adopt state and say so, rather than
projecting goose's empty ledger. A read-only probe is sufficient and does not
touch the irreversible path — reuse `probeTablesSQL`'s logic:

```go
// in runMigrateUpDryRun, before listing pending migrations
if preAdopt { // legacy schema_migrations present AND no goose row at version_id > 0
    fmt.Fprintln(out, "This database still uses golang-migrate bookkeeping.")
    fmt.Fprintln(out, "`migrate up` will adopt it into goose (one-shot, irreversible)")
    fmt.Fprintf(out, "and then apply migrations above the recorded version %d.\n", recorded)
    return nil
}
```

At minimum, add `up --dry-run` to the verbs named at `migrate.go:79-82` and to
the runbook section at `database.md:87-98`.

### WR-03: `readLegacyVersion` reads an unordered, uncounted single row from the legacy ledger

**File:** `internal/store/migrate_adopt.go:57`, `internal/store/migrate_adopt.go:180-193`

`probeLegacyStateSQL` is `SELECT version, dirty FROM schema_migrations` — no
`ORDER BY`, no row-count check — consumed by `QueryRowContext(...).Scan(...)`,
which silently takes whichever row Postgres returns first and discards the rest.

golang-migrate's postgres driver keeps at most one row (it truncates and
re-inserts in a transaction), so a well-formed ledger is safe. But this is the
input to a one-shot irreversible write that "trusts the recorded version"
(`migrate_adopt.go:69-72`), and a two-row ledger — reachable through a partial
restore, a merged dump, or manual repair by the very operator the dirty-refusal
message tells to "resolve it with the previous migration tooling"
(`migrate_adopt.go:331-334`) — is picked arbitrarily. If the arbitrarily-chosen
row carries the *higher* version, adopt records migrations as applied that never
ran, archives the evidence, and the divergence is permanent and undetectable by
goose. Unlike the dirty case, nothing refuses.

The empty-ledger case (zero rows → `sql.ErrNoRows` → `MIGRATION_ADOPT_PROBE_FAILED`
→ boot abort) is fail-closed and now documented at `database.md:207-238`. The
multi-row case is the one that fails *open*.

**Fix:** one deterministic read plus a count guard, at the same cost:

```go
const probeLegacyStateSQL = `SELECT version, dirty, count(*) OVER () FROM ` +
	legacyVersionTable + ` ORDER BY version DESC`

// in readLegacyVersion
var rowCount int64
scanErr := conn.QueryRowContext(ctx, probeLegacyStateSQL).Scan(&version, &dirty, &rowCount)
// ... existing ErrNoRows handling ...
if rowCount != 1 {
	return 0, false, oops.Code("MIGRATION_ADOPT_REFUSED_AMBIGUOUS_LEDGER").
		With("legacy_table", legacyVersionTable).
		With("row_count", rowCount).
		Errorf("%s holds %d rows; golang-migrate maintains exactly one, so the "+
			"recorded version is ambiguous and adopt refuses to guess", legacyVersionTable, rowCount)
}
```

Add a spec alongside `C2c` in `migrate_adopt_integration_test.go:335-368` that
inserts two rows and asserts the refusal plus the same "nothing written, nothing
archived" post-conditions.

### IN-02: `errAdoptRefusedDirty` reports "version 0" for golang-migrate's NilVersion

**File:** `internal/store/migrate_adopt.go:189-192`, `:326-336`

`readLegacyVersion` maps a negative recorded version (golang-migrate's
`NilVersion == -1`) to `recorded = 0` while passing `dirty` through unchanged.
A `(version = -1, dirty = true)` ledger therefore aborts boot with
"`schema_migrations` is marked dirty at version 0", pointing the operator at a
version that does not exist in the corpus. The state is unusual (golang-migrate
stamps `version = 1, dirty = true` on a failed first migration), so this is
cosmetic rather than behavioural — the refusal itself is correct.

**Fix:** carry the raw value into the message, e.g. `With("raw_version", version)`
before the clamp, or special-case `version < 0` into a distinct "no version
recorded" phrasing.

### IN-03: `MIGRATION_ADOPT_PROBE_FAILED` covers three distinct operator situations

**File:** `internal/store/migrate_adopt.go:135`, `:147`, `:184`, `:240`

Four sites share one code; they are distinguished only by the `operation`
context value, and the runbook now instructs the operator to read that field
first (`database.md:203`). The empty-legacy-ledger case in particular is a
boot-abort requiring a schema-dependent manual decision, surfaced under a code
whose documented remediation ("verify grants") does not apply. The phase
deliberately chose docs over a new code to avoid re-touching a
crypto-reviewed irreversible path (commit `fb241e33d`), which is a defensible
call. Recording it so the decision is revisitable when that path is next opened.
