## Cutover mechanism & trigger

### Q1 — What rule decides which rows get written into `goose_db_version`?

| Option | Description | Selected |
|--------|-------------|----------|
| Derive from embedded FS | Read `schema_migrations.version`, insert one row per embedded version `<=` it. Self-adjusting; handles the version gap for free. | ✓ |
| Hardcoded list of the 44 versions | Literal list, auditable in review, but drifts if a migration lands before shipping. | |
| You decide | Capture as Claude's discretion. | |

**User's choice:** Derive from embedded FS.
**Notes:** Preview shown and accepted. Grounded on `gooseutil.UpVersions` semantics fetched
during discussion — filesystem versions below the DB max that are unrecorded count as
missing and are re-applied under `-allow-missing`, so seeding only the current version is
the unrecoverable direction. Over-seeding is comparatively harmless (DB-only versions are
silently ignored) — a correction made mid-discussion after an earlier, overstated claim
about phantom rows.

### Q2 — What triggers the adopt step?

| Option | Description | Selected |
|--------|-------------|----------|
| Automatic, guarded by both tables | Fires when `schema_migrations` exists and `goose_db_version` is empty. No operator step anywhere. | ✓ |
| Explicit `holomush migrate adopt` | Fail-closed, operator-driven, auditable; one manual command at cutover. *(recommended)* | |
| Automatic, but only when auto-migrate is off | Splits behavior between CLI and startup paths. | |

**User's choice:** Automatic, guarded by both tables — against the recommendation.
**Notes:** Accepts an unattended irreversible write at boot. This raised the stakes on the
locking (Q3) and dirty-flag (Q5) guards, and made the sandbox rehearsal (Area 4 Q2)
load-bearing rather than precautionary.

### Q3 — How is the seed made safe against concurrent and repeat application?

| Option | Description | Selected |
|--------|-------------|----------|
| Advisory lock + re-check inside | goose `WithSessionLocker`, re-read emptiness inside the lock. | ✓ |
| Transaction + emptiness check | Simpler; two replicas can both read empty under READ COMMITTED. | |
| UNIQUE index on `version_id` + ON CONFLICT | Strongest, but modifies goose's own bookkeeping table. | |

**User's choice:** Advisory lock + re-check inside.
**Notes:** `WithSessionLocker` verified against goose docs before being offered. Framed on
not silently dropping the `Lock()`/`Unlock()` protection golang-migrate's driver provides
today.

### Q4 — What happens to the old `schema_migrations` table?

| Option | Description | Selected |
|--------|-------------|----------|
| Rename to `schema_migrations_pre_goose` | Inert but preserved; rollback becomes deliberate. | ✓ |
| Leave it untouched | Real one-release rollback path; divergence risk if anyone rolls back and migrates. | |
| Drop it in the adopt transaction | Cleanest end state; rollback requires full restore. | |

**User's choice:** Rename to `schema_migrations_pre_goose`.
**Notes:** Later became the basis for the surgical rollback path in Area 4 Q4.

### Q5 — What should adopt do when `dirty = true`?

| Option | Description | Selected |
|--------|-------------|----------|
| Refuse and abort boot | The version is a lie; seeding from it is undetectable afterward. | ✓ |
| Seed up to but excluding the dirty version | Self-healing, but partial effects remain and re-run may fail mid-adopt. | |
| Seed including it, warn loudly | Keeps boot unblocked; defers judgement to logs. | |

**User's choice:** Refuse and abort boot.

### Q6 — Should adopt verify the live schema matches the version it trusts?

| Option | Description | Selected |
|--------|-------------|----------|
| Cheap sentinel check | Assert a few objects the version implies exist. *(recommended)* | |
| No verification — the dirty guard is enough | Keeps adopt small and readable. | ✓ |
| Full diff against the golden dump | Strongest, but couples adopt to a dump format. | |

**User's choice:** No verification — against the recommendation.
**Notes:** A deliberate simplicity call. Recorded in CONTEXT.md as paired with the rehearsal
decision (D-06 ↔ D-16): the rehearsal against restored real data is the compensating control
and should not be weakened without revisiting this.

## Conversion mechanics for the 44 pairs

### Q1 — How do 88 files become 44, given 17 contain `DO $$` blocks?

| Option | Description | Selected |
|--------|-------------|----------|
| Script + mechanical equality proof | Re-split each converted file, assert byte-identity before deleting originals. | ✓ |
| Script, human-reviewed diff | Faster to build; relies on review across an 88-file diff. | |
| Hand-convert all 44 | Forces eyes on each; 44 repetitive merges is where attention lapses. | |

**User's choice:** Script + mechanical equality proof. Preview shown and accepted.
**Notes:** The 17-file `DO $$` finding came from a repo scan during discussion and is what
made this non-mechanical. A `CONCURRENTLY` hit was flagged and then retracted in the same
turn — it appears only inside a comment.

### Q2 — Versioning scheme for new migrations

| Option | Description | Selected |
|--------|-------------|----------|
| Stay sequential numeric | Continues `000054`; one scheme, citations and meta-tests intact. | ✓ |
| Switch new ones to goose timestamps | Collision-free branching; two regimes at the boundary. | |
| Sequential now, revisit if collisions bite | Defers; decided later by whoever hits it. | |

**User's choice:** Stay sequential — reached on a **second pass**.
**Notes:** First pass selected timestamps with the objection *"why do we need to keep two
numbering schemes forever? Heck, why not renumber the old ones based on their committed
timestamps?"* Investigation found `000041`–`000044` share one add-commit timestamp
(`2026-05-23T22:40:42-04:00`, a squash merge), so renumbering manufactures ordering data
tie-broken by the existing integers; it would also break the Area 1 Q1 derivation and
invalidate by-name citations like D-25's. The framing that resolved it: staying sequential
*is* the one-regime outcome — only switching to timestamps creates a second regime. The
question was re-asked with that correction and the objection was fully answered, not
overridden.

### Q3 — Preventing a future `$$` migration from missing `StatementBegin/End`

| Rule + a converter-time check only | Covers this phase, leaves the future to discipline. | |

**User's choice:** Meta-test enforcing the pairing.

### Q4 — Fate of the conversion script

| Option | Description | Selected |

## Proof durability & live-sandbox posture

### Q1 — Where does criterion 1's schema proof live?

**First pass returned no selection**, with the note: *"can't be exactly identical, migration
tracking schema is diff?"* — correct. Post-conversion carries `goose_db_version` (+ its
sequence) where pre-conversion carries `schema_migrations`, so criterion 1 is unsatisfiable
as written. Logged as roadmap amendment 2 and the question re-asked.

| Option (second pass) | Description | Selected |
|--------|-------------|----------|
| Exclude bookkeeping, one-time diff in the PR | Excluded-object dump diff; bookkeeping asserted separately. | ✓ |
| Exclude bookkeeping + assert it durably | Same diff plus a permanent bookkeeping end-state test. | |
| Diff whole dumps, allowlist the known delta | More information; pins brittle `pg_dump` text. | |

**User's choice:** Exclude bookkeeping, one-time diff in the PR. Preview shown and accepted.
