## Task 1 — the measurement, verbatim

The plan required the branch be selected by measurement. It was:

```
$ go mod why -m github.com/docker/docker
# github.com/docker/docker
(main module does not need module github.com/docker/docker)
```

Exit code 0. **The clean branch was taken.**

Note the plan's own warning held in reverse here: it predicted `go mod why -m` would exit *non-zero*
on the success path once the module left the graph. It exited **0** and reported the "does not need"
sentence instead. Either way the exit code is not the signal — the sentence is — which is exactly why
the plan marked this verify `|| true`.

Corroborating measurements, all on the post-swap tree:

| Probe | Result |
|-------|--------|
| `go mod graph` edges to `github.com/docker/docker` | **0** (of 1299 total edges) |
| positive control: `github.com/docker/go-connections` in same output | **8** matches |
| `go.sum` lines for `github.com/docker/docker` | **0** |
| `golang-migrate` in `go.mod` / `go.sum` | **0** |

The positive control is the load-bearing part. A zero-match search proves the package is absent only
if the same search can be observed matching something; without it, a typo'd pattern and a genuinely
clean graph are indistinguishable. `docker/go-connections` matching 8 times establishes the search
works over a populated 1299-edge graph.

This also settles the open question from the original triage in #4817: `testcontainers-go@v0.43.0`
reaches Docker through `docker/go-connections` and `moby/docker-image-spec`, **not** through
`docker/docker`, so the integration harness was never a second path keeping the chain alive.

## Task 1 — the gate, and why it is green for the right reason

`task lint:vuln` **exit code 0**, all three legs, with all five entries deleted.

**The verdict came from the exit code, not from matching output text.** The gate prints advisory ids
and reason strings, so a stdout match cannot distinguish pass from fail — the shape of the May-2026
re-run-loop incident recorded in `.claude/rules/search-tools.md`. Stdout was read only afterwards, as
secondary confirmation.

That secondary read answers the harder question — *green, or green because it scanned nothing?*

```
Scanned .../go.mod file and found 160 packages
Total 0 packages affected by 0 known vulnerabilities ... from 1 ecosystem.
```

160 packages walked, 0 affected. The scan ran over a populated manifest.

`task lint` exit 0. `task test` exit 0, 10423 tests — unchanged from the plan-01 baseline, as expected
for a config-only change. `task fmt` exit 0 and mutated nothing beyond the edit already made.

## Task 2 — #4817 left OPEN, deliberately

**This is a deviation from the plan's clean-branch instruction, which said to close.**

The plan's Task 2 directed closing #4817 on the clean branch. I posted the full evidence
([comment](https://github.com/holomush/holomush/issues/4817#issuecomment-5161117136) — `go mod why`
output, the removing commit, the exit-code result, the byline) but did **not** close it, because:

1. **The fix is on an unmerged branch.** `main` still carries both golang-migrate and the five
   suppressions. Closing now asserts a state of `main` that is not true yet, and if the phase PR were
   abandoned the issue would be wrongly closed with a comment that reads as proof.
2. **Repo precedent closes post-merge.** #4878 was closed citing "PR #4807 (merged, squash commit
   e701a72e5)"; #4892 explicitly declined to close while dependent work was open.

The phase PR should carry `Closes #4817` so it closes automatically on merge. **If the coordinator
prefers the plan's literal instruction, closing it now is a one-line `gh issue close` — the evidence
is already on the issue.** I chose the reversible, evidence-preserving option rather than guess.

The plan's `must_haves` truth — "never closed on the assumption that dropping golang-migrate was
sufficient" — is satisfied either way: nothing here rests on an assumption.

Verify command (a **listing**, not a gate — it exits 0 for OPEN or CLOSED alike, both being
legitimate outcomes, so the verdict is the recorded evidence, not this exit code):

```
state=OPEN  comments=1  has_byline=true  has_gomodwhy=true  has_exit0=true
```
