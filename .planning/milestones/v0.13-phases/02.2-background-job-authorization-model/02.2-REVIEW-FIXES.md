## Finding 1 — the D-29 fence claimed teeth it did not have (WR-04)

### What was wrong

`internal/access/policy/seed_profile_visibility_test.go`'s comment asserted that
"a future edit that widens this one's action to `read` or its principal to
`character` fails the same way." Both halves were false. The only assertion was a
name-set equality over seed policies whose compiled `Target.ResourceType ==
"character"`, and neither mutation changes a name or a resource type.

Phase 02.2 widened that fence by one entry — `seed:job-fixture-instance-scoped` —
and justified the exemption on **three** properties: principal is `job`, action
is `write` only, and `principal.job.name == "fixture"` is unmatchable in
production. None of the three was pinned anywhere in the tree; every other
reference to the seed is a bare name reference or a count.

### What changed

`internal/access/policy/seed_profile_visibility_test.go` only.

1. The compile loop now also captures each member's compiled target shape
   (principal type + action list) into a `map[string]characterSeedTargetShape`,
   compared against an expected map covering all three members of the family.
   This is what catches a widening of an **existing** member, which leaves the
   name set unchanged.
2. An exact-DSL + `SeedVersion` assertion for `seed:job-fixture-instance-scoped`
   pins the third leg — matchability — because the `principal.job.name ==
   "fixture"` clause lives in the `when` body, which the compiled `Target` does
   not carry. Precedent for this shape is in the same file (`untouched` map,
   `seed:admin-section-access`).
3. The comment was rewritten to state what each of the three assertions actually
   enforces, and that all three are load-bearing.

## Finding 2 — the fatal `action` gate never ran at the plugin-policy install path (CR-02)

### What was wrong

02.2-04 made the compiler's `action` branch fatal for every policy source. There
are **three** sources, not the two the phase artifacts name: in-tree seeds,
operator-authored database rows, and plugin-manifest policies installed by
`plugins.PolicyInstaller`.

The third never reached the gate. `compilePolicies` /
`compilePoliciesWithManifest` validated with `dsl.Parse` + `dsl.CompilePolicy`
only, and `ValidateManifestPolicySchemas` walks only `resource.<type>.<attr>`
references against the plugin's own declared schema. Neither reaches
`policy.Compiler`.

So a manifest policy carrying a typo'd `action.*` key parsed clean, passed both
validators, and was **persisted** by `ReplaceBySource`. `Cache.Reload` is
all-or-nothing, so from that point every reload failed corpus-wide — escalating
the policy health tier into `Engine.EnterDegradedMode` (deny-all) and failing
`BuildABACStack` on the next boot, recoverable only by hand-deleting the row. One
third-party plugin manifest could brick the host. The blast radius is new with
02.2-04; before it the same reference was skipped as dead code.

### What changed

**(a) The gate, at install time.** `internal/plugin/policy_installer.go` gained
`actionGate` — a `sync.OnceValue`-wrapped
`policy.NewCompiler(attribute.NewActionOnlySchemaRegistry().Schema())` — and
`validateActionAttributes`, called from **both** `compilePolicies` and
`compilePoliciesWithManifest`, before `ReplaceBySource`. A bad policy now fails
the plugin **load**, which `loader.go:977-989` already rolls back (unregister
providers, `host.Unload`, return).

One deliberate departure from the review's suggested patch: **no new oops code.**
`oops` resolves `Code()` to the *deepest* code in the chain, so an outer
`PLUGIN_POLICY_UNREGISTERED_ACTION_ATTRIBUTE` would never be what
`errutil.AssertErrorCode` or an operator's log filter sees — it would read as a
distinct failure class while being unreachable. The compiler's
`POLICY_UNREGISTERED_ACTION_ATTRIBUTE` surfaces instead, with `plugin` and
`policy` context keys for attribution. This is recorded in the function's doc
comment so a future editor does not "restore" the unreachable code.

**(b) Two tests.**

- `internal/plugin/policy_installer_action_gate_test.go` — all four install and
  replace entry points. The asserted property is not "returns an error" but
  "rejected **before** persistence": each case asserts the fake store recorded
  nothing, including no `ReplaceBySource` call. Two positive controls (a
  *declared* action key installs; a policy with no `action` reference installs)
  distinguish a working gate from one that rejects the `action` root wholesale.
- `test/meta/plugin_policy_action_gate_test.go` — compiles every in-tree
  `plugins/*/plugin.yaml` policy under the live gate. This is the analogue of
  `internal/access/setup/setup_test.go`'s
  `TestEveryShippedSeedCompilesUnderTheLiveActionGate` that the finding asked
  for. It reads the shipped yaml (not a fixture) and carries two non-vacuity
  controls.

**(c) Three inaccurate claims corrected.** `internal/access/policy/compiler.go`
and `internal/access/setup/setup.go` both said the gate applies to "every policy
source — in-tree seeds and operator-authored database rows alike", which both
under-counted the sources and implied all of them are caught at reload. Both now
name the third source and say **where** each is caught and why the containment
boundary differs. The same correction was applied to the operator note in
`site/src/content/docs/contributing/explanation/background-job-authorization.md`,
which the review's CR-02 fix explicitly asked for.

### The import cycle — hit, and how it was resolved

The brief asked for this to be reported rather than worked around silently.

`internal/plugin` importing `internal/access/policy` broke the **test** build of
`internal/access/policy`:

```text
package github.com/holomush/holomush/internal/access/policy
	imports github.com/holomush/holomush/internal/plugin/hostcap from seed_smoke_test.go
	imports github.com/holomush/holomush/internal/plugin from capabilities.go
	imports github.com/holomush/holomush/internal/access/policy from policy_installer.go: import cycle not allowed in test
```

There is no cycle in production code — `internal/access/policy` and
`.../attribute` do not depend on `internal/plugin` (verified with `go list
-deps`). The cycle is confined to the **in-package** test binary: Go rejects a
`package policy` test file importing a package that depends on `policy`.

Resolution, using the narrowest seam and an in-directory precedent: the single
hostcap-dependent test — `TestEverySeededCapabilityResourceHasDefaultPermit`
(`// Verifies: INV-PLUGIN-50`) — moved out of `seed_smoke_test.go` into a new
`internal/access/policy/seed_capability_permit_test.go` declared
`package policy_test`. An **external** test package is exempt because it compiles
separately. `seed_profile_smoke_test.go` in the same directory already documents
this exact manoeuvre for the same reason.

The moved test builds its engine via `abactest.NewSeedEngine` — the exported
`NewCompiler → NewCache → Reload → NewEngine` path, which also registers the
`action` namespace — instead of `seed_smoke_test.go`'s unexported
`createSeedEngine`, which compiles on an empty schema. So the moved test now runs
**closer** to production than the helper it left behind. Two non-vacuity controls
were added while moving it (`hostcap.Descriptors` non-empty; at least one
descriptor actually probed).

Alternatives rejected:

- **Injecting the validator into `PolicyInstaller` from the wiring site.** Avoids
  the cycle, but makes the gate optional-by-wiring: any construction path that
  forgot to supply it would silently fail open. The gate belongs inside the
  installer where it cannot be unwired.
- **A parallel `action` validator in `internal/plugin` over `dsl` + `attribute`.**
  This is the "invent a parallel validator" the brief warns against — two
  implementations of one fatal rule, free to diverge.
- **Converting all of `seed_smoke_test.go` to `package policy_test`.** 1372
  lines depending on unexported helpers (`mockAttributeProvider`,
  `createTestEngineWithPolicies`, which itself pokes `cache.mu` / `cache.snapshot`).
  Far more churn than moving the one test that needs the external package.

No source file's package changed; nothing was exported to accommodate the move.

## Finding 3 — the compiler aliases a mutable, unsynchronized `*types.AttributeSchema` (CR-01)

### What was wrong

`types.AttributeSchema.namespaces` was a bare `map[string]*NamespaceSchema` with
no mutex, and `GetNamespace`'s own doc said the type is not goroutine-safe.
Before 02.2, `BuildABACStack` built the compiler on a private
`types.NewAttributeSchema()` nobody else held. After `internal/access/setup/setup.go`
step 11 it holds the **live** object that `Resolver.RegisterProvider` writes into
and `UnregisterProvider` deletes from, reached by plugin load/unload.

**Adjudicated severity, stated as adjudicated:** this is not a live race. All
schema writes happen inside `PluginSubsystem.Prepare`; plugin load is sequential
(no goroutines in `manager.go` / `loader.go`); `Manager.UnloadPlugin` has no
production caller; and `lifecycle.Orchestrator` is a global barrier — no
`Activate` runs until every `Prepare` has returned, while the poller goroutine
launches in `Activate`. Only reader-vs-reader pairs exist today. Neither the code
comments nor this document describe it otherwise.

The problem is that the safety is **incidental** to a boot-phase ordering nothing
pins, and it becomes `fatal error: concurrent map read and map write` — a process
abort, not a race-detector warning CI would catch first — the moment a runtime
hot-reload, a first `UnloadPlugin` caller, or concurrency inside `LoadAll` lands.

### What changed, and why this option

**Chosen: `sync.RWMutex` on `types.AttributeSchema`.** All six accessors
(`Register`, `HasNamespace`, `IsRegistered`, `GetNamespace`, `Replace`, `Remove`)
now lock, and the now-false "NOT goroutine-safe" comment is gone.

Justification against the snapshot alternative:

- The lock fixes the hazard for **every** holder of a populated schema
  (`attribute.SchemaRegistry`, `schema_evolution.go`, the compiler). The snapshot
  fixes it for one holder and leaves the type's own hazard admission standing for
  the rest.
- Completeness is by construction, not by audit: a grep for the map shows
  `s.namespaces` is touched **only** inside `types.go`; every external caller goes
  through the six methods. There is no accessor left to miss.
- The snapshot would have required re-establishing an ordering guarantee that
  `setup.go`'s step-11 comment currently gets for free from the live pointer, and
  the live pointer is deliberate — it is what makes boot and steady state
  validate identically, which is 02.2-04's whole point. Trading that for the
  cheaper fix inverts the phase's goal.

One residual is documented rather than locked: `GetNamespace` returns the
registered `*NamespaceSchema`, not a copy, so mutating its `Attributes` map would
escape the lock. Verified that nothing does — the only in-tree write to an
`Attributes` map is `plugins.ConvertProtoSchema` building a fresh one before
registration, and evolution swaps the whole pointer via `Replace`. The type doc
and `GetNamespace`'s doc both state the contract.

**The guarantee is pinned by a test, not by the comment.**
`internal/access/policy/types/attribute_schema_concurrency_test.go` runs 4 writer
and 4 reader goroutines over one schema for 200 rounds each, asserting a stable
namespace reads back correctly on every iteration while other namespaces churn.
It is written against the **property** (concurrent use is safe), not the
mechanism, so a later swap to a `sync.Map` or copy-on-write keeps it green; what
it forbids is silently dropping the property. The unit lane runs `-race`, so an
unguarded accessor reintroduced later fails there rather than in production.

`setup.go`'s step-11 comment now records that the sharing is safe by construction
and must not be "fixed" into a snapshot.
