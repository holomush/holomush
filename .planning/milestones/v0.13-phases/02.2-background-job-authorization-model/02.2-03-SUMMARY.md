## ⚠ This plan's registration is a NO-OP until plan 02.2-04 lands

Stated plainly so no reader mistakes it for ROADMAP criterion 3 being met.

`BuildABACStack` builds its compiler at `setup.go:163` on `schema` — a `types.NewAttributeSchema()` allocated one line earlier at `:162`, never populated, and never referenced again in the file. The populated `schemaReg` is a *different object* allocated at `:172`. So `validateAttributes`'s `action` hard-error branch (`compiler.go:162-164`) evaluates `HasNamespace("action") == false` and is skipped, exactly as before this plan existed.

Consequences, both directions:

- **The D-59 landmine does not exist.** Registering `action` did not turn `seed.go:332`'s shipped `action.dispatch_location` into a boot error.
- **The D-59 benefit does not exist either.** Registration alone flips nothing. A typo'd `action.*` reference still silently default-denies today.

Plan **02.2-04** (D-66) wires the compiler to `schemaReg` and is what makes this load-bearing. **This plan produced the gate; plan 04 opens it.** That framing is written into the call-site comment in `setup.go` so it cannot be re-litigated from the source alone.

## The final DECLARE set

Five keys, all `types.AttrTypeString`, in `attribute.ActionNamespaceSchema()`:

```text
name                    resolver-owned (resolver.go:185,:273); spec MUST (docs/specs/abac/01-core-types.md:430-435)
dispatch_location       SHIPPED seed.go:332; produced by hostcap/interceptor.go:294
job.trigger_event_id    produced by world/caller.go:171; no seed references it yet
job.trigger_event_type  SHIPPED seed.go:517; produced by world/caller.go:174
job.trigger_subject     SHIPPED seed.go:517; produced by world/caller.go:177
```

Each key carries its dot **literally** — `IsRegistered(ns, key)` is an exact map lookup and `compiler.go:161` composes `ref.namespace + "." + ref.key`, so nesting a `job` sub-namespace would miss the lookup and hard-error at boot. Assumption **A3** is now pinned by a test with a paired negative control (`IsRegistered("action", "job")` must be FALSE).

**Two of the three `job.trigger_*` keys are already SHIPPED, not merely "new this phase."** Plan 01's `seed:job-fixture-instance-scoped` (`seed.go:517`) binds `trigger_event_type` and `trigger_subject`. Omitting either would be a boot failure the moment plan 04 lands — the same class of failure `dispatch_location` represents.

## The operator pre-flight and the accepted upgrade risk (D-67)

The audit's honest limit: operator-authored rows in the `policies` table compile through the same `Compiler` and cannot be enumerated from this repo. The audit ships the pre-flight query verbatim:

```sql
SELECT id, name, dsl_text FROM policies WHERE dsl_text LIKE '%action.%';
```

> **Upgrade risk (knowingly accepted by D-67).** After Phase 02.2 lands, the ABAC policy compiler validates `action.*` attribute references against a declared schema, and an undeclared reference is **fatal for every policy source** — in-tree seeds and operator-authored database rows alike. A deployment carrying an operator-authored policy that references an `action.*` key outside the declared set (`name`, `dispatch_location`, `job.trigger_event_id`, `job.trigger_event_type`, `job.trigger_subject`) **will fail to boot on upgrade**. The remedy is an operator edit to the offending `policies` row; run the pre-flight query **before** upgrading. This was chosen deliberately in preference to a typo'd `action.*` reference silently default-denying, which is the same fail-closed posture the rest of the ABAC stack takes.

**Plan 02.2-05 owns the release-note callout.** This paragraph is the wording to reuse.

## `reservedActionKeys` was NOT widened

`internal/access/policy/types/types.go` is untouched — verified: `git diff --name-only` across this plan's commits does not list it.

Widening it would be a **shipped-behavior regression**, not a hardening. The host's own plugin scope fence supplies `dispatch_location` through `types.NewAccessRequest` at `internal/plugin/pluginauthz/capability.go:50`, so denylisting the key would make every scope-eligible plugin capability call return `ACCESS_REQUEST_RESERVED_ATTRIBUTE`, breaking `seed:plugin-world-mutation-own-location` and INV-PLUGIN-50/52. Declaring a key in the **schema** and reserving it on the **supply side** are opposite operations; the audit (§4) and the `action_schema.go` doc comment both record this so it is not re-discovered the hard way.

## No new boot WARN

`warnOnMissingSeedCoverage` reports a namespace as uncovered when a seed references it but no **provider** owns it, and `action` has no provider by design (D-60 registers it directly, which never touches `Resolver.RegisteredNamespaces()`). That is safe **structurally**: `seedNamespaceRefPattern` is anchored on a `principal.`/`resource.` root, so an `action.` root is not a candidate at all.

Per the plan, that is asserted **directly** rather than trusted: `TestSeedNamespaceRefPatternNeverMatchesAnActionRoot` asserts the regex against three `action.*` references, carries a paired positive control (`resource.location.id` must still match, so the negatives are not vacuous), and then drives the **real** `validateSeedProviderCoverage` with the two shipped action-referencing seed shapes and an empty registered set — the harshest case — confirming `action` never appears in the missing-set.
