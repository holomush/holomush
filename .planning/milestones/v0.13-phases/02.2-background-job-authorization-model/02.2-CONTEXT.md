<domain>
## Phase Boundary

Background jobs — event-driven reactors, flushers, and any future host subsystem that acts on the
world — get a first-class ABAC identity **plus per-execution attributes the policy engine can
test**, so a job's authority is scoped to the work it is currently performing rather than granted
as a blanket capability or borrowed from the human whose command triggered it.

**In scope:** the `job:` principal namespace, its attribute provider and liveness registry, the
per-execution attribute vocabulary and where it is stamped, the `action` schema-namespace
registration, the job deny-code shape, ABAC seeds, and a fixture job proving instance-scoped
denial.

**Out of scope (moved to Phase 02.1, World Caller Model):** everything that makes per-call
attributes *reachable* from a world write — the `world.Service` caller argument, `checkAccess`'s
hardcoded `nil` at `service.go:214`, and the migration of `WithSystemSubject`. The original
success criterion 3 of this phase migrated there wholesale.

**Out of scope (Phase 3):** the retirement reactor and the `last_active_at` flusher themselves.
This phase ships the model and a fixture; Phase 3 brings the first real consumers.

### Job identity

- **D-48:** Background jobs get a **new `job:` principal namespace** (`job:retirement`,
  `job:activity-flush`) with its own attribute provider, schema, and seeds. Reusing `system:` was
  rejected for the reason D-45 was rejected: `parseEntityType`
  (`internal/access/policy/engine.go:542-548`) matches the **prefix only**, so a
  `principal is system` permit written for a job also grants `system:bootstrap`. A disjoint
  namespace makes that impossible at the target clause rather than patching it with a
  `when { principal.id == … }` identity-string guard.
  — **Reversibility:** costly — the namespace appears in seed DSL text, the schema registry, and
  every job ref; renaming it later means a policy migration, not an edit.

- **D-49:** The job provider is gated on a **registry of currently-running jobs**, copying
  `PluginProvider`'s shape (`internal/access/policy/attribute/plugin_provider.go:36-58`): a ref for
  a job that is not running resolves to `nil, nil`, so no attributes are stamped and any
  attribute-conditioned permit fails to match. This ties authority to liveness and is the property
  that makes the provider fail closed. **This is the ABAC fail-safe semantics working as designed**
  — missing attributes are `false` for every operator (ADR `holomush-iv43`) — and it is why the
  provider MUST NOT emit sentinel values for an unresolved job (`.claude/rules/abac-providers.md`).

- **D-50:** The provider stamps **`name` plus a declared capability class** (e.g.
  `{name: "retirement", writes: ["character","session"]}`), not `name` alone. This lets a seed
  express "a job may only touch resource kinds it declared" as a policy condition instead of
  relying on N per-job permits staying in sync. `bags.Subject["id"]` is stamped
  provider-independently regardless (`resolver.go:190-198`) — the provider adds on top of it.

- **D-51:** The capability class is declared **in Go, at registration** — the job registers itself
  with its declared writes. Jobs are host subsystems compiled into the binary, so a
  compile-time-adjacent declaration matches where they live. It is self-attested, and that is
  acceptable because **the declaration narrows; the seed grants** — both gates must pass.
  A manifest-style YAML was rejected: jobs are not loadable units, so there is no discovery step to
  hang parsing off, and it would add a file format for two in-tree consumers.

- **D-52:** This phase ships a **fixture job only**; Phase 3 brings the real consumers. 02.2 stays a
  substrate phase with no world-behavior change, and criterion 2's DENY test runs against the
  fixture. Migrating `internal/grpc/location_follow.go:197` was rejected here — it is a synchronous
  gRPC follow, not a background job, and shaping the model around it would distort it. (That
  migration lands in Phase 02.1 as its criterion 4.)

### Attribute vocabulary and threat model

- **D-53:** The model's honest claim is **scope drift + handler bugs**, and it explicitly does
  **NOT** defend against malicious in-process code — nothing inside the process can stop Go from
  calling `Evaluate` with arbitrary arguments. Two testable claims:
  (a) a job that grows a new write path is DENIED until someone deliberately widens its seed, which
  makes **the seed the code-review surface**; (b) a handler that derives the wrong aggregate is
  DENIED rather than corrupting it. Specs and the invariant registry MUST NOT claim more. This
  repo has a documented failure mode of registry summaries claiming more than their bindings prove
  (INV-WORLD-6).

- **D-54:** The per-execution vocabulary is the **event provenance triple** —
  `trigger_event_id`, `trigger_event_type`, `trigger_subject` — taken verbatim from the delivered
  event. A seed can then bind **both** what caused the write and what it may touch:
  `when { action.job.trigger_event_type == "character_retired" && action.job.trigger_subject == resource.id }`.
  The event-type half is what stops a job subscribed to a broad filter from acquiring broader
  authority than intended. JetStream delivery metadata (sequence, redelivery count) was rejected —
  no in-tree consumer needs it and it would couple the ABAC vocabulary to the transport.

- **D-55:** Attributes are stamped **at the consumer boundary, before handler logic runs**, from
  the delivered message, and the handler cannot alter them. This is what keeps the check from being
  tautological: the resource is whatever the handler independently derives, so a wrong derivation is
  caught. Had the handler supplied both sides, criterion 2's denial test would only prove that a
  deliberately-wrong fixture is denied. The natural stamp site is the neutral-package consumer
  wrapper that Phase 3's D-46 relocation produces.

- **D-57:** Job-supplied action keys are **namespaced under `job.`** — `action.job.trigger_event_id`
  — mirroring the `resource.<ns>.<attr>` convention in all 16 shipped seeds. `resolveAttrRef` joins
  the dotted path (`evaluator.go:401-413`), so the bag key is `"job.trigger_event_id"`. This
  permanently avoids collision with resolver-owned action keys — the collision that made `name`
  reserved in the first place (`resolver.go:185` writes `bags.Action["name"]`).

### Plumbing — split into Phase 02.1

- **D-56 (2026-08-07, maintainer decision — creates Phase 02.1 and renumbers this phase):** the
  per-call-attribute carrier is **not this phase's to build**. `world.Service` takes
  `subjectID string` and reconstructs an `AccessRequest` with `Attributes` hardcoded `nil`
  (`service.go:214`), so the world API is **lossy relative to what the authorization layer has been
  able to express since Phase 3b**. That is a pre-existing modeling defect in the caller argument;
  jobs are merely the first caller that exposes it.

  **A variadic option was considered and rejected as a code smell** — an execution context that
  every call semantically has should not be optional, and bolting one on would preserve the defect
  while hiding it. The fix is to correct the argument: **typed constructors**
  (`world.HumanCaller`, `world.JobCaller`, `world.SystemCaller`) rather than a bare struct, so
  invalid combinations (a human carrying job provenance, a job with no provenance) are
  unrepresentable and the `job.` keys are produced in exactly one place.

  Packaging follows the same reasoning that created this phase out of Phase 3 (D-47): **do not bury
  a platform fix inside the phase that surfaced it.** It became **Phase 02.1 — World Caller Model**,
  and this phase was renumbered 02.1 → 02.2 so execution order matches numeric order. The
  alternative — keeping this phase at 02.1 and numbering the caller model 02.2 — was rejected
  despite costing a rename, because the numeric/execution mismatch would persist in every future
  reference.
  — **Reversibility:** one-way — undoing the split means re-merging two roadmap phases and
  re-renumbering artifacts that already cite 02.2; undoing the caller-model refactor itself means
  reverting a ~400-call-site signature change across 3 interfaces and their generated mocks.

  **Verified blast radius of the split-out work (grep-confirmed 2026-08-07 — do NOT re-estimate):**
  21 public `Service` methods, 47 production call sites across 12 files, **347 test call sites**
  across 13 files, and 3+ interfaces redeclaring the signatures (`world/mutator.go` 11 methods,
  `command/types.go` 9+, `grpc/server.go` 2) plus mockery regeneration. My initial estimate of
  "~19 caller files" was materially low and was corrected before the decision was made.

- **D-58:** The job deny signal composes **both dimensions** — `JOB_CHARACTER_ACCESS_DENIED` — so
  alerting can distinguish a job denied on a character from one denied on a location without
  parsing log attributes. **Consequence to honor:** `entityPrefix` is derived from the **resource**
  kind today (`service.go:209-213`), so emitting a job-aware code requires the classification to
  consult the **principal** kind as well. The metrics split must be preserved: denials MUST NOT
  land in the `holomush_engine_failures_total` counter, which counts evaluation failures.

### Schema for `action.*`

- **D-59:** The **`action` namespace IS registered** in the schema registry, declaring the job
  provenance triple **plus every key already in use** — the already-shipped `dispatch_location`
  (`seed.go:332`) and the resolver-owned `name`.

  **This is load-bearing, not documentation.** `validateAttributes`
  (`internal/access/policy/compiler.go:149-170`) skips unregistered namespaces, warns on an
  undeclared key in a registered namespace, but **hard-errors for `action` specifically**:
  `"unregistered action attribute %q: action namespace is registered but attribute is not"`.
  Registering `action` therefore flips every `action.*` reference repo-wide from unchecked to
  fail-at-compile.

  **Landmine:** `seed.go:332` ships `action.dispatch_location` today with no `action` namespace
  registered. Registering `action` **without declaring that key in the same change turns a shipped
  seed into a boot-time compile error.** A repo-wide `action.*` audit MUST precede the flip, not
  chase it.
  — **Reversibility:** costly — unregistering later is easy, but any policy authored against the
  strict mode may reference keys that only validate while it is on.

  > **⚠ AMENDED 2026-08-09 by D-66 — read D-66 before acting on this entry.** Research finding F1
  > established that `validateAttributes` **cannot fire in production at all**, because every
  > production compilation path builds its `Compiler` on a fresh, never-populated
  > `types.AttributeSchema` that is a *different object* from the `attribute.SchemaRegistry`
  > providers register into. Two halves of D-59 are therefore false **as mechanism**: the described
  > landmine does not exist, and neither does the described benefit — registration alone flips
  > nothing. **D-59's INTENT stands and is now delivered by D-66 + D-67.** The `action.*` audit
  > requirement is unchanged and becomes *more* load-bearing, not less.

- **D-60:** The schema is registered by a **direct `attribute.Register(schemaReg, "action", …)`
  call in setup**, alongside the 9 provider registrations (`internal/access/setup/setup.go:150-321`)
  — not via a synthetic provider. `action` is a caller-supplied bag, not an entity that gets
  resolved, so a provider whose `ResolveSubject`/`ResolveResource` return `nil, nil` purely to carry
  `Schema()` would misrepresent what it is.

### Post-research decisions (maintainer-decided 2026-08-09, after `02.2-RESEARCH.md`)

These three resolve the open questions the research escalated. They are **locked** — a planner
implements them, it does not re-open them.

- **D-66:** The **compiler-to-schema-registry wiring fix is IN SCOPE for this phase**, as a
  **first-class, separately-committed task**, gated behind the complete `action.*` audit.

  Research finding F1: three production sites build a `Compiler` on a freshly-allocated,
  never-populated `types.AttributeSchema` rather than the `attribute.SchemaRegistry` the providers
  populate — `internal/access/setup/setup.go:150-151`,
  `internal/bootstrap/setup/subsystem.go:192-193`,
  `internal/testsupport/integrationtest/real_abac.go:49` (the research said `:48`; re-read
  2026-08-09, the `policy.NewCompiler(policytypes.NewAttributeSchema())` call is on `:49`).
  A **fourth** compilation site — `internal/testsupport/abactest/abactest.go:78` — was found during
  plan review; it is not an orphan (its registry is real) but it never carries `action`, so it is a
  coverage gap the F1 framing missed. Until they are wired, `validateAttributes`
  and its `action` hard-error branch are dead code, D-60's registration is a **complete no-op**, and
  **success criterion 3 is unachievable**. Wiring them converts a dead validation path into a live
  boot-time gate for the whole repo.

  **Sequencing trap (do not reorder casually):** `cache.Reload` runs at `setup.go:156`, **before**
  provider registration at `:163-321`. Wiring without moving the reload leaves the compiler
  validating against a still-empty schema at boot. `setup.go:378-388` wires invalidation *after* the
  reload, which suggests the move is safe — research assumption **A4** flags this as not
  exhaustively traced. Trace it during planning.
  — **Reversibility:** one-way in practice. Any policy authored while strict validation is live may
  reference keys that only validate in that mode.

- **D-67:** The `action` hard-error branch is **fatal for ALL policy sources** — in-tree seeds and
  operator-authored DB rows alike. The considered-and-rejected alternative was fatal-for-
  `PolicySourceSeed`-only with a WARN for DB rows.

  This **knowingly accepts research assumption A1** ("no production deployment currently has an
  operator-authored DB policy referencing `action.*`"), which is unknowable from the tree and is the
  highest-severity assumption in the research document. If A1 is wrong, that deployment **fails to
  boot on upgrade**, and the remedy is an operator DB edit. The rationale is that a typo'd
  `action.*` reference must never silently default-deny *anywhere*, which is the same fail-closed
  posture the rest of the ABAC stack takes.

  **Obligations this creates for the plan:** the `action.*` audit MUST be exhaustive over everything
  reachable from the tree, the boot failure MUST name the offending policy and key precisely enough
  for an operator to fix it without reading Go source, and the upgrade risk MUST be called out in
  the phase SUMMARY (and release notes) rather than discovered in production.

- **D-68:** Success criterion 4's universality reading is **option A + option D** from the research
  decision table (`02.2-RESEARCH.md` §Q3):

  - **Every** background consumer gets a `job:` identity and a **declared capability class** —
    `principal.job.name` and `principal.job.writes` via the liveness-gated registry and provider.
  - **Only event-driven** consumers get **per-execution instance scoping** (the D-54 provenance
    triple bound against `resource.id`).
  - A timer-driven job's authority is therefore **necessarily coarse**, and the documentation MUST
    say so plainly rather than implying it is instance-scoped.

  Rejected: option B (`trigger_kind` discriminator with `tick_id`/`window_*`) — the window
  authorizes nothing a flusher's real authority ("every character with a buffered key") is narrowed
  by, so it *looks* like instance scoping without being it, which is exactly the invented shape D-53
  forbids. Rejected: option C (synthetic tick provenance with an empty or sentinel
  `trigger_subject`) — an empty-string sentinel is fail-**open** under
  `.claude/rules/abac-providers.md`, since it matches any other unresolved peer.

  **Consequences:** ROADMAP criterion 4 must be amended to this reading via the sanctioned
  `gsd-tools phase edit` path (never a hand-edit — rule `a32nfcekfc`). Phase 3's `last_active_at`
  flusher crosses **no ABAC chokepoint** (it writes at the INV-WORLD-4 out-of-world writer
  boundary), so under D-68 it takes an identity but no per-execution attributes; `03-05-PLAN.md:100`
  reserved exactly this decision and now has its answer.

## Open Questions — MUST NOT be invented by a planner

1. **Timer-driven jobs have no triggering event.** Phase 3's `last_active_at` flusher (03-05) is
   periodic, so the D-54 provenance triple has nothing to carry. Criterion 4 claims this model is
   "the path every future background consumer takes" — that claim is currently false for an entire
   class of job. Resolve before the model is documented as universal. Candidate shapes: a distinct
   `trigger_kind` (`event` vs `schedule`) with a separate attribute set per kind; or a scheduled job
   presenting its tick/window as provenance. **Do not let a planner pick one silently.**

   > **✅ RESOLVED 2026-08-09 by D-68** — option **A + D**: identity and declared capability class
   > for every background consumer, per-execution instance scoping for event-driven ones only.
   > `trigger_kind` (option B) and synthetic tick provenance (option C) were both considered and
   > **rejected**; see D-68 for the grounds. Criterion 4 is amended to this reading.

2. **`SystemCaller()` vs the S1 defense** (belongs to Phase 02.1 but blocks this phase's mental
   model). `engine.go:92-101` requires **both** `req.Subject == "system"` (the bare literal) **and**
   `access.IsSystemContext(ctx)`; a bare `"system"` subject **without** the context marker is a hard
   `SYSTEM_SUBJECT_REJECTED` error. So a caller *value* must influence the *context* — the
   mechanism for that is unverified.

   > **✅ RESOLVED 2026-08-16 in Phase 02.1, which owns it.** The mechanism is
   > `checkAccess` deriving the context from the caller: `service.go:234` calls
   > `s.engine.Evaluate(caller.evalContext(ctx), req)`. Adjudicated in
   > `02.1-VERIFICATION.md` rows **R4**, **P1**, **P3**; behavioural proof
   > `TestWorldServiceSystemCallerSatisfiesTheS1GateWithoutAmbientContext`. This
   > phase's mental model is therefore unblocked.

3. **The repo-wide `action.*` audit** (D-59). Confirmed today: `seed.go:332` (`dispatch_location`)
   and the resolver-owned `name`. The audit must also cover operator-authored policies in the
   database, not only in-tree seed text — those compile through the same path and would fail the
   same way.

   > **✅ PARTIALLY RESOLVED 2026-08-09.** `02.2-RESEARCH.md` §Q2 delivers the complete in-tree
   > audit table (5 keys must declare, 2 test-only must not; plugin manifests and migrations swept
   > to zero). The operator-authored-DB half is **unknowable from the tree** and stands as research

## Existing Code Insights

### Reusable Assets
- **`PluginProvider`** (`attribute/plugin_provider.go:36-58`) — a complete, 15-line, non-character
  principal provider gated on a registry. The job provider is this shape with a job registry
  substituted. Its `nil, nil` return for an unknown ref is the fail-closed behavior to copy.
- **Cross-bag `when` comparison** — 16+ shipped seeds already do `resource.X == principal.Y`, so
  D-54's `action.job.trigger_subject == resource.id` is idiomatic, not novel.
- **`types.NewAccessRequest`'s 4th parameter** — the per-call attribute channel exists, validates,
  and deep-clones. Nothing new is needed at the request layer.

### Established Patterns
- **Attribute keys are namespaced by dotted path** (`resource.character.id` → bag key
  `"character.id"`), which is why D-57's `action.job.*` is consistent rather than novel.
- **Schema registration flows from providers** (`Namespace()` + `Schema()`), which is exactly why
  `action` needs the D-60 direct-`Register` exception — it has no entity to resolve.
- **Only 2 `principal is system` permits exist** (location, exit). ABAC is default-deny, so a job
  writing a character is denied today absent a new seed — the gap is real, not a formality.

### Integration Points
- **`internal/access/setup/setup.go:150-321`** — where the job provider registers and where the
  `action` schema registration lands.
- **`internal/access/policy/seed.go`** — where the job seeds land; touching it fires the
  `abac-reviewer` gate before push.
- **The Phase 3 D-46 neutral-package consumer wrapper** — the D-55 stamp site.
- **`internal/world/service.go:214`** — the consumer of what Phase 02.1 delivers; this phase does
  not touch it.

- The maintainer's framing on the plumbing question, verbatim in substance: *a variadic feels like
  a code smell — it seems like we built the args wrong and we need to fix it correctly for

  ~400-site refactor was accepted rather than avoided. A future reviewer tempted to "simplify"
  Phase 02.1 back into a variadic or a context-carried value should read D-56 first.
- Seed permits stay **as narrow as the DSL allows**; a blanket `action in ["read","write"]` over
  every character resource is the ceiling, not the target (carried forward from D-45's surviving
  guidance).
