# Milestone Audit — v0.13 "Web Portal: Identity & Admin Foundations"

**Status: `tech_debt`** — no blockers. Every requirement is satisfied and every
cross-phase seam holds, but the bookkeeping that is supposed to *record* that has
drifted far enough to be misleading on its own.

Audited at `c2e781c07` (post-merge of PR #4984 and #4988).

## 1. Requirements coverage — 52/52, zero unsatisfied

The 3-source cross-reference (traceability table x SUMMARY frontmatter x phase
VERIFICATION) produced **no unsatisfied and no orphaned requirements**, so the
§5e FAIL gate does not fire.

Nine requirements appear in the traceability table but in **no** SUMMARY
`requirements-completed` frontmatter. Each was checked individually against its
phase's VERIFICATION.md and each is adjudicated there:

| Requirement | Phase | Evidence found |
|---|---|---|
| AUTHZ-01 | 02.1 | Dedicated section: "AUTHZ-01 closure — is it earned?" |
| EXT-05 | 05 | Requirements table row: `EXT-05 \| 05-05 \| ✓ SATISFIED` |
| IDENT-04 | 03 | Verifier explicitly ruled on whether it is legitimately `Complete` at Phase 3 |
| IDENT-10 | 03 | Ginkgo-focused spec passed (`-ginkgo.focus=IDENT-10`, exit 0) |
| IDENT-06..09 | 02 | `status: discharged` in the phase's `requirements:` block |
| IDENT-03 | — | **Out of scope**: deferred out of v0.13 to backlog 999.20 on 2026-08-06, dated and recorded in both the traceability table and the phase row |

So the coverage is real. What is *not* real is the recorded state — see §4.

## 2. Phase verification — 10/10 passed

Every phase carries a VERIFICATION.md with `status: passed`. Phase 06.1 reached
`passed` on re-verification round 3 (+ a round-4 delta closing G-06.1-7); its
`gaps_remaining`, `gaps_new`, and `regressions` are all empty.

## 3. Cross-phase integration — all load-bearing seams hold

Verified sound: Phase 2 ABAC vocabulary → 6/6.1 (`admin_section:` defined once,
seeded type-scoped, consumed at both interceptor branches, no term
defined-unconsumed or consumed-undefined); Phase 4 `CharacterAccessService` → 5
(all four profile RPCs called); Phase 4 → 6 (divergence is designed and
documented, not accidental duplication); Phase 02.1 World Caller (honored on both
surfaces, no bypass); Phase 3 → 5 (reachable). Both end-to-end flows complete:
create → public profile → viewer tier, and admin sign-in → gate → edit → audit.

Three **non-blocking** warnings, all orphan-or-drift rather than breakage:

**3.1 `AdminGetSection` is exported and gated but never consumed.** The core RPC,
its web proxy, and the interceptor's *only* caller-supplied-`section_id` branch
all exist (`internal/grpc/admin_interceptor.go:232`), but no UI calls it — the
`[section]` route resolves its entry from the layout's `listAdminSections`
payload instead. The security consequence is the interesting part: the one gate
branch whose section id is **attacker-controlled** has no production traffic
path, so its refusal semantics are exercised only by tests.

*(Verified independently with a positive control: `webAdminGetSection` appears
only in the generated `web_pb.ts` bindings, while `webAdminListCharacters`
appears in both the bindings and `web/src/lib/admin/client.ts` — proving the
search can find a real caller and that this one has none.)*

**3.2 A deferral note names a job identity that does not exist.**
`internal/access/policy/seed.go:488` defers grants for "the REAL consumers —
`job:retirement`, `job:activity-flush`". Phase 3 shipped the retirement grant
(`retirement/reactor.go:30` `JobName = "retirement"`), but the activity job
registers as **`character_activity`** (`charactivity/subsystem.go:84`), not
`activity-flush`. A future author writing the deferred policy against the note's
name would produce a permit that silently never matches — a missing
`principal.job.name` evaluates to `false` per ADR holomush-iv43, so it would
fail closed and quietly. Latent today, because the flusher writes via raw SQL
with no `world.Caller` and no `Evaluate` call, self-documented as intentional.

**3.3 `world.ScheduledJobCaller` has zero production callers**
(`internal/world/caller.go:201`). Timer-driven job authorization is built but
unreached.

All three are static-wiring claims from a read-only pass; no runtime behavior was
executed.

## 4. The real finding — bookkeeping has drifted from reality

This is why the audit is `tech_debt` rather than `passed`.

**The traceability Status column reads `Pending` for 42 of 52 requirements** whose
phases are complete and verified. Anyone reading `REQUIREMENTS.md` alone would
conclude v0.13 delivered roughly a fifth of its scope. The evidence says it
delivered all of it.

**Only 2 of 10 phases carry a machine-readable `requirements:` block**, and the one
that does most thoroughly (phase 02) uses a status vocabulary — `discharged`,
`partial_by_decision`, `discharged_to_phase_ceiling` — that the audit matrix has
no mapping for. That vocabulary is more expressive than `satisfied/partial/
unsatisfied` and arguably better, but as long as the two disagree, this
cross-reference cannot be run mechanically and has to be done by hand each time.

**The `deferred-items.md` files do not conform to the shape GSD parses.**

> **This section is a RETRACTION.** Two earlier drafts of this audit asserted
> that `audit-uat` had two defects — scanning archived milestones, and counting
> markdown table rows as items. **Both claims were false.** Each behavior is
> deliberate, documented in the source, and was added to fix the *opposite* bug.
> The non-conforming artifacts are ours. Recorded rather than quietly deleted,
> because the reasoning error is the reusable part.

**Archived-milestone scanning is by design.** `uat.cjs:70-73`: "Active dirs are
milestone-filtered; archived dirs deliberately are NOT … applying it to them
discards every one and silently reinstates the bug." Rationale at `:57-59`:
"Outstanding UAT items do not stop mattering when a milestone closes: a deferred
human-UAT scenario or a `skipped` live-stack test is exactly what gets archived
still-open." So the 12 archived items are the tool refusing to let past-milestone
open work vanish — correct behavior, not leakage.

**Table-row counting is a deliberate fail-safe (#2766).** From
`parseDeferredTableItems`: executors write this file by hand "with no mandated
shape, and a GFM table is a natural choice for the common 'test → failing seeds'
case, **which produced ZERO items**." The docstring names the tradeoff outright —
"Deliberately permissive … That is the correct fail-safe direction for a
false-NEGATIVE bug … surface a questionable entry rather than silently drop a
real one."

**Closing an item in place is fully supported.** The parser accepts exactly two
closure forms:

| Entry form | Closure marker |
| --- | --- |
| bullet entry under a `## Deferred Items` (level-2) heading | `status: resolved` (case-insensitive) |
| GFM table row | any cell reading exactly `resolved` / `done` / `pass` |

Phase 05's file writes `**Status:** closed.` — `closed` is in neither vocabulary,
and the file has no `## Deferred Items` heading, so the whole file becomes the
section body and only its table rows yield items. Six rows, six items. The parser
is doing exactly what it documents.

**Real remediation:** bring the `deferred-items.md` files into the parseable
shape — add a closure cell to the table rows of genuinely-closed items, or
restructure to `## Deferred Items` entries with `status: resolved`. That
legitimately clears the ledger. **No tool change is warranted, and no issue
should be filed against `audit-uat`.**

The `status:` field is honored wherever it appears in the sanctioned shape —
reconciling G-06.1-2 from `failed` to `resolved` dropped the totals from 23/8 to
22/7 immediately, which is the mechanism working exactly as intended.

**Method lesson.** `.claude/rules/references/planning-artifacts.md` prescribes the
check that would have prevented this: before blaming the tool, (1) `git log -S`
the triggering structure — did we author this shape? (2) does the tool actually
generate it — check its templates and its writer? (3) is there a sanctioned
alternative we declined? All three answers were available in
`gsd-core/bin/lib/uat.cjs` and pointed at us. The audit skipped straight to a
defect claim, and the corroborating "evidence" (a closure line the parser
ignored) was really evidence of our own non-conformance.

WINDOWS.md leaks the same way: 3 of its 25 open entries are phase 09. In-scope
open count is 22.

Both are tooling/data defects worth diagnosing before the ledgers are archived
with the milestone, since archiving bakes another milestone's entries into
v0.13's record.

## 5. Nyquist coverage — incomplete, but zero failures

|---|---|---|

| NOT-VALIDATED | 01.1, 02.1, 02.2, 03, 04, 06 | `status: draft` — seeded by plan-phase, never reconciled |
| MISSING | 01, 06.1 | no VALIDATION.md |
| PARTIAL | *(none)* | no phase is `validated` + `nyquist_compliant: false` |

Per the workflow's own #2117 note, `draft` means the file was never reconciled by
validate-phase, so its `nyquist_compliant: false` is **not authoritative**. These
are coverage TODOs, not compliance failures. Running `/gsd-validate-phase <N>`
promotes each to a real verdict.

## 6. Recommendation

The milestone is deliverable-complete and safe to close. The debt above is
recording debt, not product debt — with one caveat worth deciding on explicitly:
the ledger scope leakage (§4) means archiving now bakes another milestone's
entries into v0.13's archive.

Suggested order before `/gsd-complete-milestone v0.13`:

1. Diagnose why WINDOWS.md and `audit-uat` include phases 07/08/09 — this is the
   only item that gets *worse* by archiving.
2. Refresh the traceability Status column (42 rows), so the archived
   REQUIREMENTS.md reflects what shipped.
3. Optionally run `/gsd-validate-phase` on the 8 phases lacking an authoritative
   Nyquist verdict.

The three integration warnings are worth GitHub issues rather than blocking work
— §3.2 in particular, because a wrong job name in a deferral note is a trap that
fails closed and silently for whoever picks it up.

## Method note

Two intermediate results in this audit were **artifacts, not findings**, and are
recorded here so the numbers above can be trusted: an initial orphan scan
reported 52 orphans (an extractor that silently returned zero, so every
requirement looked unclaimed), and a second reported 11 phantom requirements (a
`[A-Z]+-[0-9]+` regex matching invariant ids like `INV-ACCESS-13` and the
encoding `UTF-8`). Both were caught by requiring each search to first return a
hit on a known-present case before its absence was believed.
