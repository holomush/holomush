**D-30's sequencing constraint, and how it is discharged without a wave reorder.**
D-30 requires that the gate MUST NOT adjudicate against a partially populated
skeleton column — a live gate reading a `NULL` skeleton admits a new confusable of an
existing row — and asks that the wave ordering reflect that, not just the migration
ordering. The gate goes live in `02-06` (wave 4); this plan's backfill is `000055`
(wave 5), so on the face of it the gate precedes the backfill.

It is discharged by a **stronger mechanism than reordering**: plan `02-01`'s
`SkeletonLookup` returns an `unverifiable` flag set whenever any `characters` row has
`name_skeleton IS NULL`, and both `Gate.Check` and `02-06`'s in-transaction
`guardSkeleton` **fail closed** with `NAME_SKELETON_UNVERIFIABLE` when it is true.
The gate therefore never returns a false "no collision" against a half-populated
column — it refuses instead. Three reasons this is the right discharge rather than a
wave shuffle:

1. **It covers cases a reorder cannot.** The wave gap is a repo-state artifact; the
   durable hazard is an interrupted post-Unicode-upgrade recompute, which D-23's
   per-row version column exists precisely to make visible. A reorder closes the
   first and nothing about the second.
2. **A reorder would cost more than it buys.** `000055` calls
   `worldpostgres.BackfillCharacterIdentity`, which `02-06` Task 2 creates, so moving
   it earlier means splitting `02-06` into three plans and inserting two waves — into
   a wave graph the cross-AI review verified at zero collisions — and creating a
   window where `Create` takes a token nothing mints at a production root.
3. **In deployment the gap does not exist.** D-21 ships `000054`, `000055` and
   `000056` in ONE release, and migrations complete before `orch.StartAll`
   (`cmd/holomush/core.go:279-282`, `:857`), so the gate is never live against an
   unbackfilled column in production. If `000055` halts on a collision (D-22),
   startup aborts and the gate never comes up at all.

**State and enforce the write-exclusion precondition between B and C.** Goose's
advisory lock serializes *migrators*, not application writers, so nothing in the
framework prevents an old binary inserting a NULL `normalized_name` after the

contains null values", the index creation fails with a duplicate-key error — so the
risk is a repeatedly-failing rollout, not silent corruption. Record that
distinction; it is what makes a stated precondition sufficient rather than requiring
a redesign.

single `core` service with no `replicas:` key, and migrations complete before
`orch.StartAll`, so the migrating process never serves during its own migration —
the window is empty by construction in the default topology. It is NOT empty for
`compose.cluster.yaml` or any multi-replica posture, which is exactly the posture
D-16 assumes elsewhere in this phase.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| concurrent create requests → `characters.name` | Two requests race for one in-world identity; the window between the existence check and the insert is the vulnerability. |
| operator → duplicate resolution | A human decides which of two colliding characters keeps its name, and supplies the replacement. |
| migration runner → production schema | A DDL step whose precondition is another step having run. |
| operator → a server that will not start | The resolution command must work in exactly the state that makes the server refuse to boot. |
