<objective>
Land IDENT-07: an operator-configurable block/disallow list of regular expressions,
evaluated server-side against the normalized character name at the one gate every
admission routes through.

Purpose: the list is DB-backed configuration with no in-process writer (v0.13 ships
no editing surface per §8.12, so edits are direct SQL) in a multi-replica
deployment. That combination is already solved in-tree by `policy.Cache` +
`policy.Poller` — an immutable compiled snapshot behind a read barrier, refreshed
by polling a cheap version indicator. This plan mirrors that rather than inventing
invalidation, because in-process invalidation would only fix the replica that
served the write.
Output: `internal/charname/blocklist` with a compiled snapshot, a poller, boot
validation, and its wiring into the gate.

**Research blocker incorporated (RESEARCH § Concerns 3 / P-5).** D-16 specifies
polling `holomush_system_info.updated_at` for the key. That indicator does not work
as assumed: the column is bumped only by `SetSystemInfo`'s `ON CONFLICT` clause,
migrations forbid triggers, and D-16 itself states the only v0.13 edit path is
direct SQL — so a plain `UPDATE holomush_system_info SET value = …` leaves
`updated_at` unchanged and the poller never notices. The **decision** (mirror Cache
+ Poller) is right; the **indicator** is corrected here to the pair
`(updated_at, hash(value))`, which is the shape closest to the pattern being
mirrored: `policy.VersionQuerier` already returns two signals
(`LatestPolicyVersion` returns a timestamp **and** a count) for exactly this
reason — a deletion may not move `MAX(updated_at)`.

**Assumption-delta checkpoint answered.** The delta detector fired on
`configurable`: the name policy moves from compile-time `regexp.MustCompile`
allowlists — the repo-wide shape today, with no configurable regex list anywhere in
the tree — to an operator-editable settings key. **Has a configuration decision
become a modeling decision? No.** The block list stays a config value: it has no
lifecycle of its own — no version history, no audit trail, no editor, no "who may
edit" model beyond database access. What IS promoted is the **compiled snapshot**:
`blocklist.Snapshot` becomes the primary representation the gate consumes, and the
raw `[]string` is demoted to a storage detail of one variant (the settings row).
The one consequence worth writing down is non-retroactivity: a name admitted under
an older list is never re-validated, so the list governs admissions and not the
existing corpus. That is a stated property, recorded in the package doc comment,
and an explicit truth above — not an oversight to be discovered later.

**Note on ReDoS.** Go's `regexp` is RE2 — linear time, no backtracking — so
operator-supplied patterns carry no ReDoS risk. The residual risk is a *wrong*
(over-broad) pattern, not a slow one. Do NOT add timeouts, complexity analysis, or
any other backtracking-defense machinery.

**Three cross-AI review blockers incorporated (02-REVIEWS.md, all confirmed).**

1. **`StringSliceN` fails open on malformed JSON.**
   `internal/settings/game.go:120-128` returns `(nil, false)` both when the key is
   absent *and* when `json.Unmarshal` fails — the parse error goes to
   `DebugContext` and the caller sees one indistinguishable `false`. A loader that
   reads `false` as "absent ⇒ empty list" therefore silently disables the entire
   block list the moment an operator's direct-SQL edit produces malformed JSON —
   and direct SQL is the *only* edit path v0.13 has (D-16). That is the exact
   opposite of D-15's "hard startup failure naming the offending entry". Task 2
   replaces `StringSliceN` with a strict loader over the raw value.
2. **`BootstrapSubsystem` cannot own a poll loop.** Its `Activate` and `Stop` are
   explicit no-ops with the comment "bootstrap's work is a one-shot Prepare-time
   seed" (`internal/bootstrap/setup/subsystem.go:238-243`). A long-running loop
   placed there either never starts or never stops. Task 2 gives the poller its own
   lifecycle subsystem.
3. **A snapshot accessor is not a `Match`.** The earlier draft handed the gate "the
   cache's snapshot accessor". A value captured once at construction means every
   later reload is invisible to the already-built gate, and a bare accessor func
   does not satisfy the interface anyway. Task 1 makes `Cache` itself implement
   `Match`, and Task 2 adds the reload-visible-to-an-existing-Gate assertion.

**Composition-root scope.** This plan ships the package, its lifecycle subsystem,
its registration in `cmd/holomush/core.go`, and — added in the cycle-2 fix pass —
the **transport** that carries the compiled matcher from the subsystem to the two
config structs plan `02-06` builds the gate from, plus the `Bootstrap → BlockList`
dependency edge. It does **not** wire the matcher into the production character and
guest create paths: plan `02-06` owns `internal/bootstrap/setup/adapters.go` and the
gate construction at all three roots as this phase's single composition owner.

The split is deliberate and is the fix for cross-AI review C2-2/C2-3: `02-06` does
not own `cmd/holomush/core.go`, where this subsystem is constructed, so a plan that
only *named* the roots left the `*Cache` with no path to reach them. This plan
declares the seam (a `Matcher()` provider, a `*blocklist.Subsystem` field on
`grpcSubsystemConfig` and on `BootstrapSubsystemConfig`, both populated in
`core.go`) and `02-06` consumes it. Both files are shared across waves 3 and 4 in
strict order, which is the sanctioned shape for a producer/consumer pair.

This plan's integration proof therefore drives `charname.Gate` constructed directly
over the cache; `02-06` carries the end-to-end create-path criterion.
