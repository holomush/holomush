Land EXT-07: the core-side admin section registry with its mandatory authorization
descriptor, the shared gate helper that evaluates ABAC before it consults the
registry, and the invariant that pins the resulting refusal as indistinguishable
across registered and unregistered section ids.

Phase 2 ships no RPCs, so §10.2's mandated non-vacuous denial test runs here at the
**shared authorization helper** level — seven assertions, one per registered
section — with the endpoint-level form landing in Phase 4 once the RPCs exist
(D-08). The phase that builds the gate proves the gate.

Purpose: the sketch round found a registry-enumeration oracle between §10.3 and
§10.4. §10.3 requires a planned-section refusal to reveal nothing about which
sections exist, but §10.4 defines two distinguishable denial codes. D-06 closes it
by ordering: **gate first, then distinguish.** That works because
`seed:admin-section-access` is scoped by resource **type**, so an unregistered id
is still covered by the policy and the gate can decide before the registry is ever
consulted. It is the same ordering §10.3 already mandates for `NOT_IMPLEMENTED`,
applied one field over.

**Settle the validation API here — the earlier plan alternated between a
`Registry.Validate()` method and a package-level `Validate()`, defined no `Registry`
type, and therefore gave the malformed-registry tests no injection surface (review
finding, confirmed).** There is **no `Registry` type**. `Validate()` is exactly
`validateEntries(all)`; every rule lives in `validateEntries`, which takes a slice,
so a test can hand it a deliberately malformed set without mutating package state or
inventing a constructor. Say that in the package doc comment, because "add a
`Registry` type for testability" is the obvious-looking refactor and it buys nothing
here.

**The descriptor is a required field of the entry, not a lookup in a parallel table
that can be missing a key.** There is no default and no "if unset, use admin". A
zero-valued descriptor, an empty action, or an empty resource is **rejected**, never
read as permissive — the same fail-open shape §8.6's totality rule forbids for
visibility floors and §4.3 forbids for lifecycle reads. Carry that reasoning in
`Validate`'s doc comment.

**`Status` is closed too, and it gets the same treatment (cross-AI review C2-15,
confirmed).** §10.1's vocabulary is exactly two values — verified against
`01-SPEC.md:2107-2117`, seven ids, one `available` and six `planned`. Add two things
so an unrecognized value cannot be served as available:

1. **A boot rule in `validateEntries`.** Reject any entry whose `Status` is neither
   `StatusAvailable` nor `StatusPlanned`, naming the offending entry AND the
   offending value — a `Status` is a bare string type, so `Status("")` and
   `Status("availabe")` both compile, and neither is caught by any descriptor rule.
2. **An exhaustive classifier with a denying default.** Add an unexported
   `func sectionAvailability(s Status) (available bool, err error)` implemented as a
   `switch` over the two constants with a `default:` arm returning
   `oops.Code("ADMIN_SECTION_STATUS_UNKNOWN")` and `available == false`. Every
   request-time decision about a section's status goes through it. Do NOT classify a
   status at a decision site by comparing it against the planned constant alone:
   that is the shape the review found — only the planned value is refused, so the
   zero value and every typo fall through to the available branch and the section is
   served. The distinction is the same one
   `world.Selectable` is built on in plan `02-04`, for the same reason: the default
   arm must deny so a value added later is excluded by the code path that already
   excludes the others, without a second predicate to keep in sync.

Both halves ship, and neither is redundant: the boot rule stops a malformed registry
from reaching production, the denying default stops a malformed value from being
served if one ever does — through a substitute slice in a test, a future dynamic
registration, or a merge that lands a typo in the same commit as a skipped boot.
The classifier is a plain function over a `Status`, so it is unit-testable with a
synthetic value and needs no registry injection seam.

Go has no `satisfies`, so §10.2's compile-time half is unavailable; §10.2 explicitly
permits boot as the enforcement point. `Validate()` is the boot-time half and it is
paired with the meta-test (D-09). Build each entry's `Descriptor.Resource` by
calling `access.AdminSectionResource(string(entry.ID))` rather than writing the
literal, so the descriptor cannot drift from its id — and have `validateEntries`
re-derive and compare it anyway, so a future hand-written literal is caught rather
than trusted.

Write the set-equality meta-test in `registry_test.go`: derive the id set from

failure report the symmetric difference in both directions. Assert both failure
directions explicitly with a helper that takes a substitute slice, so the test is

Create `internal/admin/section/gate.go` with
`func AssertSectionAccess(ctx context.Context, engine <engine iface>, playerID, sectionID, action string) (Section, error)`,
following `AssertOperatorAdmin`'s shape: layered checks, each returning a distinct
`oops.Code("DENY_*")`, with the code taxonomy documented above the function.

**The order is the specification.** Step 1 is the ABAC evaluation. Build the request
with `types.NewAccessRequest(access.PlayerSubject(playerID), action, access.AdminSectionResource(sectionID), nil)`
and pass it to `engine.Evaluate(ctx, req)` — that is the real signature
(`internal/access/policy/engine.go:82`); there is **no** positional
three-argument `Evaluate`, and the earlier plan's pseudocode invented one. Handle
`NewAccessRequest`'s error rather than discarding it: it rejects an empty subject,
action or resource, which is a second line of defence behind the empty-id guard.
A DENY returns `oops.Code("DENY_ADMIN_SECTION")` **immediately**, before the
registry is consulted — so a denied caller's refusal is identical whether or not
the id is registered.

Step 2, reached only by a permitted caller, is `Lookup(sectionID)`; a miss returns
`oops.Code("DENY_ADMIN_SECTION_UNREGISTERED")`.

Step 3 **uses the descriptor rather than merely returning it**. Compare the entry's
`Descriptor.Resource` against the resource string step 1 evaluated; a mismatch is
`oops.Code("ADMIN_SECTION_DESCRIPTOR_MISMATCH")`, because a descriptor that has
drifted from its id means the gate authorized one resource while the caller is about
to act on another. Without this the descriptor is validated at boot and never
consulted again — mandatory data that decides nothing, which the review flagged and
which is how a required field quietly becomes decoration.

Step 4 refuses a `StatusPlanned` entry with `oops.Code("SECTION_NOT_IMPLEMENTED")`,
here in the helper rather than deferred to a caller. §10.3 places this refusal after
the gate, and Phase 2 ships no RPC that could otherwise carry it — leaving it to a
future caller would make the phase's own must-have unprovable, which is exactly what
the review found. Return the `Section` and its `Descriptor` for an available entry.

Guard the empty section id explicitly before constructing the resource, returning
an error rather than letting `AdminSectionResource` panic — a panic in a request
path is a different failure mode from a denial, and the panic guard exists to catch
programmer error at construction sites, not to handle untrusted input.

Carry the D-06 rationale in the function's doc comment: gate first, then
distinguish, because the two denial codes are otherwise a registry-enumeration
oracle; and this works precisely because `seed:admin-section-access` is scoped by
resource type, so an unregistered id is still covered by the policy.

Write the denial suite in `gate_test.go` against the **real** engine loaded with
**all** seed policies, built via `abactest.NewSeedEngine` with `abactest`'s
`PlayerProvider` double supplying `roles`. Do NOT reach for `createSeedEngine` — it
is unexported, in a `_test.go` file, in `package policy`, and unreachable from here.
Do NOT use `policytest` fakes — they return canned decisions, so a test written
against them asserts the fake's behaviour rather than the policy's, and this is the
phase's only proof that `seed:admin-section-access` actually matches. Iterate
`All()` to generate the seven-section table rather than writing seven literal
blocks, so a new registered section is covered automatically.

Assert the byte-identical refusal by comparing the two errors' caller-visible
message strings for equality, not by comparing codes. `errutil.AssertErrorCode` is
the right tool for asserting *which* internal code a handler produced and is used
for that, but it chain-walks and returns the deepest code, so it is not evidence
that two refusals are indistinguishable to a caller.
