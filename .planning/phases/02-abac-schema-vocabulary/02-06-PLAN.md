<objective>
Make `charname.Gate` the **only** way a character display name can reach the
database, structurally rather than by convention: introduce the `charname.Admitted`
admission token, make it the sole name parameter of every name-writing method in
the sanctioned writer boundary, and prove both facts with a tree-derived census
demonstrated RED first.

Purpose: IDENT-09 and success criterion 1 require the name checks at create **and**
at rename. No rename path exists yet — `RenameCharacter` is Phase 3's — so the
rename half can only be discharged **structurally**. The previous shape of this
plan tried to discharge it with a census over SQL string literals, which cannot
work: a Phase 3 `RenameCharacter` that calls the pre-existing
`CharacterRepository.Update` introduces no new SQL literal, so the census would
stay green while the new write site bypassed the gate — exactly the case it exists
to catch. This plan replaces that with a type the gate alone can mint, and demotes
the census to a backstop over the remaining freedom.
Output: `charname.Admitted` + `Gate.Admit`; a writer boundary whose `Create` and
new `Rename` take the token and whose `Update` no longer writes `name` at all; the
five-site `ExistsByNormalizedName` migration; and the admission census in
`test/meta/`.

**Writer-boundary constraint (the reason this plan is shaped this way).**
`test/meta/world_sql_fence_test.go` is the RAW-WORLD-SQL FENCE binding
`INV-WORLD-4` / the writer-boundary invariant. Its Go scan (`:188-232`) walks the
whole tree and exempts ONLY `internal/world/postgres` (`writerBoundaryDir`,
`:134`), `_test.go` files, generated files, and a skip set that its own self-test
at `:306-309` proves **excludes `internal/store`** and does not cover `cmd/`.
Critically, the `world-sql-fence:allow` escape hatch exists only in
`scanMigrationForWorldDML` (`:113-129`), which globs `*.sql` — **there is no marker
path for `.go` files.** So any `characters` mutation SQL this phase plants in
`internal/store/migrations/*.go` or in `cmd/` is an unexemptable fence violation.
Everything that mutates `characters` therefore lands as a method inside
`internal/world/postgres`, and the migration and the CLI (plan `02-12`) become thin
callers with no SQL literal of their own. The fence itself is NOT modified: it is a
bound-invariant guard, and weakening it to accommodate this phase would be trading
a durable guarantee for a convenience.

**Pre-existing ungated write path (the reason `Update` changes).**
`internal/world/postgres/character_repo.go:79` is
`UPDATE characters SET name = $2, description = $3, location_id = $4, version = version + 1`
— a generic `Update` that writes `characters.name` today through neither
`world.NormalizeCharacterName` nor the gate. Left alone it would also write a
`name` whose `normalized_name` went stale, silently defeating the UNIQUE index
plan `02-12` lands over that column. Its ONLY production caller is
`internal/world/service.go:798` `UpdateCharacterDescription`, which reads the
character, sets `Description`, and round-trips the just-read `name` back. Dropping
`name` from that statement is therefore **behaviour-preserving for the only caller**
and closes the hole.

**Scope note (recorded, not a reduction).** This plan was split out of a single
oversized `02-06`. The migration chain (`000055` Go backfill + `000056`
`SET NOT NULL` then `CREATE UNIQUE INDEX`), the operator resolution CLI, the
RED-first concurrent-claim proof and the NFKC-only duplicates spec all land in
**plan `02-12`** (wave 5), which depends on this one. Success criteria 1 and 2 are
**not** amended; they are discharged across the pair.
