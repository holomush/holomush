## Summary

The phase's three flagged unknowns all resolve cleanly, and each resolves in the *direction* the
success criteria assume — but the surrounding blast-radius numbers in ROADMAP/CONTEXT are wrong in
several load-bearing ways, and there is one previously-unrecorded design constraint that will
silently break criterion 3 if the planner does not address it.

**The three open questions.** (1) `SystemCaller()` can be made byte-identical: the ABAC engine's S1
gate needs `req.Subject == "system"` **and** `access.IsSystemContext(ctx)`
[VERIFIED: internal/access/policy/engine.go:92-101], and `IsSystemContext` has exactly **one**
production consumer — that gate [VERIFIED: rg over `IsSystemContext`, only
`internal/access/policy/engine.go:93` outside `internal/access/context.go` and its own tests]. So
`checkAccess` may derive the marker internally (`ctx = access.WithSystemSubject(ctx)` when the caller
is system-kind) with zero observable side effects elsewhere; `internal/world` already imports
`internal/access` [VERIFIED: internal/world/service.go:17]. (2) Subject strings at the production
sites are a small, fully-enumerated set — `character:<ulid>`, `plugin:<name>`, the literal
`"system:bootstrap"`, and the bare literal `"system"` — see the table in §Open Question 2. (3)
`action.dispatch_location` is supplied by the plugin host-capability interceptor at
`internal/plugin/hostcap/interceptor.go:294`, which calls
`pluginauthz.EvaluateCapabilityAccess(... Context: scopeAttrs)` — a path that never goes through
`world.Service`, so 02.1's flip cannot disturb it.

**The behavioral-identity guarantee is structural, not incidental.** `types.NewAccessRequest`
normalizes an empty attribute map to `nil` (`if len(attrs) > 0 { … }`, else `clonedAttrs` stays nil)
[VERIFIED: internal/access/policy/types/types.go:160-172], and `Engine.Evaluate` gates the overlay on
`len(req.Attributes) > 0` [VERIFIED: internal/access/policy/engine.go:258]. So a `HumanCaller` that
carries no attributes produces a request byte-identical to today's `nil`. Criterion 3 is therefore
achievable by construction for the attribute channel.

**Primary recommendation:** Model the caller as an opaque struct with unexported fields
(`subject string`, `system bool`, `attrs map[string]any`) in `internal/world`, constructed only via
`HumanCaller`/`SystemCaller`; give it two package-internal accessors consumed by `checkAccess` —
one returning the subject string, one returning the attribute map — plus a `contextFor(ctx)` that
stamps `access.WithSystemSubject` when `system` is set. **`HumanCaller("")` MUST NOT panic** (see
Pitfall 1). Do the migration with a single ast-grep rule + a `METHOD` regex constraint (verified
working, §Code Examples), but ship **two rule variants** — one emitting `world.HumanCaller(...)` for
external test packages, one emitting bare `HumanCaller(...)` for the two `package world` internal
test files — plus a second rule class for the ~106 hand-rolled test-double *declarations*.

### Pattern 1: Opaque caller value with unexported fields + constructor-only construction

**What:** A struct in `package world` whose fields are unexported, so the zero value is
unconstructible-by-accident from outside and `HumanCaller`/`SystemCaller` are the only public
construction paths (D-62's planner constraint).

**When to use:** This phase's caller type.

**Why this shape here:** The census/binding test (D-65) proves *the parameter type*, not the
*values*; unexported fields are what stop a consumer package from writing `world.Caller{attrs: …}`
and reaching the attribute channel before 02.2 defines the vocabulary.

**Precedent in-repo:** `internal/world.WriteCommandDescriptor` is the closed-construct pattern this
repo already uses for census-provable surfaces
[VERIFIED: internal/world/mutator.go:63-80 — "the EXPLICIT closed write-command construct the census
(05-11) derives the write-command surface from"].

### Pattern 2: `checkAccess` derives the system context from the caller

**What:** `checkAccess` takes the caller value instead of `subject string`, and:

```go

func (s *Service) checkAccess(ctx context.Context, c Caller, action, resource string, prefix entityPrefix) error {
	metricKey := strings.ToLower(string(prefix)) + "_access_check"
```

## Open Questions — ANSWERED

### Q1. `SystemCaller()` vs the S1 defense — RESOLVED

**The gate.** `Engine.Evaluate` step 2 [VERIFIED: internal/access/policy/engine.go:91-125]:

```go
	// Step 2: System bypass — defense-in-depth (S1)
	if req.Subject == "system" {
		if !access.IsSystemContext(ctx) {
			slog.ErrorContext(ctx, "system subject used without system context (S1 violation)", …)
			return types.Decision{},
				oops.Code("SYSTEM_SUBJECT_REJECTED").Errorf("system subject is only allowed from system context")
		}
		decision := types.NewDecision(types.EffectSystemBypass, "system bypass", "")
		…
		return decision, nil
	}
```

Note the bypass is **total** — it returns before degraded-mode, validation, session resolution,
attribute resolution, and policy evaluation. Any attributes a system caller carried would be
**ignored**, which is a fact the criterion-2 proof test must not build on.

**The single production consumer.** `access.IsSystemContext` is called in exactly one production
location — the gate above [VERIFIED: `rg -n 'IsSystemContext' --glob '*.go'` returns
`internal/access/policy/engine.go:93`, the definition at `internal/access/context.go:16-21`, and one
test file]. **Nothing else in production branches on the marker.**

**The single production producer.** `access.WithSystemSubject` is called in exactly one production
location: `internal/grpc/location_follow.go:197` [VERIFIED: `rg -n 'WithSystemSubject' --glob '*.go'`
— every other hit is a `_test.go` file or the definition]. Criterion 4's claim is accurate.

**Therefore the mechanism is (a): `checkAccess` (or the caller's own accessor) derives the context
internally.** Behavior stays identical because:

1. `location_follow.go:197` wraps ctx and makes **two** world calls under it —
   `GetLocation(sysCtx, systemSubjectID, locationID)` at `:203` and
   `GetExitsByLocation(sysCtx, systemSubjectID, locationID)` at `:216`
   [VERIFIED: internal/grpc/location_follow.go:197,203,216]. Both become `world.SystemCaller()` and
   the plain `ctx`. The marker is re-derived inside each `checkAccess`, so each `Evaluate` still sees
   `IsSystemContext(ctx)==true`.
2. Nothing downstream of `checkAccess` reads the marker (previous paragraph), so removing it from the
   ctx that reaches the **repositories** and the **outbox** changes nothing observable.
3. `systemSubjectID` is `const systemSubjectID = "system"` [VERIFIED:
   internal/grpc/location_follow.go:26-28] — the **bare** literal, so it hits the S1 branch.
   `SystemCaller()` must produce exactly `"system"`.

**Do not conflate `"system:bootstrap"`.** `internal/bootstrap/setting.go` passes the *literal*
`"system:bootstrap"` [VERIFIED: internal/bootstrap/setting.go:134,272,276,331], which is **not**
`req.Subject == "system"`, so it falls through to normal policy evaluation via
`parseEntityType`-style prefix matching. Those four sites map to `HumanCaller("system:bootstrap")`,
**not** `SystemCaller()`. Mapping them to `SystemCaller()` would silently convert four
policy-evaluated bootstrap writes into total bypasses — a security regression that no existing test
would necessarily catch. **This is the single highest-risk judgment call in the migration.**

**Residual risk (LOW, but name it in the plan):** if a `SystemCaller()` is ever constructed and used
in a code path where the ctx is later inspected for the marker by future code, the derived-marker
scope is narrower than today's (it lives only for the duration of the `Evaluate` call rather than the
whole request). Nothing today depends on the wider scope.

```go
func (c *Compiler) validateAttributes(cb *dsl.ConditionBlock) ([]ValidationWarning, error) {
	refs := collectAttrRefs(cb)
	warnings := make([]ValidationWarning, 0, len(refs))

	for _, ref := range refs {
		if !c.schema.HasNamespace(ref.namespace) {
			continue
		}
```
