## AUTHZ-01 closure — is it earned?

AUTHZ-01 reads: *"Every public `world.Service` command takes a typed caller value carrying the
subject and its execution context together — no bare `subjectID string` parameter and no
overload/variadic escape hatch — and `checkAccess` forwards that context to
`types.NewAccessRequest` (deleting the hardcoded `nil` at `internal/world/service.go:214`)."*

Both clauses are proven, not asserted:

| Clause | Independent proof |
| --- | --- |
| No bare `subjectID string`, no escape hatch | 25 exported `*Service` methods enumerated; 23 carry `Caller`, 0 carry a bare string, 0 aliases of `Caller`, 0 variadic subject options, 0 `Deprecated:` shims. Census re-implementation: `violations=0` |
| `checkAccess` forwards the context | `service.go:216` forwards `caller.attrs`; real-engine paired permit/deny proves the attribute is load-bearing |

**The `UpdateCharacterPreferences` exemption (D-68) is legitimate and does not hollow the
requirement.** Verified independently at `internal/world/service.go:864`: its second parameter is
`characterID ulid.ULID`, it takes **no subject of any kind**, and its body genuinely contains no
`checkAccess` call — the requirement's operative prohibition ("no bare `subjectID string`
parameter") is not something it can violate. Its exemption is from the *caller-parameter* clause
only, and the exemption is asserted bidirectionally, so adding a `checkAccess` to it would fail the
build. The pre-existing D-05 rationale (settings-subsystem persistence primitive; predecessor raw
store path had no ABAC) is a Phase 02 decision this phase inherited, not a carve-out minted to make
02.1 pass.

**Waves 1 and 2 correctly left AUTHZ-01 open** (Wave 1 even reverted an automatic mark-complete);
Wave 3 closed it only after the census and the registry binding landed. The closure is earned.
