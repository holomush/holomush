<objective>
Make the six deferred sections reachable, gated, and refusing after the gate — and ship the
non-authoritative `roles` hint the rail uses to decide whether to draw `/admin` at all.

Purpose: ROADMAP Success Criterion 4 requires the refusal to be reachable **over the wire**,
not only at the helper level. `section.AssertSectionAccess` already returns
`SECTION_NOT_IMPLEMENTED` after steps 1–3 (`gate.go:163-167`) and `gate_test.go:209` proves it
in-package; what does not exist is an RPC through which a caller can actually reach it. D-100
supplies exactly one endpoint with the section id as a **parameter**, so seven denial
assertions iterate one method rather than manufacturing six stub RPCs whose only job is to be
denied.

Output: `AdminGetSection(section_id)`, its `Web`-prefixed proxy, `repeated string roles` on
`WebCheckSessionResponse`, and the seven-section wire-level denial iteration with paired
positive controls.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| direct gRPC caller → `AdminGetSection` | A caller supplying an arbitrary `section_id`. The registry is enumerable through this parameter if the gate does not run first. |
| gateway → browser (`WebCheckSessionResponse.roles`) | A capability-shaped field crossing to an untrusted client; the client may lie about it on the way back, so nothing may depend on it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-09 | Information Disclosure | `AdminGetSection` as a registry-enumeration oracle — a denied caller learning which section ids exist | high | mitigate | `AssertSectionAccess` runs before the registry lookup (D-06, `gate.go:103-134`); both `DENY_ADMIN_SECTION` and `DENY_ADMIN_SECTION_UNREGISTERED` map to one `codes.PermissionDenied` with one static message; the wire-level differential asserts byte equality for registered vs unregistered ids. |
| T-06-10 | Information Disclosure | `SECTION_NOT_IMPLEMENTED` leaking to a denied caller, revealing the section exists | high | mitigate | Reachable only after steps 1–3 permit; the seven-section iteration asserts a non-admin gets `DENY_ADMIN_SECTION` for every id including the planned six. |
| T-06-11 | Elevation of Privilege | `WebCheckSessionResponse.roles` mistaken for the authorization boundary by a later change | high | mitigate | Doc comment states the constraint on the wire; the boundary integration test denies a caller whose `roles` said `admin`; `rg 'RoleAdmin' internal/web/` must stay empty. |
| T-06-12 | Information Disclosure | per-character role map leaking player↔alt linkage | medium | mitigate | The field is player-scoped and singular by construction (`repeated string`, no character key) — §10.5.1.1; reshaping it later is a wire-compat change and is out of scope. |
| T-06-13 | Tampering | client re-asserting `roles` on a subsequent request to gain admin | high | mitigate | No admin request message carries a roles field; identity is resolved server-side from the hashed session token. |
| T-06-14 | Denial of Service | unbounded section enumeration | low | accept | The registry is a fixed seven-entry compile-time table; there is no growth vector. |
</threat_model>
