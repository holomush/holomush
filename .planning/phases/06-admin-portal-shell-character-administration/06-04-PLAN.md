The SELECT reads the full character projection `Get` uses **plus** `p.username`, from
`characters c JOIN players p ON p.id = c.player_id`. The search predicate is
`(c.normalized_name ILIKE '%' || $n || '%' ESCAPE '\' OR p.username ILIKE '%' || $n || '%' ESCAPE '\')`
with the term bound as a **parameter** — never string-concatenated into SQL.

**Escape LIKE metacharacters in the bound term.** `charname.Normalize` folds case and strips
format runes but passes `%`, `_` and `\` through untouched — none is in category Cf — so a typed
`a_b` silently matches `axb` and `100%` matches every row containing `100`. Parameter binding
already closes injection (T-06-21 stands); this is the **correctness** half. Escape in this
order — `\` first, then `%` and `_` — in a small helper beside the repository method, and carry
`ESCAPE '\'` on both predicate arms (cross-AI review R-19).

**`total_count` comes from its own scalar count, not from a window column.** Issue
`SELECT count(*) FROM characters c JOIN players p ON p.id = c.player_id WHERE <same predicate>`
and the page query **inside one read transaction**. `COUNT(*) OVER ()` was the earlier design and
is **wrong**: once `OFFSET` has removed every row there is no row left to carry the window value,
so a page beyond the end reports `0` instead of the true total — contradicting this plan's own
out-of-range acceptance criterion (cross-AI review R-20).

**Open that transaction with `pgx.TxOptions{AccessMode: pgx.ReadOnly, IsoLevel: pgx.RepeatableRead}`**
(cross-AI review C2-30). `AccessMode: pgx.ReadOnly` alone does **not** give the two statements one
snapshot: PostgreSQL's default isolation is read-committed, under which **every statement takes
its own snapshot even inside a single transaction**. A concurrent insert or delete landing between
the count and the page therefore makes `total_count` disagree with the rows returned — the exact
inconsistency the transaction was added to prevent, claimed but not delivered. `RepeatableRead`
is what makes the claim true. Note in a comment that this is a two-statement read of a small
bounded page and the isolation level costs nothing here.

Add an integration case that proves it rather than asserting it: begin the read, insert a matching
row from a **second** connection between the count and the page (drive the interleaving with a
test hook or by issuing the two statements around an explicit synchronisation point), and assert
`total_count` and the row set still agree. Under read-committed that test fails.

The ORDER BY is exactly three clauses and is emitted from a closed `switch` over the sort-field
enum (never from caller-supplied text):
`ORDER BY (c.last_active_at = 0), c.last_active_at {ASC|DESC}, c.normalized_name ASC`
for the `last_active_at` key, and `ORDER BY {col} {dir}, c.normalized_name ASC` for the
others, where `{col}` is `c.normalized_name` for the **name** key (§11.3's name row orders on the
stored normalized name of §6.1.3, not the display name — the two differ observably under case and
NFKC folding), `c.created_at`, `c.status`, or `p.username` for the joined player column. The
`switch` has **five** arms plus a denying default; there is no `player_id` arm, because §11.3
marks it Sort=No. The **first** clause is what makes the `0` sentinel sort last in *both* directions —
descending gets it free as the column minimum, ascending does not. The **third** clause is the
tiebreak that makes the order total: without it the `never` block falls back to whatever
secondary key the plan happens to carry and the ordering is untestable. An unrecognised sort
field returns `oops.Code("CHARACTER_ADMIN_SORT_FIELD_UNSUPPORTED")` — reject, never default.

Do **not** copy `ListAll`'s projection. Its doc block at `:700-707` warns that it reads only
`id, name`, so `Status` and `LastActiveAt` are zero-valued *by omission*, and a lifecycle
decision from that result violates INV-WORLD-5.

Normalization: the term is passed to the repository **already normalized** by the service
layer through the same `charname` function that produces the stored `normalized_name`. The
repository does not normalize and does not lower-case; there is exactly one normalizer.
