<objective>
Ship `/characters/new`: the structured creation card that replaces the roster's name-only
inline input, six fields in one section with one Save, and the honest half of D-88's create
echo.

Purpose: IDENT-01 asks for creation through a structured identity card, and six fields plus
§6.1's rejection reporting need room the roster's dashed card does not have (D-87). The design
is submit-and-report: a live availability check cannot be honest, because check and insert are
different moments. That trade is only defensible if the round trip is cheap — a submit that
discards five typed fields to report one collision converts submit-and-report into the hostile
option, on the one surface where a first-time player forms their impression. Preserving the
form on rejection is therefore a precondition of a locked decision, not a nicety.

Output: one route, one props-only form, the create flow that treats the RPC as authoritative,
and the one-shot notice that carries the server-returned name — and, when the create's second
transaction lost a supplied value, the fact that it did — to the roster.
</objective>

## Pinned decisions this plan settles

**The echo vehicle is a persistent inline `role="status"` region on the roster, not a toast.**
D-88 names "the toast and the new roster card" as the echo sites; UI-SPEC's "Deliberate
refinement of D-88" keeps the substance and changes the vehicle, and this plan follows UI-SPEC:
the app ships no toast infrastructure (zero `toast`/`sonner` references under `web/src/` or in
`web/package.json`), a four-second toast is a poor carrier for teaching that the server rewrote
the player's name, and a persistent region is directly Playwright-assertable and announced
without a live-region race.

**The name crosses the navigation through a one-shot module store, not a URL.**
`web/src/lib/characters/createdNotice.ts` is written by the create flow and read-and-cleared by
the roster's first render. A query parameter would put a display name in a shareable URL and
would let any visitor to `/characters?created=<anything>` synthesise a confirmation the server
never issued. — **Reversibility: reversible.**

**The name field's advisory counter is in RUNES.** Three unit systems collide in this phase:
the character name is 2–32 **runes** (`internal/charname/syntax/syntax.go`), the short
`profile.*` fields are 100 **bytes** (`world.MaxNameLength`), and the long ones 4000 bytes. The
form must not conflate them — `ByteCounter` (plan 05-04) serves the five profile fields, and the
name gets a rune count via `[...value].length`, which counts code points rather than UTF-16
units.

**A lost profile write is REPORTED, not silently absorbed — and reporting it does not reopen Q1.**
Plan 05-03's ratified Q1 decision (option-a) makes the create authoritative: when the second
transaction fails, the RPC returns **success** with the character and the un-set keys simply
absent from its `profile` map. That is the right server contract — option-c's "report failure"
sends the player to resubmit, and the resubmit collides with the name their own new character
just reserved. But the contract only settles what the *server* returns. Left there, the player
is told nothing: the roster shows the new character, the response's absent keys are discarded on
the way to `createdNotice`, and the loss surfaces days later as five blank fields on a page they
had no reason to open.

So the flow compares the profile keys it submitted against those present in the response and,
on any mismatch, carries a second notice variant. This costs one comparison over five keys. It
changes **nothing** on the wire, nothing about the create's success, and nothing about Q1: the
character still exists, nothing prompts a retry, and the notice points **forward** to the repair
surface rather than backward at the submission. Threat `T-05-03-09` (Repudiation / partial
identity card) remains `accept`ed — this narrows what the player is left not knowing, it does
not change the disposition. — **Reversibility: reversible.**

## Flagged planner assumptions (not silently dropped)

- **The partial-create confirmation copy is PLANNER-AUTHORED; `05-UI-SPEC.md` has no row for
  it.** Its § Copywriting → Success states table contracts three strings, and the create row is
  `Created {name}.` — written before the Q1 checkpoint settled that a create can succeed while
  losing profile values, so the table has no vocabulary for a partial outcome. This plan authors
  one string in UI-SPEC's own register — declarative, sentence case, no exclamation, naming the
  next action rather than the fault:

  `Created {name}. Some details didn't save — add them on the character page.`

  `{name}` is the server-returned display name, so D-88's echo is still the first thing said and
  the base row's substance is unchanged; `the character page` is the link to `/characters/{id}`.
  **The UI-SPEC is deliberately NOT edited here** — its 28 consideration rows are a verified
  tally and a plan is the wrong place to grow one. Fold this row into UI-SPEC when the phase's
  copy is next revised.

- **The notice does not NAME which fields were lost.** It could: the flow knows the missing
  keys. It does not, because the field labels live in the form and the notice renders on the
  roster, and the repair surface shows all five together anyway — naming them would buy a longer
  sentence and a second label table for no additional action. The flag stays a boolean; if the
  copy is later revised to enumerate, the missing-key set is already computed and one field on
  the notice carries it.
