<objective>
Rewrite `/characters` into the sectioned multi-alt roster IDENT-05 asks for: a `Playable` grid
carrying the create link, a `Not playable` section that starts expanded, a badge matrix in which
a retired character never wears a session word, and the default-character control the tracer
slice wired.

Purpose: the shipped roster reads `web.v1.CharacterSummary` through `webListCharacters` and
renders last-played telemetry; the owner roster this phase needs is `OwnCharacter` through
`webListMyCharacters`, which carries `status` and `version` and carries no session telemetry at
all. Neither message alone can draw UI-SPEC's badge matrix, which is why the page joins both on
the character id. Sectioning is what defuses the sharp edge sketch 008 found: a retired
character can no longer float to the top of a sort, because it is in the other section.

Output: two presentational components, one rewritten route, and the second of D-88's two echo
sites.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → gateway | Two owner-audience reads plus one owner-audience write, all session-gated |
| layout data → page | `defaultCharacterId` arrives from the layout's own authenticated session check |
| module store → status region | The create confirmation crosses a navigation in process memory, never in a URL |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-07-01 | Information disclosure | another player's roster | high | mitigate | Both list RPCs resolve whose roster is returned from the header token; neither request message carries a player id a caller could point at someone else. |
| T-05-07-02 | Information disclosure | presence telemetry on a retired character | medium | mitigate | The session badge is suppressed in the template for every non-`active` lifecycle, and the suppression is asserted with session data deliberately supplied. |
| T-05-07-03 | Spoofing | a forged create confirmation | low | mitigate | The confirmation is read once from a module store written only by a successful create; there is no URL parameter a visitor could craft. |
| T-05-07-04 | Elevation of privilege | default change through the command parser | high | mitigate | The control calls the typed RPC through the character flow layer; `sendCommand` is negative-grepped. |
| T-05-07-05 | Denial of service | roster load on every visit | low | accept | Two bounded owner-scoped reads behind session auth; the character count is capped by `DefaultMaxCharacters`. |
| T-05-07-06 | Tampering | a stale default marker after a failed set | low | mitigate | The marker moves only on a success status; a failure renders the authored save-failure copy and leaves the marker where the server last put it. |
</threat_model>
