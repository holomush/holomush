## Pinned decisions this plan settles

**Q2 — the roster's data sources (PINNED, not deferred).** `/characters` reads **two** RPCs
and joins them on the character id: `webListMyCharacters` → `OwnCharacter` supplies `id`,
`name`, `status` and `version` (the lifecycle truth UI-SPEC's sectioning and `Retired` badge
need, and which exists **only** on `OwnCharacter`); `webListCharacters` →
`web.v1.CharacterSummary` supplies `hasActiveSession` / `sessionStatus` (the session overlay,
which exists **only** on `CharacterSummary`). Adding session telemetry to `OwnCharacter` is
rejected: `PublicCharacterSummary`'s own doc records that removing presence telemetry from the
character-access family was deliberate and structural.

**Q2 corollary — where `Default` comes from (a gap D-90's wording leaves open).** `OwnCharacter`
carries **no** is-default field, so the roster returned by `SetDefaultCharacter` cannot by
itself say which character is default. This plan resolves it without contradicting D-90 (whose
`ListMyCharactersResponse`-shaped response is locked and census-pinned): the **initial** default
comes from `default_character_id` on `WebCheckSessionResponse` (`web.proto:567`), which the
`(authed)` layout already fetches — this plan only propagates it through the layout's return
value, adding **no** round trip. After a successful `SetDefaultCharacter` the client re-renders
the cards from the returned roster and marks as default the id it just requested, which the
success status makes true. Adding an `is_default` field to `OwnCharacter` is rejected: it would
change a shape D-90 pinned and move a census inventory row.

**Q4 — a retired character may not be made default (PINNED).** The retire path clears
`players.default_character_id` in the same transaction as the status write
(`internal/world/postgres/character_repo.go:536-545`), so permitting a set-to-retired creates
exactly the state that code exists to prevent. **Deviation from `05-RESEARCH.md` Q4's
recommendation, recorded:** research suggests the ownership-generic message; this plan uses
`codes.FailedPrecondition` with its own literal instead, because ownership has already been
proven at that point, the owner can see the character on their own roster, and returning "no
such character on your roster" for a card the player is looking at reads as a bug while
buying no opacity (existence was never in question). Recorded as SPEC amendment 4 below.

**Constructor shape.** `SetDefaultCharacter` adds **no** constructor argument:
`playerRepo` and `charRepo` are already promoted onto the facade from the embedded
`playerGate` (`internal/grpc/characteraccess_service.go:192`), and the new repository method
hangs off the existing `auth.PlayerRepository` interface. The 11-call-site constructor churn
belongs to plan 05-03, not here. — **Reversibility: reversible** (additive).
