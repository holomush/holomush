<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous reader -> public export surfaces | already-live, already-unauthenticated; publishes denormalized character names today |
| authenticated player -> another player's character | untrusted with respect to the other player's owner-audience fields |
| admin -> the rich character row | privileged, but must still be reached through a distinct message type |
| a future PR adding a character-returning RPC -> the census | the census is the only thing standing between a new endpoint and a silent leak |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-08 | Information disclosure | Section 2 message shape | high | mitigate | Mandate separate proto messages per audience so a public projection cannot carry an owner-only field; reject the single-message-with-cleared-scalars alternative in writing, naming the empty-string-is-present failure. |
| T-01-09 | Information disclosure | Section 3 inventory completeness | high | mitigate | Make the inventory exhaustive by reading the proto tree, and bind it as the census expected set so a later RPC omitted from the table fails RED rather than shipping. |
| T-01-10 | Spoofing | Census comparison key | medium | mitigate | Fix the key as the fully-qualified proto method name compared exactly; a substring or handler-name key lets two distinct RPCs collide into one census member. |
| T-01-11 | Information disclosure | Client-side hiding | high | mitigate | Prohibit any per-field visibility hint or mask in a response; enforcement is absence from marshaled bytes, asserted at the wire per PORTAL-10 rule 3. |
| T-01-12 | Tampering | Public export surfaces | medium | mitigate | Give each of the three existing public export surfaces an explicit audience verdict and cross-link them to section 5's name-capture verdicts, so no surface is inventoried in only one of the two tables. |
| T-01-13 | Elevation of privilege | Shared projection across audiences | medium | accept | Two RPCs sharing one projection is mandated for consistency; the risk that a shared projection is later widened is carried by the census plus the per-audience message types, not by a second gate. |
</threat_model>
