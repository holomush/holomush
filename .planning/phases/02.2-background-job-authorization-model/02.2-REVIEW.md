# Phase 02.2: Code Review Report

**Reviewed:** 2026-08-09
**Depth:** deep (cross-file: import graph, call chains, lifecycle ordering, goroutine topology)
**Files Reviewed:** 29 changed source files (+ 5 transitively traced: `internal/access/policy/types/types.go`, `internal/access/policy/attribute/schema.go`, `internal/access/policy/cache.go`, `internal/plugin/setup/subsystem.go`, `internal/plugin/policy_installer.go`)
**Status:** issues_found

## Summary

The job-principal substrate itself is well built: `internal/jobs.Registry` is
correctly mutex-guarded and copies defensively on both edges; `attribute.JobProvider`
honours the omit-don't-sentinel rule (`.claude/rules/abac-providers.md`) with a real
prefix guard that short-circuits before the registry lookup; `access.JobSubject`
upholds the panic-on-empty convention 4-for-4; the deny-code composition is a prefix
so `mapWorldError`'s `_ACCESS_DENIED` suffix classification survives; and the outbox
Actor stays byte-identical (`buildIntent` takes `caller.subject` verbatim; `wire.go:177`
never parses it). Test quality is unusually high — paired positive/negative halves,
non-vacuity controls, set-equality rather than containment, and call-count assertions
where an answer-only assertion could not distinguish "the guard fired" from "the
double happened to say no."

The defects are concentrated in **02.2-04**, the plan that took `validateAttributes`
from a dead branch to a live boot gate. That change did two things the phase artifacts
do not account for:

1. It wired the production compiler to the **live, explicitly-not-goroutine-safe**
   `AttributeSchema` map that plugin loading mutates at runtime (CR-01).
2. It made a **third policy source** — plugin-manifest-installed rows, which are never
   validated against the action schema at install time — able to brick the entire ABAC
   stack and the next boot (CR-02).

Both are new blast radius that did not exist when the compiler held its own isolated,
never-populated schema. The rest are docs/comment over-claims and test-gate teeth that
are weaker than the comments beside them assert.

## Critical Issues

### CR-01: The live compiler now shares a documented-not-goroutine-safe map with runtime plugin registration

**File:** `internal/access/setup/setup.go:396` (with `internal/access/policy/types/types.go:355-393`, `internal/access/policy/attribute/schema.go:33-99`, `internal/plugin/setup/subsystem.go:427-439`, `internal/access/setup/subsystem.go:172-184`)

**Issue:** Before this phase, `BuildABACStack` built its compiler on a *separate*
`types.NewAttributeSchema()` that nothing ever wrote to. 02.2-04 changed it to
`policy.NewCompiler(schemaReg.Schema())` — and `SchemaRegistry.Schema()` returns the
**live** `*types.AttributeSchema` pointer (`attribute/schema.go:97`), whose backing map
is bare and explicitly documented as unsynchronised:

```go
// internal/access/policy/types/types.go:397-399
// NOT goroutine-safe: callers must ensure schema evolution (UpdateNamespace/RemoveNamespace)
// does not run concurrently with policy evaluation that reads the schema.
```

Two goroutines now touch that map:

- **Writer** — plugin load/unload. `internal/plugin/setup/subsystem.go:434-439` wires
  `WithAttributeProviderRegistrar`/`Unregistrar` onto the **same** resolver
  (`s.cfg.ABAC.AttributeResolver()`), so `resolver.RegisterProvider` →
  `attribute.Register` → `s.namespaces[ns] = schema` and `UnregisterProvider` →
  `UnregisterForRollback` → `delete(s.namespaces, ns)`. `Resolver` itself states
  "register/unregister paths are not mutex-guarded" (`attribute/resolver.go:97-99`).
- **Reader** — the policy poller. `ABACSubsystem.Activate` launches
  `go s.stack.Poller.Run(pollerCtx)` (`internal/access/setup/subsystem.go:180`) on a
  10 s ticker; each tick calls `cache.Reload` → `pc.compiler.Compile(sp.DSLText)`
  (`cache.go:149`) → `c.schema.HasNamespace(...)` / `IsRegistered(...)`
  (`compiler.go:177,180`) — bare map reads.

ABAC activates before the plugin subsystem starts, so a plugin load that spans a
ticker boundary (binary-plugin subprocess launch + mTLS handshake + plugin storage
migrations easily exceed 10 s), or **any** runtime plugin load/unload, races. Go's
runtime does not tolerate this: it aborts with an unrecoverable
`fatal error: concurrent map read and map write`. Nothing in this diff added
synchronisation, and no test exercises it.

**Fix:** Guard the schema. Minimal version — add an `RWMutex` to `types.AttributeSchema`
so its own `Register`/`HasNamespace`/`IsRegistered`/`GetNamespace` are safe (the compiler
reads only through these three):

```go
type AttributeSchema struct {
	mu         sync.RWMutex
	namespaces map[string]*NamespaceSchema
}

func (s *AttributeSchema) Register(namespace string, schema *NamespaceSchema) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.namespaces[namespace] = schema
	return nil
}

func (s *AttributeSchema) HasNamespace(namespace string) bool {
	s.mu.RLock()
	defer s.mu.RUnlock()
	_, ok := s.namespaces[namespace]
	return ok
}
// ...same for IsRegistered / GetNamespace / UnregisterForRollback's delete
```

Then delete the now-false "NOT goroutine-safe" comment. Add a `-race` test that reloads
the cache in a loop while registering/unregistering a provider. The alternative — hand
the compiler an immutable snapshot taken after registration — reintroduces the
boot-vs-steady-state divergence 02.2-04 exists to remove, so the lock is the right shape.

### CR-02: A plugin-manifest policy referencing an undeclared `action.*` key bricks the whole ABAC stack and the next boot

**File:** `internal/access/policy/compiler.go:185-190` (with `internal/plugin/policy_installer.go:62,86,173-186`, `internal/access/policy/cache.go:141-153`, `internal/access/setup/setup.go:417-420,479-491`)

**Issue:** The phase declares the action gate "fatal for every policy source — in-tree
seeds and operator-authored database rows alike (D-67)". There is a **third** source it
does not account for: plugin-manifest policies installed by `plugins.PolicyInstaller`.
Those are validated at install time with `dsl.Parse` + `dsl.CompilePolicy`
(`policy_installer.go:62,86`) — **not** with `policy.Compiler`, so the action-schema gate
never runs on them. They land in `access_policies` regardless.

`Cache.Reload` is all-or-nothing: one uncompilable row aborts the whole reload
(`cache.go:149-152`), so the failure is not scoped to the offending plugin. Consequences:

- **At runtime:** `InstallPluginPolicies` → `ReplaceBySource` → `ps.SetOnMutate` →
  `cache.Invalidate` fails → `healthTracker.RecordFailure` (`setup.go:481-490`).
  Persistent failure escalates to `HealthDead`, which calls
  `eng.EnterDegradedMode("policy cache dead — initiating shutdown")` (`setup.go:468-470`).
  A single third-party plugin manifest can therefore deny-all and shut down the host.
- **At next boot:** the bad row is already persisted, so `cache.Reload` at
  `setup.go:418` fails, `BuildABACStack` returns an error, and the server does not
  start. Recovery requires manual SQL against the database — and the documented
  pre-flight query is itself wrong (see WR-01).

This blast radius did not exist before 02.2-04: the same reference was previously
skipped because `HasNamespace("action")` was false.

**Fix:** Gate the reference at install time, where it can be rejected without taking
the corpus down. In `compilePolicies`/`compilePoliciesWithManifest`, run the same
`policy.Compiler` the cache uses (an `attribute.NewActionOnlySchemaRegistry()`-backed
one is the correct scope — the compiler validates by DSL root, not provider name):

```go
// internal/plugin/policy_installer.go
var actionGate = policy.NewCompiler(attribute.NewActionOnlySchemaRegistry().Schema())

// inside compilePolicies, after dsl.Parse succeeds:
if _, _, err := actionGate.Compile(mp.DSL); err != nil {
    return nil, oops.Code("PLUGIN_POLICY_UNREGISTERED_ACTION_ATTRIBUTE").
        With("plugin", pluginName).With("policy", mp.Name).
        Wrapf(err, "plugin policy references an undeclared action attribute")
}
```

That turns "one plugin kills the host" into "this plugin fails to load", which is the
posture the rest of the plugin loader already takes. Also extend the operator note in
`background-job-authorization.md` to name plugin-installed rows as a third source.

## Warnings

### WR-01: The documented pre-upgrade safety query names a table that does not exist

**File:** `site/src/content/docs/contributing/explanation/background-job-authorization.md:233`

**Issue:** The operator note documents a knowingly-accepted "fail to boot on upgrade"
risk and gives exactly one mitigation:

```sql
SELECT id, name, dsl_text FROM policies WHERE dsl_text LIKE '%action.%';
```

The table is `access_policies`, not `policies`
(`internal/access/policy/store/postgres.go:146,170,304,329`). An operator running the
documented check gets `ERROR: relation "policies" does not exist` and has no working
pre-flight for a change that can brick their upgrade.

**Fix:**

```sql
SELECT id, name, dsl_text FROM access_policies WHERE dsl_text LIKE '%action.%';
```

### WR-02: `jobs.Registry` liveness read is a two-call TOCTOU, so INV-ACCESS-13 clause (1) does not hold under concurrency

**File:** `internal/access/policy/attribute/job_provider.go:75-98` (with `internal/jobs/registry.go:99-118`)

**Issue:** `ResolveSubject` takes the read lock twice — once via `IsJobRunning(name)`
(line 75) and again via `DeclaredWrites(name)` (line 93). A concurrent `Unregister`
between them produces a torn view: `attrs = {"name": name, "has_writes": false}` rather
than the `(nil, nil)` INV-ACCESS-13's registry entry claims for an absent job
(`docs/architecture/invariants.yaml`, clause 1: "returns (nil, nil) for a job name
absent from the injected jobs.Registry ... so no principal.job.* attribute is stamped
at all"). The shipped fixture seed happens to survive this because it also requires
`principal.job.writes.containsAll(...)`, but a future job seed gating only on
`principal.job.name` — which nothing forbids — would grant a job that has already
stopped. Unregister happens on subsystem Stop, i.e. exactly during shutdown, when the
window is most likely to be hit.

**Fix:** Give `Registry` one atomic read and use it:

```go
// internal/jobs/registry.go
// Snapshot returns the job's declared write kinds and whether it is running,
// under a single lock acquisition. Liveness and declaration cannot disagree.
func (r *Registry) Snapshot(name string) ([]string, bool) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	writes, ok := r.declaredWrites[name]
	if !ok {
		return nil, false
	}
	return slices.Clone(writes), true
}
```

Narrow `attribute.JobRegistry` to that one method (or add it alongside) and have
`ResolveSubject` call it once.

### WR-03: `Registry.Register` silently last-writer-wins on a duplicate job name

**File:** `internal/jobs/registry.go:60-85`

**Issue:** "Registering an already-registered name replaces the previous declaration"
is documented, but the declared write set is a **security gate** (D-51). Two subsystems
that pick the same name silently produce: (a) the incumbent's capability class replaced
— potentially *widened* — with no error and no log line, and (b) either subsystem's
`Unregister` revoking the other's liveness. Both arguments are validated as
"programming error at a call site" (lines 71-79), but the collision case — the one that
actually changes authority — is not. Phase 3 introduces `job:retirement` and
`job:activity-flush` from separate subsystems, so the collision surface is real.

**Fix:** Reject a duplicate registration, matching how `attribute.Register` treats an
already-registered namespace:

```go
if _, exists := r.declaredWrites[name]; exists {
	return oops.Code("JOB_REGISTRATION_DUPLICATE").
		With("job", name).
		Errorf("job %q is already registered: two subsystems sharing a job name silently "+
			"replace each other's declared capability class", name)
}
```

### WR-04: The D-29 fence comment claims teeth the test does not have

**File:** `internal/access/policy/seed_profile_visibility_test.go:716-718`

**Issue:** The comment justifying the fixture seed's addition to the `want` set asserts:

> The gate keeps its teeth: any FURTHER `resource is character` seed still turns this
> RED by name, and a future edit that widens this one's action to `read` or its
> principal to `character` fails the same way.

The second half is false. The test collects seed **names** whose compiled
`Target.ResourceType == "character"` (lines 725-733) and compares that name set. Editing
`seed:job-fixture-instance-scoped`'s action list from `["write"]` to `["read"]`, or its
principal from `job` to `character`, changes neither the name nor the resource type — the
test stays green. Nothing else in the tree pins the fixture seed's action list or DSL
text (`rg -n "job-fixture-instance-scoped" --type go` returns only name-membership and
count assertions). The reviewer this comment is written for would be misled into
believing an unreviewed widening is mechanically blocked.

**Fix:** Either correct the comment to claim only what the assertion proves, or pin the
seed's shape. The latter is cheap and matches the `untouched` table already in this file:

```go
t.Run("the job fixture seed stays write-only under a job principal", func(t *testing.T) {
	s := requireSeedPolicy(t, "seed:job-fixture-instance-scoped")
	compiled, _, err := NewCompiler(emptySchema()).Compile(s.DSLText)
	require.NoError(t, err)
	require.NotNil(t, compiled.Target.PrincipalType)
	assert.Equal(t, "job", *compiled.Target.PrincipalType)
	assert.Equal(t, []string{"write"}, compiled.Target.ActionList,
		"widening this seed to `read` re-opens D-29: it would gate world.Service.GetCharacter")
})
```

### WR-05: "identical at every compilation site" is asserted but four integration compilation sites still skip the action gate

**File:** `internal/access/policy/attribute/action_schema.go:92-95` and `internal/access/setup/setup.go:374-379`

**Issue:** Both comments claim the `NewActionOnlySchemaRegistry` treatment makes the
action hard-error branch "behave IDENTICALLY at every compilation site, which is what
lets a typo'd `action.*` reference fail uniformly instead of depending on which code
path compiled the policy." The 02.2-04 inventory covered four sites (production,
bootstrap installer, `WithRealABAC`, `abactest`). Four more remain and were not touched:

- `test/integration/world/world_suite_test.go:243`
- `test/integration/access/access_suite_test.go:214`
- `test/integration/plugin/abac_widget_test.go:283` and `:426`
- `test/integration/plugin/binary_plugin_test.go:457`

Each builds `policy.NewCompiler(registry.Schema())` on a provider-only registry with no
`action` namespace, so `HasNamespace("action")` is false and the gate is skipped there.
A policy with a typo'd action key can pass `task test:int` and fail at boot — the exact
divergence the claim rules out.

**Fix:** Register the namespace at those four sites too (one line each), or downgrade
both comments to name the sites actually covered.

### WR-06: A stale comment states this phase's own work as still-future, and leaves a probe policy that production would now reject

**File:** `internal/world/caller_test.go:106-111`

**Issue:**

// tracerProbeKey is the caller-supplied attribute key the criterion-2 proof

### IN-03: Conditional, deepest-code assertion in the permit half

**File:** `internal/world/caller_test.go:535-538`

**Issue:** The `if oopsErr, ok := oops.AsOops(err); ok { require.NotEqual(...) }` guard
means the assertion is skipped entirely for a non-oops error, and `Code()` resolves the

`require.NotErrorIs(t, err, world.ErrPermissionDenied, "...")`, which is exact and cannot

### IN-05: `has_writes: false` is unreachable with the production registry

**File:** `internal/access/policy/attribute/job_provider.go:96-97`

**Issue:** `Registry.Register` rejects an empty `writes` list (`registry.go:75-79`), and
`IsJobRunning` is true iff the key is present, so with the production `jobs.Registry` the
`else` branch cannot be reached: a live job always has a non-empty declaration. The
`has_writes` witness is therefore constant-`true` in production and carries no
information. (WR-02's TOCTOU is the only path that reaches it, which is itself a bug.)
The branch is still correct defence for an alternative `JobRegistry` implementation —
this is a note, not a request to delete it.

**Fix:** Add a one-line comment noting the branch is reachable only for a `JobRegistry`
implementation other than `jobs.Registry`, so a future reader does not mistake the
witness for a live discriminator.

### IN-06: The documented enumeration grep over-reports

**File:** `site/src/content/docs/contributing/explanation/background-job-authorization.md:146-150`

**Issue:** "Enumerate them with this grep, and only this one:
`rg 'SystemCaller\(\)' --glob '*.go' -g '!*_test.go'`" — that pattern also matches the
definition site (`internal/world/caller.go:104`) and four doc-comment references
(`caller.go:37,51,92,103`; `mutator.go:22`), so it returns 7 hits, not the 2 the table
lists. An operator or auditor comparing counts will think three extra bypasses exist.

**Fix:** Narrow it, e.g. `rg 'world\.SystemCaller\(\)' --glob '*.go' -g '!*_test.go'`,
and state the expected hit count.

### IN-07: Boot-path panic instead of a returned error

**File:** `internal/access/policy/attribute/action_schema.go:107-113` (called from `internal/bootstrap/setup/subsystem.go:213`)

**Issue:** `NewActionOnlySchemaRegistry` panics on a `Register` error. It is called inside
`policyBootstrapFn`, which runs during `BootstrapSubsystem.Prepare` — so any failure
crashes the process rather than surfacing through the lifecycle error path. The panic is
provably unreachable today (fresh registry, static non-empty schema, valid `AttrType`s),
and the doc comment says so, so this is a note rather than a defect.

**Fix (optional):** Return `(*SchemaRegistry, error)` and let the two call sites wrap it,
so a future edit to `ActionNamespaceSchema` that introduces an invalid entry produces a
lifecycle error instead of a crash.
