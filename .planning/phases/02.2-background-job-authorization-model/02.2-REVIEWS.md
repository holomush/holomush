# Cross-AI Plan Review

## Summary

The five-wave sequence is architecturally strong: it proves the `job:` path before widening compiler validation, audits `action.*` before activating the fatal gate, and separates implementation from durable documentation. The plans correctly identify the orphaned compiler schemas and cover all four current non-test compilation sites.

I found two blockers:

1. Plan 01's provider tests contradict Plan 01's required `has_writes` emission and will fail as written.
2. Plan 05 overclaims what its invariant bindings prove and contradicts D-68 about timer-driven jobs, especially the Phase 3 flusher.

Overall verdict: revise before execution.

## Plan-by-plan assessment

### Plan 01 — Tracer

Strengths

- The permit/deny pair exercises the real authorization mechanism: `checkAccess` forwards `caller.attrs` through `types.NewAccessRequest` at `internal/world/service.go:209`, while the engine's resolver independently stamps `resource.id` at `internal/access/policy/attribute/resolver.go:206`.
- Testing `UpdateCharacterDescription` is a sound positive-control strategy. Authorization runs before the repository read at `internal/world/service.go:812`, and reaching `characterRepo.Get` at line 815 proves the authorization gate returned nil.
- The plan correctly requires an explicit foreign-reference guard. Every registered provider is invoked with the full entity reference at `internal/access/policy/attribute/resolver.go:350`.
- Registering the provider atomically with the seed and the hard-coded seed-coverage mirror is good bisect hygiene.

Concerns

- **HIGH — internally contradictory provider contract.** Task 2 Test 3 requires the resolved map's keys to equal exactly `{"name", "writes"}`, but Task 2's implementation requires `has_writes` on every successful resolution path. The actual result must therefore contain `{"name", "writes", "has_writes"}`. Execution cannot satisfy both instructions.
- **MEDIUM — the tracer-helper integration is underspecified.** The plan says to build the engine with `abactest.NewSeedEngine(...)`, but the existing `newProbeService` creates its own compiler, cache, resolver, and engine from a single DSL string at `internal/world/caller_test.go:225`. The executor must either add a second helper accepting an engine or refactor `newProbeService`; that choice should be explicit.
- **LOW — Task 1's intermediate schema is intentionally incomplete but awkward.** The provider initially declares only `name`, then Task 2 adds `writes` and `has_writes`. This is safe in the final tree but makes the tracer's first commit incapable of testing the full D-50 capability shape.

Suggestions

- Change Task 2 Test 3's exact set to `{"name", "writes", "has_writes"}` and add a separate missing-writes case expecting `{"name", "has_writes"}` with `has_writes == false`.
- Specify a helper such as `newProbeServiceWithEngine(t, engine, repo)` so the shipped-corpus engine is unquestionably the engine used by `world.Service`.
- Consider adding `writes` and `has_writes` to the provider in Task 1, with Task 2 limited to making the seed consume them. That produces a cleaner tracer commit.

### Plan 02 — Production wiring and deny code

Strengths

- A dependency-free registry injected through configuration avoids an unnecessary lifecycle subsystem and its topology cascade.
- The denial spelling preserves the `_ACCESS_DENIED` suffix consumed by `internal/world/grpc_server.go:166`, so `JOB_CHARACTER_ACCESS_DENIED` still maps to `codes.PermissionDenied`.
- Keeping evaluation-failure codes unqualified preserves the existing engine-failure classification and player-facing code maps.
- The plan explicitly retargets both exact assertions in the earlier tracer rather than weakening them.

Concerns

- **MEDIUM — "top-level code" assertions rely on a known-drifted rule.** The plan repeatedly describes `oops.AsOops(err).Code()` as returning the top-level code. In this repository, multiple sources record that it returns the deepest oops code, including `internal/admin/policy/subsystem_integration_test.go:46` and `internal/eventbus/crypto/invalidation/types.go:149`. The project's own `.claude/rules/grpc-errors.md:58` conflicts with those verified observations. The present service error chain happens to contain only one oops code around a sentinel, so the assertion likely passes, but it is not a general double-wrap detector.
- **LOW — the proposed setup unit-test fallback does not prove the stated production truth.** Registering a fresh `JobProvider` on a fresh resolver proves provider compatibility, not that `BuildABACStack` performs that registration. The existing integration coverage can carry that truth, but the plan should label the fallback accordingly.

Suggestions

- Reword the code assertions as "the code surfaced by the pinned oops traversal semantics," or use a helper that inspects the outer error node if the project has one.
- If the unit path cannot construct `BuildABACStack`, make the integration test the authoritative production-registration proof and keep the unit test as provider compatibility only.

### Plan 03 — Audit and action schema

Strengths

- The audit is reproducible and explicitly includes non-Go policy sources, migrations, attribute producers, and compiler-construction sites.
- It correctly distinguishes the fourth site: `abactest.NewSeedEngine` uses a real registry but lacks `action`, as shown at `internal/testsupport/abactest/abactest.go:71`.
- The five-key schema matches current production vocabulary: resolver-owned `name`, shipped `dispatch_location`, and the three planned `job.trigger_*` keys.
- The plan correctly forbids reserving `dispatch_location`; `NewAccessRequest` applies the same reserved-key check to all supplied attributes at `internal/access/policy/types/types.go:143`.

Concerns

- **LOW — line-count equality is brittle as specified.** Comparing raw compiler-search line count with manually counted Markdown table rows can be thrown off by table headers or wrapped cells. This is a review-process weakness, not an implementation flaw.
- **LOW — direct registration's "no observable behavior" statement should be tightly scoped.** It has no compile-validation effect before Plan 04; it can still affect schema introspection tests or future code reading that registry.

Suggestions

- Put compilation-site paths in a machine-readable fenced list and compare sorted path sets, not counts.
- Phrase the no-op statement as "no production policy-compilation behavior changes until Plan 04."

### Plan 04 — Compiler/schema wiring

Strengths

- All four current non-test compiler sites are covered: production stack `internal/access/setup/setup.go:150`; bootstrap installer `internal/bootstrap/setup/subsystem.go:190`; real-ABAC integration harness `internal/testsupport/integrationtest/real_abac.go:45`; unit seed engine `internal/testsupport/abactest/abactest.go:68`.
- Moving initial reload after provider and action registration fixes the real boot/steady-state divergence. Currently reload runs at `internal/access/setup/setup.go:155`, before the registry exists at line 160.
- `Cache.Reload` already names the policy and ID in compilation failures at `internal/access/policy/cache.go:147`; adding the offending key in the compiler error yields an actionable boot failure.
- Registering `action` in `abactest.NewSeedEngine` is particularly valuable because it moves malformed seed detection into ordinary unit tests.

Concerns

- **MEDIUM — the same oops traversal terminology problem affects the proposed compiler tests.** Wrapping the compiler error inside `Cache.Reload` with `fmt.Errorf("%w")` preserves the inner oops value, but `oops.AsOops(err).Code()` demonstrates the deepest code, not necessarily the outer boundary. This does prove the compiler code survives wrapping; it does not prove absence of an outer coded wrapper.
- **LOW — Task 3 Test 4 cannot literally prove `NewSeedEngine` rejects an arbitrary extra policy.** `NewSeedEngine` accepts providers, not policy text, and always loads the fixed `policy.SeedPolicies()` corpus at `internal/testsupport/abactest/abactest.go:78`. The plan's proposed reconstruction of "the same registry shape" tests the underlying registration but not the exported helper against a synthetic bad policy.

Suggestions

- Split the site-4 proof into: a same-package test confirming the helper's constructed registry has `action`; and a corpus regression proving `NewSeedEngine` still loads all shipped seeds.
- Do not claim that a synthetic bad policy was driven through `NewSeedEngine` unless the helper gains an injectable policy-store seam, which would probably be unnecessary scope.

### Plan 05 — Invariant, documentation, roadmap amendment

Strengths

- The documentation obligations are appropriately treated as phase deliverables.
- The `SystemCaller()` enumeration is correctly updated for the Phase 02.1 caller model.
- The upgrade note includes the operator pre-flight query and remedy, making D-67's accepted risk operationally visible.
- The scoped ROADMAP edit and before/after milestone-filter check are careful safeguards around a tool-owned file.

Concerns

- **HIGH — the proposed invariant claims a consumer-boundary property its bindings do not prove.** The proposed `INV-ACCESS-13` says `action.job.trigger_subject` is "stamped at the consumer boundary from the delivered message" and independently derived from the handler resource. Plan 01's test constructs `world.JobCaller` directly and immediately invokes `world.Service`; it contains no JetStream message, consumer wrapper, or handler boundary. The existing test helper similarly constructs callers directly at `internal/world/caller_test.go:271`. This would repeat the false-binding failure the plan explicitly says it is avoiding.
- **HIGH — Plan 05 contradicts locked D-68 for the flusher.** D-68 says every background consumer gets a `job:` identity and specifically concludes that Phase 3's flusher "takes an identity but no per-execution attributes." Plan 05 instead says the flusher "needs no job identity" and its final output says it "takes neither unless it starts to" cross a chokepoint. That is option A alone, not D-68's locked A+D result.
- **MEDIUM — the invariant's declared-capability clause may overstate what the proposed binding proves.** The seed-smoke mismatch test proves the fixture seed reads `principal.job.writes`; it does not establish that every future job seed must do so. The invariant should be explicitly fixture/model-contract scoped unless a meta-test enforces that all `principal is job` seeds contain the capability conjunct.
- **LOW — external issue creation makes the plan non-autonomous in practice.** Filing GitHub issues and an upstream GSD issue requires network/authentication and creates external state. The plan is marked autonomous and does not specify what happens if `gh` is unavailable.

Suggestions

- Narrow `INV-ACCESS-13` to what this phase actually proves: job subject construction; liveness-gated provider attributes; fixture policy consuming declared writes; typed event provenance matching a resource ID; scheduled callers carrying no provenance. Treat "stamp at the consumer boundary before handler logic" as a Phase 3 invariant/binding when a real consumer wrapper exists.
- Rewrite every flusher statement to match D-68: it registers a job identity and declared writes but supplies no per-execution provenance. Its current out-of-world write may not consume that identity at an ABAC check, but the background consumer still participates in the registry lifecycle.
- Either add a meta-test enumerating all job seeds and requiring a declared-capability condition, or phrase the invariant as "the shipped fixture seed requires…".
- Make external issue filing a checkpoint or permit recording a deferred issue draft when credentials/network are unavailable.

## Risk Assessment

**Overall risk: HIGH until revised.** The core implementation architecture is sound and security-conscious. The high rating comes from two execution blockers: Plan 01 contains mutually incompatible expected key sets; Plan 05 would create a bound invariant that claims an untested boundary and would document behavior contrary to locked D-68. After those corrections, the implementation risk would fall to medium, driven mainly by the one-way boot-time validation flip and the knowingly accepted risk around operator-authored policies.

### O-1 [HIGH] `oops.AsOops(err).Code()` does not compile, and its stated rationale is inverted

Prescribed three times: `02.2-02-PLAN.md:188`, `02.2-02-PLAN.md:245`, `02.2-04-PLAN.md:163`.
Three separate defects, all verified:

1. **It does not compile.** `oops.AsOops` returns `(OopsError, bool)` —
   `~/go/pkg/mod/github.com/samber/oops@v1.22.0/helpers.go:34-38` (`go.mod:31` pins v1.22.0).
   Every one of the ~20 call sites in this repo uses the two-value form
   (`pkg/errutil/testing.go:17`, `cmd/holomush/cmd_admin_read_stream.go:189`, …). The single-value
   spelling is `multiple-value in single-value context`.
2. **`Code()` returns the DEEPEST code, not the top-level one.**
   `oops@v1.22.0/error.go:233-235` → `return getDeepestErrorCode(o)`; `:237-247` recurses into
   `err.err` and prefers the child's code. Codex flagged this at MEDIUM against
   `.claude/rules/grpc-errors.md:58`; the library source settles it in codex's favour.
3. **The two forms the plans contrast are the same call.** `errutil.AssertErrorCode`
   (`pkg/errutil/testing.go:15-21`) is literally `oops.AsOops(err)` + `assert.Equal(code, oopsErr.Code())`.
   So the plans' claim that the direct form is a stronger, non-chain-walking assertion than the
   helper is **false** — identical semantics.

**Why HIGH, not MEDIUM.** The compile error self-corrects at first `task test`. The durable harm is
what happens next: the executor repairs the spelling, lands the assertion, and believes it has
pinned a top-level-code opacity contract on the phase's load-bearing instance-scoping deny
(`02.2-02-PLAN.md:245` — "instance scoping is the phase's load-bearing claim"). It has pinned
nothing of the sort. Root cause is a pre-existing defect in `.claude/rules/grpc-errors.md:58-70`,
which the plans faithfully copied; that rule should be corrected in the same change.

### O-2 [MEDIUM] Plan 04 states a false mechanism for the provider-namespace skip, and prescribes writing it into production source

`02.2-04-PLAN.md:280` justifies Test 3 with "`HasNamespace("character")` is false there".
The compiler never looks up `"character"`. `collectFromExpr` (`internal/access/policy/compiler.go:240-247`)
and `collectFromCondition` (`:207-220`) set `namespace = <the DSL ROOT>`, which the grammar
constrains to `principal | resource | action | env` (`internal/access/policy/dsl/ast.go:163`, `:175`).
So `resource.character.roles` is validated as namespace `"resource"`, key `"character.roles"`.
Confirmed by the shipped test fixture, which registers a schema namespace literally named
`"resource"` (`internal/access/policy/compiler_test.go:378-385`).

Consequences:

- The `action` gate works **exactly** as the plans design it — `action` IS a grammar root, so
  registering it makes `HasNamespace("action")` true and the hard-error branch live. No change needed.
- But provider namespaces (`character`, `location`, …) can **never** be validated by the compiler on
  **any** registry. Plan 04's asymmetry claim — "the FATAL behavior is uniform across sites, the
  WARNING behavior is not" — is false: WARN never fires for provider namespaces anywhere, on any
  site. Site 1's full-registry wiring is therefore *safer* than the plan assumes (it can introduce
  no new provider-namespace warnings), but for a different reason than stated.
- `02.2-04-PLAN.md:312` instructs the executor to write that false claim into
  `internal/bootstrap/setup/subsystem.go` as a durable comment.

pi reached the same *behavioural* conclusion from `compiler.go:154` (`gsd-review-pi.md:21`) without
naming the cause; this finding supplies the mechanism.

Latent, out of scope but worth a line in the SUMMARY: `environmentProvider.Namespace()` returns
`"env"` (`internal/access/policy/attribute/environment.go:29-31`) — a grammar root. It is not
registered in `BuildABACStack` today, but if it ever is, `HasNamespace("env")` flips true and
`env.*` refs begin to be validated.
