## 0. What actually determines the DECLARE set

`validateAttributes` walks **policy TEXT**, not producers:

```go
for _, ref := range refs {            // refs come from collectAttrRefs(conditionBlock)
    if !c.schema.HasNamespace(ref.namespace) { continue }
    if c.schema.IsRegistered(ref.namespace, ref.key) { continue }
    fqn := ref.namespace + "." + ref.key
    if ref.namespace == "action" {
        return nil, fmt.Errorf("unregistered action attribute %q: ...", fqn)
    }
    ...
}
```
`[VERIFIED: internal/access/policy/compiler.go:149-171]`

Two consequences that shape every verdict below:

1. **A key that is PRODUCED but never REFERENCED by any policy cannot fail a compile.** Caller-supplied
   attributes reach `bags.Action` through the engine overlay (`engine.go:263`), which never consults
   the schema registry. So "something produces it" is **not** a reason to declare.
2. **A key that is REFERENCED by any compiled policy MUST be declared**, or that compile hard-errors
   once plan 04 lands. This is the only criterion that matters for boot safety.

`ref.key` is `strings.Join(c.Path, ".")` (`compiler.go:210,218,245`) and the fqn is composed as
`ref.namespace + "." + ref.key` (`compiler.go:161`), while `IsRegistered(ns, key)` is an **exact map
lookup**. Therefore a dotted key such as `job.trigger_subject` **MUST be a single literal map key**
containing the dot — `Attributes["job.trigger_subject"]`, never a nested namespace. (Research
assumption **A3**, confirmed here.)

## 4. `reservedActionKeys` was NOT widened

`internal/access/policy/types/types.go:108-110` still contains exactly one entry, `"name"`, and this
plan did not touch that file.

**Widening it would be a shipped-behavior regression, not a hardening.** `IsReservedActionKey` is
consulted by `NewAccessRequest` (`types.go:154`), and the host's own plugin scope fence routes its
attributes through that same constructor at **`internal/plugin/pluginauthz/capability.go:50`**
(`types.NewAccessRequest(in.Subject, in.Action, in.Resource, in.Context)`), where `in.Context` is the
`{"dispatch_location": …}` map built at `internal/plugin/hostcap/interceptor.go:294`. Adding
`dispatch_location` to the denylist would therefore make every scope-eligible plugin capability call
return `ACCESS_REQUEST_RESERVED_ATTRIBUTE`, breaking `seed:plugin-world-mutation-own-location` and
INV-PLUGIN-50/52.

Declaring a key in the **schema** (what this plan does) and reserving it on the **supply side** (what
`reservedActionKeys` does) are opposite operations. Do not confuse them.

## 7. The audit's honest limit, and the operator pre-flight (D-67 obligation)

**This audit cannot be exhaustive over operator-authored policies.** Rows in the `policies` table are
compiled through the *same* `policy.Compiler` at `cache.Reload`, so they are subject to the *same*
`action` hard-error branch — but they live in a deployment's database, not in this repository, and
cannot be enumerated from the tree by any means.

D-67 **knowingly accepts** this (research assumption **A1**, the highest-severity assumption in the
research document). The compensating control is that every deployment can answer the question for
itself, **before** upgrading:

```sql
SELECT id, name, dsl_text FROM policies WHERE dsl_text LIKE '%action.%';
```

**Every `action.<key>` appearing in any returned row MUST be a member of the declared set below, or
that deployment will fail to boot after the plan 02.2-04 wiring change lands.**

```text
action.name
action.dispatch_location
action.job.trigger_event_id
action.job.trigger_event_type
action.job.trigger_subject
```

A row returning `action.event_type`, `action.plugin_name`, `action.plugin_inst`, or anything else is
an **actionable finding**: either the policy is edited to stop referencing the key, or the key is
added to `ActionNamespaceSchema()` and the binary rebuilt. There is no third option and no runtime
override.

## 8. The upgrade-risk statement

> **Upgrade risk (knowingly accepted by D-67).** After Phase 02.2 lands, the ABAC policy compiler
> validates `action.*` attribute references against a declared schema, and an undeclared reference is
> **fatal for every policy source** — in-tree seeds and operator-authored database rows alike. A
> deployment carrying an operator-authored policy that references an `action.*` key outside the
> declared set (`name`, `dispatch_location`, `job.trigger_event_id`, `job.trigger_event_type`,
> `job.trigger_subject`) **will fail to boot on upgrade**. The remedy is an operator edit to the
> offending `policies` row; run the pre-flight query in §7 **before** upgrading to identify any such
> row. This behaviour was chosen deliberately in preference to the alternative — a typo'd `action.*`
> reference silently default-denying — which is the same fail-closed posture the rest of the ABAC
> stack takes.

This paragraph is the wording the phase SUMMARY and the release notes reuse (plan 02.2-05 owns the
release-note callout).
