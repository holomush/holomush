  a job that is not running resolves to `nil, nil`, so no attributes are stamped and any

  that makes the provider fail closed. The provider MUST NOT emit sentinel values for an

  that is acceptable because **the declaration narrows; the seed grants** — both gates must pass.

## Summary

Phase 02.2 is composition on an ABAC substrate that is **more capable than the roadmap assumed in
one dimension and materially less wired than it assumed in another.**

The capable dimension: everything D-48/D-49/D-54/D-57 need already exists and was re-verified on
this tree. `job:retirement` parses as an entity ref, matches `principal is job` and nothing else in
the target clause, resolves through the ordinary provider loop, and can be liveness-gated by a
15-line provider copied from `PluginProvider`. The DSL grammar accepts a three-segment
`action.job.trigger_subject` path and the evaluator joins it to bag key `"job.trigger_subject"`.
02.1 landed the carrier: `checkAccess` forwards `caller.attrs` to `types.NewAccessRequest`, and
the engine overlays those onto `bags.Action`.

The unwired dimension is the phase's biggest risk and it **falsifies the mechanism (not the intent)
behind D-59 and success criterion 3.** Every production policy-compilation path in this repo builds
its `Compiler` on a **freshly-allocated, never-populated `types.AttributeSchema`** that is a
different object from the `attribute.SchemaRegistry` the providers register into. There are three
such sites, all verified. Consequently `validateAttributes` — including its `action`-specific
hard-error branch — **cannot fire in production today**. Registering the `action` namespace at
D-60's insertion point is therefore a **no-op on the current tree**: it changes neither compile
validation (the compiler never sees that registry) nor runtime merging (the caller-attribute
overlay bypasses `mergeAttributes` entirely). The `seed.go:332` "landmine" does not exist as
described — and neither does the benefit criterion 3 promises.

The second material finding: the `reservedActionKeys` denylist hole reported in the roadmap is
**real in shape but not reachable today**, and — critically — **cannot be closed by adding
`dispatch_location` to the denylist**, because the one production producer of that key routes
through the same `NewAccessRequest` precondition the denylist enforces. A naive fix breaks a
shipped scope fence.

**Primary recommendation:** treat "wire the production compiler to the provider schema registry
(all three sites), in the correct order relative to `cache.Reload`" as a **first-class, separately
committed task of this phase**, gated behind the complete `action.*` audit below — because it is
the only way success criterion 3 can be honestly met, and because it converts a currently-dead
validation path into a live boot-time gate for the whole repo. If the maintainer declines that
scope, criterion 3 MUST be reworded to what registration alone actually delivers, and the phase
must not claim compile-time typo protection it does not have.

## Answers to the Five Flagged Open Questions

### Q1 — `IsReservedActionKey` / reserved-key interaction

**The reserved list, verbatim** `[VERIFIED: internal/access/policy/types/types.go:102-120]`:

```go
var reservedActionKeys = map[string]struct{}{
	"name": {},
}

func IsReservedActionKey(key string) bool {
	_, ok := reservedActionKeys[key]
	return ok
}
```

**Exactly one key is reserved: `"name"`.** `action.dispatch_location` is **not** on the list —
the roadmap's claim is **CONFIRMED**.

Enforcement fires at **two** places, both with identical semantics:
1. Constructor precondition — `NewAccessRequest` returns
   `oops.Code("ACCESS_REQUEST_RESERVED_ATTRIBUTE")` for a colliding key
   `[VERIFIED: types.go:153-159]`.
2. Engine defense-in-depth — for a hand-built `AccessRequest` literal that bypassed the constructor
   `[VERIFIED: internal/access/policy/engine.go:243-250]`.

So a caller-supplied `action.name` is **rejected outright**, not silently overwritten. Any
*non*-reserved caller key **wins on conflict** by overlay order (`engine.go:257-265`, which runs
after `Resolver.Resolve` has already written `bags.Action["name"]`).

**Is the hole reachable today? NO.** The complete set of production `NewAccessRequest` call sites
that pass a non-nil `attrs`:

| Call site | attrs source | Reachable by an untrusted party? |
|---|---|---|
| `internal/world/service.go:216` | `caller.attrs` | **No.** Both exported `Caller` constructors leave `attrs` nil (`caller.go:73-75`, `:88-90`); the field is unexported, and the only writers are same-package composite literals + `internal/world/export_test.go` (test binary only). `[VERIFIED: internal/world/caller.go:39-90]` |
| `internal/plugin/pluginauthz/capability.go:50` | `in.Context` | **No.** The single production populator is `internal/plugin/hostcap/interceptor.go:294`, `scopeAttrs = map[string]any{"dispatch_location": dc.Attributes["location"]}`, where `dc` comes from `pluginauthz.DispatchForHost(ctx)` — a context key only `WithDispatch` writes, and `dispatchwire.AttachOutgoing` *strips* any plugin-injected metadata before re-attaching the host-vouched envelope. `[VERIFIED: interceptor.go:268-295; pluginauthz/dispatch.go:29-45; dispatchwire/dispatchwire.go:56-84]` |

Every other production `NewAccessRequest` call passes literal `nil`
`[VERIFIED: rg 'NewAccessRequest\(' --glob '*.go' -g '!*_test.go'` → 11 sites, 9 of them `nil`].

**The trap: you cannot close this with a denylist entry.** `interceptor.go:294` → `capability.go:50`
→ `NewAccessRequest(…, in.Context)` runs the *same* `IsReservedActionKey` loop. Adding
`"dispatch_location"` to `reservedActionKeys` would make the host's own scope fence return
`ACCESS_REQUEST_RESERVED_ATTRIBUTE` on every scope-eligible plugin capability call, breaking
`seed:plugin-world-mutation-own-location` (INV-PLUGIN-50/52). **This is a shipped-behavior
regression, verified by reading both ends of the chain.** `[VERIFIED: capability.go:50 + types.go:153-159]`

**Allowlist evaluation.** A denylist is unbounded by construction; the roadmap is right about that.
A supply-side allowlist is *cheap today* — the total legitimate caller-supplied key set is
`{dispatch_location}` plus this phase's three `job.*` keys. But an allowlist at `NewAccessRequest`
does not distinguish **host-vouched** from **caller-asserted** — both channels are the same
parameter — so it prevents *typos and new keys*, not *self-assertion by a future attrs-carrying
caller*. The structurally correct fix is a **second, host-only attribute channel** (e.g. an
unexported field populated by a `types.NewHostVouchedAccessRequest` in the same package, or a
`vouched map[string]any` alongside `Attributes`), which is a substrate change larger than this phase.

**SCOPE VERDICT (required deliverable):** the `reservedActionKeys` denylist hole is
**PARTIALLY IN SCOPE**, split as follows, with evidence:

| Item | In scope for 02.2? | Evidence |
|---|---|---|
| Ensure `JobCaller` cannot emit a non-`job.`-prefixed key (constructor-enforced prefix, no arbitrary-map parameter) | **YES — mandatory** | D-56's own rationale: "the `job.` keys are produced in exactly one place." This is the phase's own new attrs producer; letting it take an arbitrary map re-opens the hole this phase is adding surface to. |
| Add `dispatch_location` to `reservedActionKeys` | **NO — would regress production** | `capability.go:50` routes the host-vouched value through the same check (verified above). |
| Convert the denylist to a supply-side allowlist | **DEFER — belongs elsewhere** | It touches the `types` package contract for every caller, delivers no defence against the actual (future) self-assertion vector, and is not needed for AUTHZ-02. Recommend filing a GitHub issue. |
| Introduce a separate host-vouched attribute channel | **DEFER — belongs elsewhere** | Substrate redesign of `AccessRequest`; blast radius spans `internal/plugin/hostcap`, `pluginauthz`, `world`, and the engine. Recommend filing a GitHub issue referencing this section. |

### Q2 — `warnOnMissingSeedCoverage` / `RegisteredNamespaces()` coupling, and the complete `action.*` audit

#### F1 (BLOCKING FINDING) — the production compiler's schema is orphaned

`validateAttributes` behaves exactly as the roadmap describes — **when it has a populated schema**
`[VERIFIED: internal/access/policy/compiler.go:145-170]`:

```go
for _, ref := range refs {
	if !c.schema.HasNamespace(ref.namespace) {
		continue
	}
	if c.schema.IsRegistered(ref.namespace, ref.key) {
		continue
	}
	fqn := ref.namespace + "." + ref.key
	if ref.namespace == "action" {
		return nil, fmt.Errorf("unregistered action attribute %q: action namespace is registered but attribute is not", fqn)
	}
	warnings = append(warnings, ValidationWarning{...})
}
```

But `c.schema` is never populated in production. Three verified sites:

| # | Site | Code (verbatim) | Effect |
|---|------|-----------------|--------|
| 1 | `internal/access/setup/setup.go:150-151` (inside `BuildABACStack`, the production stack builder) | `schema := types.NewAttributeSchema()` / `compiler := policy.NewCompiler(schema)` | The cache-reload compiler. `schemaReg := attribute.NewSchemaRegistry()` is allocated *separately* at `:160`, and `NewSchemaRegistry()` calls `types.NewAttributeSchema()` internally (`attribute/schema.go:21-25`). `schema` is never referenced again in the 433-line file. |
| 2 | `internal/bootstrap/setup/subsystem.go:192-193` (`policyBootstrapFn`, the seed installer) | `schema := types.NewAttributeSchema()` / `compiler := policy.NewCompiler(schema)` | Seeds are compiled against an empty schema at bootstrap. |
| 3 | `internal/testsupport/integrationtest/real_abac.go:48` | `policy.NewCompiler(policytypes.NewAttributeSchema())` | The `WithRealABAC()` harness seeds the same way. |

`[VERIFIED: internal/access/setup/setup.go:138-161,345-418; internal/bootstrap/setup/subsystem.go:186-197; internal/testsupport/integrationtest/real_abac.go:44-52; internal/access/policy/attribute/schema.go:20-25]`

Only **two** places in the repo wire the compiler to a populated registry, and both are hand-built
integration suites with their own provider sets:
`test/integration/access/access_suite_test.go:214` and `test/integration/world/world_suite_test.go:243`
(`policy.NewCompiler(registry.Schema())`). The unit-test engine helper
`createTestEngineWithPolicies` also uses a fresh empty schema
(`internal/access/policy/engine_test.go:907-908`), which is why every seed-smoke test compiles the
whole seed corpus without ever exercising `validateAttributes`.

**Three consequences the planner MUST honor:**

1. **D-59's landmine is FALSE on this tree.** Registering `action` at D-60's insertion point does
   not turn `seed.go:332` into a boot-time error, because `BuildABACStack`'s compiler and
   `policyBootstrapFn`'s compiler never see that registry.
2. **A bare D-60 registration is a complete no-op.** It affects neither compile validation (F1) nor
   runtime attribute merging: `mergeAttributes` (`resolver.go:489-504`) is the only registry
   consumer at runtime and it is called **only from `resolveEntity`/`resolveEnvironment`** for
   *provider*-returned attributes. Caller-supplied action attributes bypass it entirely via the
   engine overlay (`engine.go:252-265`). No provider owns `action` (that is D-60's whole premise),
   so `mergeAttributes` is never invoked with namespace `"action"`.
3. **Success criterion 3 is not achievable by registration alone.** "a typo'd `action.*` reference
   is a compile-time failure rather than a silent default-deny" requires fixing sites 1 and 2 (and
   arguably 3) to pass `schemaReg.Schema()` to `NewCompiler`.

**And that fix has its own ordering trap.** In `BuildABACStack`, `cache.Reload(ctx)` (which compiles
every stored policy) runs at **line 156**, *before* the providers register their schemas at lines
163-321. Wiring the compiler to `schemaReg` without moving the reload would compile the boot
snapshot against a still-empty registry and every *subsequent* reload (poller / invalidation hook)
against a populated one — different validation behaviour at boot vs. steady state, which is worse
than the current uniform no-op. `[VERIFIED: internal/access/setup/setup.go:154-157 vs :163-321]`

**Blast radius if the wiring is fixed.** It is *not* limited to `action`. Once the compiler sees the
registry, **every** registered namespace becomes validated: `resource.<ns>.<undeclared-key>`
becomes a non-fatal `ValidationWarning`, and `action.<undeclared>` becomes a **hard error that
fails `cache.Reload`, which fails `BuildABACStack`, which fails boot.** The audit below is
therefore mandatory before any wiring change.

**The universality claim in success criterion 4 is FALSE for the timer-driven class as written.**
Confirmed: `trigger_event_id` / `trigger_event_type` / `trigger_subject` are, by D-54, "taken

`[CITED: .planning/phases/03-world-character-commands/03-RESEARCH.md:211-224, :716, :1106-1116;
.planning/phases/03-world-character-commands/03-05-PLAN.md:100,142]`
`[VERIFIED: docs/architecture/invariants.yaml:5065-5085 — INV-WORLD-4 enumerates exactly THREE
sanctioned out-of-world writers today; Phase 3 amends it to FOUR]`

Phase 3 plan 03-05 has already **reserved** this decision and forbidden itself from resolving it:
> *"if 02.2's landed model answered the timer-driven-job question, follow that answer exactly;
> otherwise ship the flusher WITHOUT job-registry participation and record the still-open question
> in the SUMMARY. Never invent a trigger_kind or tick-provenance shape (Pitfall 12)."*
`[VERIFIED: 03-05-PLAN.md:100]`

### Q5 — How a `job:` principal parses, and whether it is genuinely disjoint

The parse chain for a subject `"job:retirement"`, in evaluation order:

1. **`Engine.Evaluate` step 2, S1 gate** `[VERIFIED: engine.go:91-105]`:
   `if req.Subject == "system"` — **exact string equality**, no prefix match. `"job:retirement"`
   never enters the bypass branch. (Note the shape: a bare `"system"` *without*
   `access.IsSystemContext(ctx)` is a hard `SYSTEM_SUBJECT_REJECTED`, and a prefixed
   `system:bootstrap` is normally policy-evaluated — which is exactly why the synthetic
   `system:retirement` was rejected in D-45/D-48.)
2. **`validateRequest`** at `engine.go:157` → `:550-566`: requires `strings.SplitN(req.Subject, ":", 2)`
   to yield a non-empty type and a non-empty id. `job:retirement` ✅; a bare `job` ❌
   (`INVALID_ENTITY_REF`).
3. **`Resolver.Resolve`** → `validateEntityRef` (`attribute/resolver.go:336-344`), same `type:id`
   rule; then `bags.Subject["id"] = req.Subject[idx+1:]` → **`principal.id == "retirement"`**
   `[VERIFIED: resolver.go:195-198]`.
4. **`resolveEntity`** (`resolver.go:350-397`) iterates **every** registered provider with the
   **full ref** and merges whatever each returns. A provider self-filters; `PluginProvider` does so
   by asking its registry (`plugin_provider.go:40-48`). A job provider does the same.
5. **`mergeAttributes`** (`resolver.go:489-504`) writes `bag["job."+key]` **only if**
   `registry.IsRegistered("job", key)` — an unregistered key is dropped with a WARN and a
   `rejectedAttributesCounter` increment. **The job provider's `Schema()` is load-bearing, not
   documentation.**
6. **`findApplicablePolicies`** (`engine.go:352-389`) compares `parseEntityType(req.Subject)`
   against `target.PrincipalType`. `parseEntityType` (`engine.go:542-548`) returns the substring
   before the first `:` — `"job"`.
7. **DSL target grammar**: `PrincipalClause` is `'principal' ('is' @Ident)?`
   `[VERIFIED: internal/access/policy/dsl/ast.go:86-88]` — any identifier, so `principal is job`
   parses.

**Disjointness verdict: `job:` IS genuinely disjoint from `system`, and the D-48 rationale holds
exactly as written.**
- `principal is system` and `principal is job` can never both match one subject —
  `parseEntityType("job:retirement") == "job"` ≠ `"system"`, and `parseEntityType("system") == ""`
  (no colon) so the two shipped `principal is system` permits (`seed.go:206-217`) never match a
  `job:` subject either.
- **The precise, non-obvious half:** prefix-only matching means `principal is job` grants **every**
  `job:*` subject, exactly as `principal is system` grants every `system:*`. D-48 does not fix that
  and does not claim to — what it fixes is the *cross-family* leak (a job permit accidentally
  granting `system:bootstrap`). **Job-to-job separation is bought entirely by the `when` clause**
  (`principal.job.name`, `principal.id`, and the D-54 provenance binding), not by the target clause.
  The planner MUST NOT write a bare `permit(principal is job, action in ["write"], resource is
  character);` — that is a blanket grant to every job present and future.

**Additional wiring the planner must not miss:** `internal/access/prefix.go` has no `SubjectJob`
constant and `knownPrefixes` (`:74-93`) has no `job:` entry. `knownPrefixes` feeds only
`ParseEntityRef` (`:290-322`), which has **zero production consumers**
`[VERIFIED: rg 'ParseEntityRef' --glob '*.go' -g '!*_test.go'` → declaration only], so omitting it
breaks nothing at runtime — but `TestKnownPrefixes_AllConstantsCovered`
(`internal/access/prefix_test.go:511`) asserts the list covers the constants, so a new
`SubjectJob = "job:"` constant **must** be added to `knownPrefixes` in the same change. A
`JobSubject(name string) string` constructor should follow the 4-for-4 panic-on-empty convention
(`prefix.go:97-121`).

### Pattern 1: Registry-gated principal provider (D-49)

**What:** an `AttributeProvider` whose `ResolveSubject` returns `(nil, nil)` unless a liveness
registry confirms the principal is currently running.
**When to use:** any non-entity principal whose authority should expire with its lifetime.
**Template** `[VERIFIED: internal/access/policy/attribute/plugin_provider.go:36-62]` — the shape to
copy, verbatim:

```go
func (p *PluginProvider) Namespace() string { return "plugin" }

func (p *PluginProvider) ResolveSubject(_ context.Context, subjectID string) (map[string]any, error) {
	if subjectID == "" {
		return nil, nil
	}
	if p.registry == nil || !p.registry.IsPluginLoaded(subjectID) {
		return nil, nil
	}
	return map[string]any{"name": subjectID}, nil
}

func (p *PluginProvider) ResolveResource(_ context.Context, _ string) (map[string]any, error) {
	return nil, nil
}

func (p *PluginProvider) Schema() *types.NamespaceSchema {
	return &types.NamespaceSchema{
		Attributes: map[string]types.AttrType{
			"name": types.AttrTypeString,
		},
	}
}
```

⚠️ **Two things to get right that the template does not show:**
1. `ResolveSubject` receives the **full ref** (`"job:retirement"`), not the bare name —
   `resolveEntity` passes `entityRef` unmodified (`resolver.go:350,376`). The job provider MUST
   strip its own prefix (or its registry must key on the full ref) and MUST return `(nil, nil)` for
   a ref belonging to another namespace, because **every** provider is called for **every** ref.
2. `mergeAttributes` (`resolver.go:489-504`) silently drops any returned key not present in
   `Schema()`. D-50's `writes` list must be declared as `types.AttrTypeStringList` or it will never
   reach the bag.

### Pattern 2: Cross-bag instance scoping in a seed `when` clause (D-54)

**What:** compare a caller-supplied `action.*` value against a resolver-supplied `resource.*` value.
**Proof it parses and evaluates** — `Comparison.Left` / `Right` are both `*Expr`, and `Expr` may be
an `AttrRef` `[VERIFIED: dsl/ast.go:145-150, 208-222]`; the shipped precedent compiles and is
smoke-tested `[VERIFIED: seed.go:332 + seed_smoke_test.go:958-1002]`:

```go
// internal/access/policy/seed.go:332 — the shipped cross-bag precedent (verbatim)
DSLText: `permit(principal is plugin, action in ["write"], resource is location) when { resource.location.id == action.dispatch_location };`,
```

### Pattern 3: The provenance carrier is a typed constructor, never a map (D-56)

`world.Caller`'s `attrs` field is unexported and both existing constructors leave it nil
`[VERIFIED: internal/world/caller.go:39-90]`. `JobCaller` must follow: take a job **name** and a
**typed provenance struct**, and build the `job.`-prefixed keys internally. It MUST NOT take
`map[string]any` — that would hand every caller the ability to assert `action.dispatch_location`
(Q1's hole) through a brand-new door.

### Anti-Patterns to Avoid

- **Bare `permit(principal is job, …)` with no `when` clause** — prefix-only target matching makes
  that a blanket grant to every present and future job (Q5).
- **Emitting `""` for an unresolved optional attribute** — a fail-OPEN bug in this DSL
  (`.claude/rules/abac-providers.md`; ADR `holomush-9gtl`). Omit the key; emit a `has_X` witness.
- **Registering the `action` namespace and declaring it "done"** — F1: on this tree that is a no-op.
- **Adding `dispatch_location` to `reservedActionKeys`** — Q1: breaks the shipped plugin scope fence.
- **Claiming the model defends against malicious in-process code** — D-53 forbids it; INV-WORLD-6 is
  the repo's documented precedent for a registry summary claiming more than its binding proves.

## Common Pitfalls

### Pitfall 1: Believing the `action`-registration landmine (or its benefit)
**What goes wrong:** the plan schedules an "audit before the flip" task, flips, sees nothing change,
and marks criterion 3 satisfied.
**Root cause:** F1 — production compilers carry an orphaned empty schema.
**Avoid:** decide explicitly whether the wiring fix is in scope. If yes, fix all three sites AND the
`cache.Reload` ordering. If no, reword criterion 3.
**Warning sign:** a plan task whose verification is "`action` appears in the registry" rather than
"a deliberately-typo'd `action.bogus` seed fails boot."

### Pitfall 2: Fixing the compiler wiring without moving `cache.Reload`
**What goes wrong:** boot compiles against an empty registry, the first poller reload compiles
against a populated one — validation behaviour differs between boot and steady state, and a bad
policy passes boot then kills the first reload.
**Root cause:** `setup.go:154-157` (reload) precedes `:163-321` (provider registration).
**Avoid:** move the initial `cache.Reload` to after provider registration, or construct the compiler
lazily.
**Warning sign:** a diff that changes line 151 and nothing else.

### Pitfall 3: Widening `reservedActionKeys` and breaking the plugin scope fence
See Q1. **Warning sign:** any diff touching `types.go:108-110` without a corresponding change at
`pluginauthz/capability.go:50`.

### Pitfall 4: A job provider that answers for refs it does not own
**What goes wrong:** `resolveEntity` calls **every** provider for **every** ref, so a job provider
that does not check the prefix will try `IsJobRunning("character:01ABC")`, and worse, could stamp
`job.*` keys onto a character subject's bag.
**Avoid:** return `(nil, nil)` unless `strings.HasPrefix(ref, "job:")`.
**Warning sign:** a `ResolveSubject` with no prefix guard. Note `PluginProvider` itself relies on its
registry returning false for foreign refs — copy the *intent*, add the explicit guard.

### Pitfall 5: `Schema()` omissions silently swallowing D-50's capability class
`mergeAttributes` drops unregistered keys with a WARN, not an error. A `writes` list declared as
`AttrTypeString` instead of `AttrTypeStringList` still registers (the type check at
