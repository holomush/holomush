### Why sites 2 and 3 use an action-only registry, stated correctly

The compiler validates **by DSL ROOT**, never by provider name. `collectAttrRefs` sets `namespace` to the grammar root — constrained to exactly `principal | resource | action | env` — and `key` to the whole dotted remainder. So `resource.character.anything` is looked up as namespace `"resource"`, key `"character.anything"`; the mechanism is **not** `HasNamespace("character")`, and a provider name is never a namespace the compiler looks up at all.

Two consequences, and the second corrects an earlier framing:

1. `action` **is** a grammar root, so registering it makes the hard-error branch live — **identically at all four sites**. That is the whole point of the action-only registry: it is the correct scope, not a lossy substitute.
2. **Do NOT say "fatal is uniform across sites, WARN is not."** That is false. A provider namespace such as `character` can never be validated by the compiler on *any* registry at *any* site. WARN fires only for an unregistered KEY inside a REGISTERED ROOT — e.g. `resource.bogus` on a schema that carries a namespace literally named `"resource"` (`compiler_test.go`). Site 1's full-registry wiring is therefore *safer* than an earlier draft assumed, but for a different reason than that draft gave. Asserted directly by `TestActionOnlyRegistrySkipsEveryRootItDoesNotCarry`.

### The `DependsOn()` finding (Task 3 step 4) — confirmed, not assumed

**The ABAC stack IS fully built when `policyBootstrapFn` runs.** `internal/bootstrap/setup/subsystem.go`'s `DependsOn()` names `lifecycle.SubsystemABAC`, and the closure already calls `s.cfg.ABAC.PolicyStore()`, which **panics** unless `Prepare()` has run (`internal/access/setup/subsystem.go:221-226`; every accessor in that family guards on `s.stack == nil`). `Prepare()` is what calls `BuildABACStack`.

So a future change **could** switch site 2 to the real registry — but not today: `ABACSubsystem` exposes `AttributeResolver()`, not the registry, and `ABACStack` does not carry `schemaReg` at all. Adding that accessor was declined deliberately (see key-decisions): it would couple seed installation to provider-registration ordering across two subsystems for a namespace that depends on no repo, no pool and no provider.

**A related sequencing fact, unchanged by this plan but worth recording:** BuildABACStack's `cache.Reload` runs at ABAC `Prepare()`, *before* the bootstrap subsystem installs the seeds. On a first boot the policies table is empty, so that reload compiles zero policies and the seeds are first compiled by site 2 at install time. Site 2 carrying the gate is therefore what protects a first boot — the boot-time reload alone would not.

## 🔴 THE D-67 UPGRADE RISK — wording for plan 02.2-05's release notes

> **Upgrade risk (knowingly accepted by D-67).** After Phase 02.2 lands, the ABAC policy compiler validates `action.*` attribute references against a declared schema, and an undeclared reference is **fatal for every policy source** — in-tree seeds and operator-authored database rows alike. A deployment carrying an operator-authored policy that references an `action.*` key outside the declared set (`name`, `dispatch_location`, `job.trigger_event_id`, `job.trigger_event_type`, `job.trigger_subject`) **will fail to boot on upgrade**. The remedy is an operator edit to the offending `policies` row; run the pre-flight query below **before** upgrading to identify any such row. This behaviour was chosen deliberately in preference to the alternative — a typo'd `action.*` reference silently default-denying — which is the same fail-closed posture the rest of the ABAC stack takes.

Operator pre-flight, to be run **before** the upgrade:

```sql
SELECT id, name, dsl_text FROM policies WHERE dsl_text LIKE '%action.%';
```

Every `action.<key>` in any returned row must be a member of the declared set above. A row returning `action.event_type`, `action.plugin_name`, `action.plugin_inst`, or anything else is an actionable finding: either edit the policy or add the key to `ActionNamespaceSchema()` and rebuild. There is no third option and **no runtime override** — none was added, deliberately.
