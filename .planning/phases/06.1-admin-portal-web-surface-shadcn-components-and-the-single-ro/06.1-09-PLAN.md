<objective>
Close G-06.1-4. The parity guard plan 06.1-06 shipped is genuinely good: it holds
`adminProfileMaskablePaths` as a live symbol, compares the path set in both
directions, pins both cap VALUES to `world.MaxNameLength` /
`world.MaxDescriptionLength`, and asserts the per-path mapping — with anti-vacuity
preconditions running before any comparison.

One hole remains. `webCaps[path]` is assigned from the matched CONSTRUCTOR NAME
(`kind == "line"` yields `shortCap`, otherwise `longCap`), never from the
`maxBytes` the constructor emits. Change the `line` constructor to a fresh literal
and: the Go guard still reads `const SHORT = 100` and still maps every `line` path
to 100 — green; the surviving TS assertion sees one line cap and one prose cap
with the first smaller — green; the counter test asserts `0 of ${f.maxBytes}` and
self-echoes the wrong number — green. Every rendered counter reads a cap the
server does not enforce.

The SWAP case is already caught. Only an edit to the emitted VALUE escapes.

Purpose: ROADMAP criterion 3's cap half — the operator is warned at the boundary
the server actually refuses at.
Output: the guard reads the emitted `maxBytes` and resolves it, and refuses to
guess when it cannot.
</objective>
