## Criterion 3 — now MET (G-06.1-3 closed)

Plan 06.1-06's binding is real, and I checked it rather than taking the summary's word.

`internal/grpc/admin_characters_web_parity_test.go` holds the authority as a **live symbol**, not a transcription: it iterates `adminProfileMaskablePaths` (unexported, hence the test's placement in `package grpc`) and compares `world.MaxNameLength` / `world.MaxDescriptionLength` as live constants. Three distinct properties are pinned:

- **The path set, in both directions** (`:180-200`) — `missingFromClient` and `unknownToServer` are both asserted empty, so adding a path to either side alone fails.
- **The two cap values** (`:174-179`) — `assert.Equal(t, world.MaxNameLength, shortCap)` reads the Sheet's `const SHORT = 100` and the Go constant. A trailing comment naming the constant is no longer the only link.
- **The path→cap mapping, per path** (`:203-215`) — each client cap is compared against that entry's `field.maxBytes`, which is what catches a `line` that should have been a `prose`.

The anti-vacuity preconditions run **before** any comparison (`:122-149`): the file must exist, the declaration must parse (`require.Len(body, 2)`), at least one entry must parse (`require.NotEmpty(entries)`), both cap declarations must be found, both caps must be positive and distinct, and the server allowlist must be non-empty. Duplicate paths `t.Fatalf` rather than silently collapsing.

The self-echoing web-side assertion is **gone**. `EditCharacterSheet.svelte.test.ts:175-209` no longer carries a hardcoded copy of the path list; what remains are genuine internal invariants (one entry per path, unique non-empty flat wire names, exactly two caps partitioned by kind).

Run at HEAD: `go test -count=1 -run TestAdminEditableFieldsInTheWebSheetMatchTheServerMaskAllowlist ./internal/grpc/` → **exit 0**.

**Residue (G-06.1-4, minor).** The guard reads each per-path cap from the matched **constructor name** (`:162-167`), never from the emitted `maxBytes`. Editing `line` to `maxBytes: 90` leaves the Go guard green (it still reads `const SHORT = 100`) and the surviving TS assertion green (`90 < 4000`), while every rendered counter says "n of 90" and the server refuses at 100. The *swap* case is caught; the *value* case is not. This does not reopen the criterion's field-set clause, which is what criterion 3 words — it is a narrower hole in the new guard.

- **The census is non-vacuous over what it scans.** Both meta-tests run green at HEAD (`exit 0`), and the offender list is legitimately empty.

### Why the criterion still fails

The conversion changed the **unit** of one half and not the other.

Every emitted media condition is rem:

```
$ rg -o --no-filename '@media[^{]*(48rem|64rem)[^{]*' web/.svelte-kit/output/client/_app/immutable/assets/*.css | sort | uniq -c
   9 @media (width>=48rem)
   1 @media (width>=64rem)
   6 @media not all and (width>=48rem)
   3 @media not all and (width>=64rem)
$ rg -o --no-filename '@media[^{]*(767px|768px|1023px|1024px)[^{]*' <same>
(no output)
```

The JS half is `web/src/lib/hooks/mediaQuery.svelte.ts:5` — `'(min-width: 768px)'`, a px literal that does not move with the user's font-size preference. `rem` inside a media query resolves against the browser's *initial* font size, so the two halves are complements only at exactly 16px.

**Proven, not argued.** I launched Chromium under `@playwright/test` with `--blink-settings=defaultFontSize=N` at a 900px viewport:

| defaultFontSize | JS `(min-width: 768px)` | CSS `(width >= 48rem)` | agree |
|---|---|---|---|
| 16px | `true` | `true` | ✓ |
| 20px | `true` | `false` | ✗ |

At a 20px default the CSS boundary sits at 960px while JS stays at 768px. Across that 768–960px band the shell renders the phone layout (rail and `.adminnav-col` collapse to zero, the mobilebar appears, `CharacterTable` drops columns) while `EditCharacterSheet` renders `data-side="right"` — a phone-band shell with a desktop side sheet. The same split hits `ScenesShell.svelte`, where `{#if desktop.current}` (`:459`, px) and `md:hidden` (`:221`, rem) put both chrome variants on screen at once.

The code asserts the opposite in two places, and both are false: `EditCharacterSheet.svelte:196` ("the exact complement of this file's viewport rule at EVERY width") and `06.1-05-SUMMARY.md:45`.

### The two guard problems

The census does not merely fail to catch this. It **licenses** it and then **blocks the repair**.

1. **The exemption's rationale is false.** `web_phone_band_breakpoint_census_test.go:91-94` permits the one authored 768 because Tailwind "does not emit it to `:root`, so the JS side provably cannot read the token at runtime". The build says otherwise — `--breakpoint-md:48rem` and `--breakpoint-lg:64rem` sit inside the `:root,:host{…}` block of `0.THubD8Pl.css`. This is the single load-bearing sentence in the census, so it will be re-cited.

2. **The staleness check rejects the fix.** `:257` is `require.Positive(t, allowlistHits[path])`, and `allowlistHits` increments only on lines carrying `767|768|1023|1024` (`:79`, `:219-230`). Changing `DESKTOP_MEDIA_QUERY` to `'(min-width: 48rem)'` drops the count to zero and fails the census with *"its exemption is stale and must be removed"* — for both allowlisted files. Only the defective spelling satisfies the guard.

Additionally, `forbiddenViewportWidths` carries only px decimals, so a future hand-written `@media (min-width: 48rem)` — now the *visible* form of these breakpoints, and therefore the most likely future duplication — sails straight through.

### Why every existing proof missed it — the lesson

All five census RED-proofs recorded in `06.1-05-SUMMARY.md` and the whole 767/768/1023/1024 E2E sweep ran at a **16px root font size**, where rem and px are numerically identical. `web/playwright.config.ts` declares no font-size or launch-arg variation. The single axis along which the two halves can diverge was invisible to every one of them. The proofs were rigorous about *width* and silent about *unit*.

Any correct guard must therefore turn RED at a **non-16px root font size** — that is the axis the existing proofs cannot see.

## Gaps Summary

**Criterion 4 is not achieved, and the reason is narrower and sharper than in the previous round.** The phase did the hard, broad part of the work: sixteen CSS rules genuinely derive from Tailwind's own tokens, exactly one authored band number survives anywhere under `web/src`, both JS consumers route through one shared hook, and a real 767/768 boundary sweep now exists. What went wrong is a **unit mismatch introduced by the fix itself** — the CSS half became rem, the JS half stayed px — so the two halves diverge under any non-default browser font size, an ordinary accessibility setting. The census then compounds it twice: its exemption is justified by a claim about the build that the build contradicts, and its staleness assertion turns red on the one-line repair.

**Criterion 3 is achieved.** The Go↔TS parity guard is the real thing: it holds the server's allowlist as a live symbol, compares in both directions, pins both cap values to `world.MaxNameLength` / `world.MaxDescriptionLength`, and asserts the per-path mapping — with anti-vacuity preconditions running before any comparison. The self-echoing test is deleted. The one residue (a cap edited inside the constructor body escapes both guards) is a new, narrower hole, filed as G-06.1-4 rather than a reopening of G-06.1-3.

**Four gaps, one blocking.** G-06.1-2 (major) blocks criterion 4. G-06.1-4, G-06.1-5 and G-06.1-6 are minor durability items in the same guard family; none invalidates what the guards do cover.

**The transferable lesson:** every proof this phase produced was rigorous about *width* and silent about *unit*, because they all ran at 16px where the two are numerically identical. When a guard's job is to keep two expressions equal, the proof must vary every axis the expressions can differ on — not just the obvious one.
