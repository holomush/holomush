# Phase 06.1 Plan 09: Admin cap parity read from the emitted value (G-06.1-4) Summary

The parity guard now reads each path's client cap from the `maxBytes` expression the
`line`/`prose` constructor actually emits, resolves it against the Sheet's own pinned
`SHORT`/`LONG` declarations, and refuses to guess when it cannot resolve — so a number
typed inside a constructor body fails `task test` instead of being echoed into all seven
(or all six) counters that constructor builds.

## The hole, and that it was real

`webCaps[path]` was assigned from the matched constructor NAME: `kind == "line"` yielded
`shortCap`, anything else `longCap`. `shortCap` came from parsing `const SHORT = 100`.
Nothing anywhere asserted the constructors USED those constants.

This was demonstrated, not argued. With `maxBytes: SHORT` changed to `maxBytes: 90` in
the `line` constructor and `const SHORT = 100` left in place, the **pre-task guard exited
0**. Seven counters would have rendered a boundary the server does not enforce, with every
guard green.

## What was built

**Task 1 — the guard reads what is emitted (`ce6b6633c`).**
Two regexes joined the existing four: `adminSheetCtorRe` captures each single-expression
arrow constructor's name and body, `adminSheetMaxBytesRe` captures a `maxBytes:`
right-hand side up to the next comma or brace. A `consts` table maps `SHORT`/`LONG` to the
already-parsed declaration values, and `resolveAdminSheetCap` turns an expression into a
number: a bare identifier in the table, or a digits-only literal. Anything else is a
`t.Fatalf` naming the constructor and the verbatim expression and saying the guard will
not guess a cap it cannot read.

Anti-vacuity for the new parse runs before any comparison: each matched constructor must
carry a `maxBytes` property (`require.Len`), both `line` and `prose` must be present
(`require.Contains`), and the two resolved values must differ (`require.NotEqual`) — the
same reason the two declarations must differ. The entry loop then looks up
`ctorCaps[kind]`; a constructor with no resolved cap is a `t.Fatalf` naming it.

Every existing assertion was kept. `assert.Equal(t, world.MaxNameLength, shortCap)` still
pins the DECLARATIONS; what is new is that the constructors are pinned to those
declarations too. The doc comment's "THREE things" list became four, and
`# What it does NOT cover` now says plainly that this compares declarations rather than
rendered output and names what closes that half: the Sheet's own suite for per-field
counter rendering, and the byte-cap block of `web/e2e/admin-portal.spec.ts` for the unit
in a browser. The ordering paragraph was left as it was, being already correct.

**Task 2 — the contract comment at the point of edit (`63c901ad5`).**
The comment above `SHORT`/`LONG` now names BOTH enforced relationships — the declarations
pinned by value, and each constructor required to emit one of the two identifiers — and
says what a number typed in place of `SHORT` costs. It opens with the unit: every cap here
is a BYTE count, the same unit the Go constants enforce and the counter measures, which is
why a short-looking multi-byte value can be over the cap. The surrounding `EditableField`
doc block's still-correct paragraphs (the set is the server's, the wire order, the two caps
disagreeing on purpose) were left alone.

  `test(...)`.

**2. [Rule 2 — Missing correctness] `isDecimalLiteral` added beside `strconv.Atoi`**
- **Found during:** Task 1
- **Issue:** the plan says "a string of decimal digits resolves to itself via
  `strconv.Atoi`". `Atoi` alone also accepts `-5` and `+100`, so a signed expression would
  have resolved silently to a nonsense cap instead of reaching the refuse-to-guess branch.
- **Fix:** a digits-only predicate gates the `Atoi` call, so only the shape the plan names
  resolves and everything else fails loudly.
- **Files modified:** `internal/grpc/admin_characters_web_parity_test.go`
- **Commit:** `ce6b6633c`

## Notes for the verifier

- **The chain is now closed end to end, across three artifacts, none of which duplicates
  another.** `world.MaxNameLength`/`MaxDescriptionLength` → `SHORT`/`LONG` (pinned by value
  in the Go guard) → the emitted `maxBytes` (parsed and resolved, new here) → the rendered
  counter (asserted per field by `EditCharacterSheet.svelte.test.ts`) → the unit is bytes
  (proven in a browser by the byte-cap block of `web/e2e/admin-portal.spec.ts`). The
  `must_haves` backstop row cites that e2e block rather than minting a second proof.
- **Declaration ORDER remains deliberately unasserted.** The guard compares path SETS and
  per-path caps, so the Sheet may reorder its form freely; the order it uses is the wire's
  own. The doc comment says so and this plan did not touch that paragraph.
- **The `unknown constructor` Fatalf is currently unreachable via the entry regex**, which
  admits only `line|prose`. It is the assertion that fires when a future change widens that
  regex without extending cap resolution — the realistic order in which a third constructor
  arrives. RED proof 4 covers the other direction (a constructor that stops matching).
