## Summary

The nine project invariants supplied with this review hold under adversarial reading:

- **One boundary, no branch.** `web/src/routes/+error.svelte` is the only `+error.svelte` in the tree (census at `test/meta/web_error_boundary_census_test.go:59` pins it, and the walk root is guarded by `require.DirExists`), and the component reads nothing about the request — only the auth store's resolution bit, defaulting unresolved viewers to the smaller guest destination set (`+error.svelte:31-37`). `/admin` never appears as a destination, asserted for all three viewer states at `error-boundary.svelte.test.ts:111-119`.
- **Nav is a projection.** `AdminNav.svelte:29-44` renders one anchor per array member with no client-side registry; the monogram is derived from the response's own `displayName` rather than an id→glyph table. `AdminNav.svelte.test.ts:26-46` drives the count from the input length, so a hardcoded list fails.
- **No `status` on a mutation wire.** `client.ts:243-258` sends `{characterId, expectedVersion}` and nothing else on both transitions; the Sheet's picker snaps back and routes to the confirmation (`EditCharacterSheet.svelte:269-277`). No `sendCommand`/`HandleCommand` string-building anywhere in the phase.
- **No server string reaches the operator.** Every catch in the phase declines to bind the caught value (`+page.svelte:213-219`, `EditCharacterSheet.svelte:219-223, 318-324`, `LifecycleConfirmDialog.svelte:81-84`), and the negative assertions are made against rendered output rather than file text.
- **Unit systems.** `byteCount.ts:42-44` is the single non-test implementation and uses `TextEncoder`; the over-cap comparison is strict `>` at both `ByteCounter.svelte:37` and `EditCharacterSheet.svelte:477`, and Save stays enabled over cap (`EditCharacterSheet.svelte:262`, pinned at `EditCharacterSheet.svelte.test.ts:472-484`). The byte tests carry astral (U+10400), CJK and full-width Latin fixtures — they discriminate.
- **Generated invariant doc.** `INV-PRIVACY-14` is registered in `invariants.yaml:2478-2487` with `binding: bound` and a genuinely asserting `asserted_by`; `invariants.md:196` matches the YAML summary.

Test quality is unusually high for this phase: the vacuity traps named in the brief are handled explicitly (the jsdom backdrop-dismissal case at `LifecycleConfirmDialog.svelte.test.ts:142-173` asserts the *role* and documents why the synthetic interaction is not evidence; the CSS containing-block case at `CharacterTable.svelte.test.ts:238-274` parses the stylesheet because jsdom applies no media query; `LifecycleConfirmDialog.svelte.test.ts:134-138` proves its own forbidden-vocabulary regex can fail).

What the phase does **not** hold is the completeness of its own mutation loop. The D-110 contract is that every refusal lands in an authored surface — and one entry point into the lifecycle mutation has no such surface at all. That is the blocker below; the remaining findings are robustness and honesty-of-comment defects around the same page.

## Critical Issues

### CR-01: The receipt's `Undo` fails silently — no authored surface, and an unhandled rejection

**File:** `web/src/routes/(authed)/admin/characters/+page.svelte:168` (call site), `:148-177` (`applyLifecycle`)

**Issue:** `applyLifecycle` has a `try`/`finally` and **no `catch`**. That is correct for its other caller — `confirmLifecycle` is awaited inside `LifecycleConfirmDialog.confirm()`, which catches and renders `FAILURE_COPY` (`LifecycleConfirmDialog.svelte:73-88`). The toast action is a different caller and has no such wrapper:

```ts
onClick: () => void applyLifecycle(undoId, 'unretire', undoAt),
```

`void` discards the promise; svelte-sonner's action handler ignores a returned promise. So when `AdminUnretireCharacter` refuses (a concurrent edit bumping the version to something other than `undoAt` produces exactly this — `Aborted` — and it is the likeliest failure here, since Undo is composed against a version the retire response returned and a second operator may have moved it since):

1. the operator has clicked `Undo`, and sonner dismisses the toast on action click — which reads as "done";
2. `pendingRowId` is cleared by the `finally`, so the row simply un-greys;
3. the row is never updated (`applyRow` is not reached), so it still reads `retired`;
4. nothing authored renders anywhere, and the rejection surfaces only as an unhandled promise rejection (Sentry/console).

The operator is told an operation succeeded that did not. This is the one path in the phase where a refusal has no screen — the contract the whole surface is built around.

The test suite does not cover it: `characters-page.svelte.test.ts:509-530` drives `impl.undo!()` with `impl.unretire` resolving, and there is no rejecting counterpart. The failure-path coverage that exists (`:549-562`) goes through the confirm dialog, i.e. the caller that *is* wrapped.

**Fix:** give the Undo call the same failure surface as the confirm path. Minimal shape — fire an authored receipt for the failed undo rather than dropping it:

```ts
const UNDO_FAILED = "Couldn't undo that. The character is still retired.";

onClick: () => {
  void applyLifecycle(undoId, 'unretire', undoAt).catch(() => {
    toast(UNDO_FAILED, { duration: TOAST_MS });
  });
},
```

Add a case to `characters-page.svelte.test.ts` with `impl.unretire` rejecting, asserting the row still reads `retired` **and** that a second toast fired — that case fails RED against the current code.

## Warnings

### WR-01: `reload()` has no request-sequencing guard — a stale response can overwrite a newer one

**File:** `web/src/routes/(authed)/admin/characters/+page.svelte:201-223`

**Issue:** Every interactive re-read (`onsearch`, `onstatus`, `onsort`, `onfilterplayer`, `onPageChange`, `clearFilters`) calls `void reload()`, and `reload` writes `rows`, `totalCount`, `failure` and `loading` unconditionally when its own await settles. Nothing records which request is current. Two in-flight reads are easy to produce — the 250 ms debounce bounds keystroke bursts but not the *network*, and a sort click or status change fires immediately with no debounce at all. If request A (term `mir`) resolves after request B (term `miren`), the table renders A's page while the search box, `term`, `status`, `playerId`, `sortField` and `pageNum` all describe B. `failure` is equally affected: a late-resolving failure clobbers a successful newer page into the load-failure screen.

`loading` compounds it — the first response to arrive sets `loading = false` while the second is still outstanding.

**Fix:** stamp each read and drop responses that are not the latest:

```ts
let readSeq = 0;

async function reload() {
  const seq = ++readSeq;
  loading = true;
  flashRowId = '';
  const query = { sortField, descending, status, playerId, page: pageNum };
  const wanted = term;
  try {
    const page = wanted.trim() === ''
      ? await listAdminCharacters(query)
      : await searchAdminCharacters(query, wanted);
    if (seq !== readSeq) return;   // a newer read has already answered
    rows = page.rows;
    totalCount = page.totalCount;
    failure = '';
  } catch {
    if (seq !== readSeq) return;
    rows = [];
    totalCount = 0n;
    failure = wanted.trim() === '' ? 'load' : 'search';
  } finally {
    if (seq === readSeq) loading = false;
  }
}
```

### WR-02: `[section]` renders an entirely blank page for any `available` section that has no concrete route

**File:** `web/src/routes/(authed)/admin/[section]/+page.svelte:15-21`

**Issue:** The template is a single `{#if data.entry.status === 'planned'}` with no `{:else}`. The load has already resolved the entry and returned 200 (`[section]/+page.ts:33-44`), so an `available` entry renders the admin frame, the breadcrumb, and a completely empty content column — no copy, no error, no not-found. Today the only `available` row is `characters` (`internal/admin/section/registry.go:98-99`: "Seven ids, one available and six planned"), and `/admin/characters` is shadowed by its own concrete route, so this is latent rather than live. It becomes live the moment a second section flips to `available` — which the registry comment explicitly anticipates as a normal PR — and the symptom (a blank screen, no console error, tests green) is the hardest kind to attribute.

`section-page.svelte.test.ts:60-68` asserts only the *negative* for that case ("does not render the planned line"), which an empty render satisfies.

**Fix:** make the unhandled case loud rather than blank. Either `error(404)` in the load for an `available` entry reaching the parameterised route (it means no concrete route matched, which is a routing bug, and 404 keeps the surface's one-screen contract), or render an authored placeholder:

```svelte
{:else}
  <!-- An available section reaching the parameterised route means no concrete
       route claimed it. Loud, not blank. -->
  <Empty.Root class="planned">
    <Empty.Title class="planned-name">{data.entry.displayName}</Empty.Title>
    <Empty.Description class="planned-line">This section is not available here.</Empty.Description>
  </Empty.Root>
{/if}
```

Whichever is chosen, add the positive assertion to `section-page.svelte.test.ts` so the branch is pinned.

### WR-03: The receipt interpolates possibly-undefined response fields, printing literal `undefined` to the operator

**File:** `web/src/routes/(authed)/admin/characters/+page.svelte:133-137` and `:158`

**Issue:** `updateAdminCharacter`, `retireAdminCharacter` and `unretireAdminCharacter` are all typed `Promise<CharacterRow | undefined>` (`client.ts:226, 246, 255`), and `applyRow` guards for exactly that (`:105-106, if (!updated) return`). The toast on the same code path does not:

```ts
toast(`AdminUpdateCharacter · update_mask: ${args.paths.length} paths · v${args.expectedVersion} → v${updated?.version}`, …)
const message = `${rpc} · ${updated?.name} · v${expectedVersion} → v${updated?.version}`;
```

With a body-less success response the operator gets `… → vundefined` and `AdminRetireCharacter · undefined · v1 → vundefined`, alongside a row that did not change — a receipt asserting a mutation the page could not confirm. The same `updated` also gates the `Undo` action (`:159`), so the two halves already disagree about whether the value is trustworthy.

**Fix:** treat an absent character as a failure of the receipt, not as a value to interpolate:

```ts
const updated = await updateAdminCharacter({ characterId: id, ...args });
selected = null;
if (!updated) return;            // no confirmed post-write row: no receipt to write
applyRow(updated);
toast(`AdminUpdateCharacter · update_mask: ${args.paths.length} paths · v${args.expectedVersion} → v${updated.version}`, { duration: TOAST_MS });
```

### WR-04: `CharacterFilterBar` never clears its debounce timer, so a search fires after the component is destroyed

**File:** `web/src/lib/components/admin/CharacterFilterBar.svelte:45-56`

**Issue:** `timer` is cleared only on the next keystroke. Nothing cancels it on teardown, so a pending timeout that outlives the component invokes `onsearch?.(raw)` on the destroyed instance — which on this page runs `reload()` and issues a `WebAdminSearchCharacters` RPC for a surface that is gone (navigating away mid-typing is the ordinary way to reach it). The sibling media-query listener in the Sheet is torn down properly (`EditCharacterSheet.svelte:188`) and even has a test for it (`EditCharacterSheet.svelte.test.ts:650-658`); this timer has neither.

**Fix:**

```ts
import { onDestroy } from 'svelte';
// …
onDestroy(() => clearTimeout(timer));
```

and mirror the existing teardown test: mount, type, unmount, advance 250 ms, assert `onsearch` never fired.

### WR-05: `ByteCounter`'s `aria-live` region is created together with its content, so the "counter appears" announcement it claims never happens

**File:** `web/src/lib/components/characters/ByteCounter.svelte:41-58`

**Issue:** The comment states the region exists because "the counter APPEARS at 80% of cap and flips to `over` at 100%, and neither is a focus change, so a screen-reader user typing into the field is never told." The `aria-live` attribute sits on the `<p>` *inside* the `{#if shown}` block — the live region is inserted into the accessibility tree at the same moment its content appears. Assistive technologies announce mutations to a live region that is **already present**; a region added wholesale with its content is generally not announced. So the second claim holds (once `shown` is true, the text update from `80 / 100` to `101 / 100` is a genuine mutation and is announced) and the first — the appearance moment, which is the one the comment leads with — does not.

This is not the previously accepted "ByteCounter has no `aria-live`" gap; it is a new claim in the code that the code does not deliver, which is the more expensive failure because it reads as covered.

**Fix:** render the region unconditionally and gate only its *content*, so the container is in the tree before anything changes:

```svelte
<p class="counter" class:over data-testid="byte-counter" data-over={over ? 'true' : 'false'} aria-live="polite">
  {#if shown}{bytes} / {maxBytes}{/if}
</p>
```

If the empty container is unacceptable visually, keep the current markup and correct the comment to claim only the over-cap flip.

### IN-02: A second mutation of the same row does not replay the arrival flash

**File:** `web/src/routes/(authed)/admin/characters/+page.svelte:105-109`

**Issue:** `applyRow` sets `flashRowId = updated.id`. If the same row is mutated twice in a row (edit, then retire), the value is unchanged, the `is-flash` class never leaves the element, and the CSS animation does not restart — the second change lands with no arrival cue. `flashRowId` is only reset at the top of `reload()`.

**Fix:** clear before setting so the class is genuinely re-added, e.g. `flashRowId = ''; await tick(); flashRowId = updated.id;` — or key the flash on a monotonically increasing token rather than the id.
