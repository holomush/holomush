# Phase 06.1: Code Review Report

**Reviewed:** 2026-08-15
**Depth:** deep

## Summary

This is a gap-closure diff whose whole claim is that coincidence has been replaced by
enforcement. Two of the three enforcement stories hold up under attack; the third does not.

**What holds.** The Go↔TS parity test (`admin_characters_web_parity_test.go`) is genuinely
non-vacuous: I ran its regexes against seven realistic reformats of `ADMIN_EDITABLE_FIELDS`
in a scratch harness. A whole-array reflow and a `satisfies` rewrite fail LOUD at
`require.Len(body, 2)`; a quote-style flip fails LOUD at `require.NotEmpty(entries)`; a
single prettier-reflowed entry is silently dropped from the parse but is then caught LOUD by
the `missingFromClient` set comparison. Trailing-comma changes and commented-out entries are
handled correctly. Both new Go tests were executed and are green
(`task test -- -run … ./internal/grpc/`, `./test/meta/`). The `admin_characters_write.go`
change is four lines of comment and its claims check out against the test it names; I traced
`world.Service.UpdateCharacterProfileAttributes` (service.go:1232-1304) to confirm the
description-only-mask path (RULE 2's `!descriptionChanged` conjunct) is real and not
swallowed by the empty-partition return.

**What does not hold.** The phase's central claim — that the CSS half and the JS half of the
breakpoint bridge are "exact complements everywhere" — is false, and I proved it from build
output rather than by argument. `@media (width < theme(--breakpoint-md))` compiles to
`@media not all and (width>=48rem)`: the CSS half is **rem**-derived and moves with the
user's browser font-size setting, while `DESKTOP_MEDIA_QUERY` is a hard **px** literal that
does not. Worse, the census's allowlist rationale — the load-bearing justification for
exempting that one number — asserts a fact about the build that is demonstrably wrong
(`--breakpoint-md:48rem` **is** emitted to `:root,:host` in the shipped CSS), and the
allowlist's own staleness assertion turns RED on the correct fix. The guard does not merely
fail to catch this defect; it institutionalizes it.

Distinguishing WRONG from NARROW, as asked: CR-01/CR-02 are **wrong**. WR-01 through WR-05
are **narrow** — real holes in the census's reach, none of which invalidate what it does
cover. WR-06 is **wrong-but-small**: a hole in the parity test that both guards stay green
under.

## Critical Issues

### CR-01: The CSS half is rem, the JS half is px — the two halves are NOT complements, and the census forces them to stay that way

**File:** `web/src/lib/hooks/mediaQuery.svelte.ts:5`, `test/meta/web_phone_band_breakpoint_census_test.go:90-100,257`, `web/src/lib/components/admin/EditCharacterSheet.svelte:196-199`

**Issue:**

Tailwind v4's default `--breakpoint-md` is `48rem`, not `768px`
(`web/node_modules/tailwindcss/theme.css:328`), and `app.css` overrides neither breakpoint.
I ran `pnpm build` and read the emitted stylesheet: every converted rule ships as
`@media (width>=48rem)` (9 occurrences) or `@media not all and (width>=48rem)` (6) /
`not all and (width>=64rem)` (3) — exactly the 16 authored rules, all rem-derived.

The JS half is `export const DESKTOP_MEDIA_QUERY = '(min-width: 768px)';`.

`rem` in a media query resolves against the browser's **initial** font-size (the user's
default-font-size preference), not against `html { font-size }`. So with a user default of
20px — a routine accessibility setting — the CSS boundary sits at 960px while the JS boundary
sits at 768px. Between 768px and 960px the two halves take **different branches at the same
width**, which is precisely the failure this phase was written to eliminate. The concrete
result on the admin surface: `SectionRail` and `.adminnav-col` collapse to zero width, the
`.mobilebar` appears, `CharacterTable` drops two columns — and `EditCharacterSheet` renders
`data-side="right"`, because `desktop.current` is `true`. A phone-band shell with a desktop
side sheet.

It is not confined to the admin surface. `ScenesShell.svelte:78,221,459` pairs `isDesktop()`
(px) with Tailwind `md:hidden` (rem) utilities: in that same band the desktop three-pane
renders under `{#if desktop.current}` **and** the `md:hidden` mobile header bar renders, so
both chrome variants are on screen at once.

Nothing in the phase can see this. The E2E boundary block
(`web/e2e/admin-portal.spec.ts:376-451`) probes 767/768/1023/1024 in a Chromium with the
default 16px font, where rem and px coincide exactly — which is why its comment can honestly
say "this block was green before the conversion too". The census cannot see it either
(see CR-02).

And the census actively **blocks the repair**. `web_phone_band_breakpoint_census_test.go:257`
asserts `require.Positive(t, allowlistHits[path])` for `mediaQuery.svelte.ts`, i.e. that the
file still carries a viewport-deciding line containing one of `767|768|1023|1024`. Changing
`DESKTOP_MEDIA_QUERY` to `'(min-width: 48rem)'` — the exact fix — drops that count to zero and
fails the census with *"its exemption is stale and must be removed"*. The guard's staleness
check has been written so that only the defective spelling satisfies it.

**Fix:**

```ts
// web/src/lib/hooks/mediaQuery.svelte.ts
/**
 * Tailwind `md` — 48rem, the SAME unit --breakpoint-md compiles to, so this query
 * and `@media (width >= theme(--breakpoint-md))` resolve identically under any
 * browser default font size. matchMedia parses rem exactly as CSS does.
 */
export const DESKTOP_MEDIA_QUERY = '(min-width: 48rem)';
```

Then, in the same change:

1. Update `mediaQuery.svelte.test.ts:105` (`expect(DESKTOP_MEDIA_QUERY).toBe(...)`) to the
   new literal.
2. Add `"48"`/`"64"` rem forms to `forbiddenViewportWidths`, or (better, see CR-02) delete the
   `mediaQuery.svelte.ts` allowlist entry entirely and derive the query from the emitted
   custom property.
3. Add an E2E case that sets a non-default root font size and asserts the CSS band and
   `data-side` still agree — Playwright can do this via
   `context.newPage()` + a `--font-size` / `Page.setDeviceMetricsOverride` equivalent, or at
   minimum assert `matchMedia(DESKTOP_MEDIA_QUERY).matches ===
   !matchMedia('(width < 48rem)').matches` inside the page at several widths.

### CR-02: The allowlist's stated justification is false — `--breakpoint-md` IS emitted to `:root`, so the JS side CAN read the token at runtime

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:91-94`

**Issue:**

The exemption reads:

> "Tailwind v4 compiles `--breakpoint-md` away at build time and does not emit it to `:root`,
> so the JS side **provably cannot** read the token at runtime and one authored number is
> unavoidable; forbidding it would forbid the fix"

That is the single load-bearing sentence in the entire census — it is why the one number the
census exists to eliminate is permitted to exist. It is wrong. From the shipped build
(`web/build/_app/immutable/assets/0.*.css`):

```
@layer theme{:root,:host{ … --spacing:.25rem;--breakpoint-md:48rem;--breakpoint-lg:64rem; … }}
```

Tailwind v4 emits `@theme` variables to `:root,:host` by default; only `@theme inline` /
`@theme static` change that, and `app.css:9` uses plain `@theme`. So
`getComputedStyle(document.documentElement).getPropertyValue('--breakpoint-md')` returns
`"48rem"` at runtime, and the "unavoidable authored number" is avoidable.

This matters beyond tidiness for two reasons. First, it is the premise that licenses CR-01's
divergence, so future work will re-cite it and re-derive the same defect. Second, a comment
of this shape ("provably cannot") is exactly what stops a later reader from checking; the
repo's own plan-review learnings file records this failure mode verbatim.

**Fix:** either delete the entry and derive the query from the token —

```ts
// web/src/lib/hooks/mediaQuery.svelte.ts
const MD_FALLBACK = '48rem';
function desktopQuery(): string {
  if (typeof document === 'undefined') return `(min-width: ${MD_FALLBACK})`;
  const token = getComputedStyle(document.documentElement)
    .getPropertyValue('--breakpoint-md')
    .trim();
  return `(min-width: ${token || MD_FALLBACK})`;
}
```

— or, if a runtime read is judged not worth the cost, keep the literal but **correct the
reason**: the number is authored because a build-time read is preferred to a
`getComputedStyle` on every hook construction, *not* because the token is unreadable. Either
way the unit must become `rem` (CR-01).

## Warnings

### WR-01: `forbiddenViewportWidths` carries only px decimals, so the rem spelling the tokens compile to sails straight through

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:79`

**Issue:** The forbidden set is `{"767","768","1023","1024"}`. A future hand-written
`@media (min-width: 48rem)` or `@media (width < 64rem)` is classified as viewport-deciding by
`isViewportDecidingLine` (it starts with `@media`) but carries no forbidden substring, so it
is not flagged. Since the conversion made `48rem`/`64rem` the *visible* form of these
breakpoints — it is what a developer now sees in DevTools and in the built CSS — a rem-spelled
copy is the **most likely** future duplication, and it is the one form the census cannot see.
This is a NARROW guard, not a wrong one.

**Fix:**

```go
// px decimals AND the rem forms the tokens compile to; a copy in either unit
// is a copy.
var forbiddenViewportWidths = []string{"767", "768", "1023", "1024", "48rem", "64rem"}
```

Note the substring predicate makes `"48rem"` safe (it cannot collide with `480rem`-style
values in practice, and `lineCarriesForbiddenWidth` is already narrowed to viewport-deciding
lines).

### WR-02: Tailwind arbitrary-variant and JS-width viewport decisions are not classified as viewport-deciding lines

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:110-118`

**Issue:** Two shapes decide a viewport band and satisfy none of the three clauses:

- `class="min-[768px]:flex"` / `class="max-[767px]:hidden"` — Tailwind v4 arbitrary variants.
  No `@media` prefix, no `matchMedia(`, no `(min-width:`. This is idiomatic in a Tailwind v4
  codebase and is literally a hand-written breakpoint in markup.
- `if (window.innerWidth < 768)` — no media syntax at all. `Composer.svelte:49,102,123`
  already reads `window.innerWidth` for other purposes, so the idiom is present in-tree.

Neither exists today (verified with `rg '(min|max)-\[[0-9]+(px|rem)\]'` and
`rg 'innerWidth'` over `web/src`), so this is prospective reach, not a live escape.

**Fix:** add two clauses:

```go
if strings.Contains(line, "min-[") || strings.Contains(line, "max-[") {
    return true
}
if strings.Contains(line, "innerWidth") || strings.Contains(line, "outerWidth") {
    return true
}
```

### WR-03: The anti-vacuity floor is inflated by non-band `@media` lines and is roughly half the real corpus

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:239-243`

**Issue:** `scanned` counts every line matching the predicate, including the five
`@media (prefers-reduced-motion: …)` / `(prefers-color-scheme: …)` rules and the
`window.matchMedia(` call sites — lines that can never carry a band literal. Measured over
`web/src` the predicate matches **32** lines, of which only **7** carry a forbidden width
(all 7 in the two allowlisted files). The floor is `> 15`. So the walk could stop reaching
more than half the tree — a renamed `web/src/lib`, a `skipDirs` addition, an extension-set
edit — and the floor would still pass while the census silently covered nothing that matters.

**Fix:** count only band-relevant lines, and raise the floor to something derived:

```go
// Count lines that COULD carry a band literal, not every media rule.
if strings.Contains(line, "prefers-") || strings.Contains(line, "hover:") ||
    strings.Contains(line, "forced-colors") {
    continue
}
scanned++
…
require.GreaterOrEqual(t, scanned, len(bandedViewportRules), …)
```

### WR-04: The duplicated `TopBar.svelte` census entry is decorative — `require.Contains` cannot count occurrences

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:65-68,295-297`

**Issue:** The comment says *"TopBar carries TWO rules in ONE style block … so its pair
repeats"*, and the slice lists `{TopBar, ruleAtOrAboveM}` twice. But
`TestEveryBandedViewportRuleDerivesItsWidthFromTheTailwindToken` asserts
`require.Contains(src, r.rule)` — a substring test. Both entries carry the identical rule
text, so the second assertion is the first one re-run. Deleting either of TopBar's two rules
(`TopBar.svelte:204` `.kbd-hint`, `:244` `.mobile-only`) leaves the census green. The census
documents per-rule coverage it does not have; every other multi-rule file (`SectionRail`,
`admin/+layout`) is safe only because its two rules happen to use *different* tokens.

**Fix:** count occurrences instead of testing containment:

```go
want := map[bandedViewportRule]int{}
for _, r := range bandedViewportRules {
    want[r]++
}
for r, n := range want {
    src := readFile(t, filepath.Join(root, r.path))
    require.Equal(t, n, strings.Count(src, r.rule),
        "%s must carry the token-derived rule %q exactly %d time(s)", r.path, r.rule, n)
}
```

### WR-05: `referenceDirectiveFor` computes a wrong directive for a file directly under `web/src`

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:142-149`

**Issue:** For `web/src/foo.svelte`, `filepath.Dir(rel)` is `"."`,
`strings.Count(".", "/")` is 0, so `depth` is 1 and the expected directive is
`@reference "../app.css";` — which points at `web/app.css`, one level too high. The correct
value is `"./app.css"` (or `"app.css"`). No such file exists today, so this is latent, but
the census would demand the wrong directive from the first one added, and a build failure
would be blamed on the file rather than on the helper. I verified the formula is correct for
every depth ≥ 1 currently in the census (`../../app.css` for `lib/components/TopBar.svelte`
through `../../../../app.css` for `routes/(authed)/characters/new/`), and the full
`pnpm build` succeeds, which confirms all 16 blocks resolve `theme()`.

**Fix:**

```go
dir := filepath.ToSlash(filepath.Dir(rel))
if dir == "." {
    return `@reference "./app.css";`
}
depth := strings.Count(dir, "/") + 1
```

### WR-06: The parity test reads the per-path cap from the constructor NAME, never from the emitted `maxBytes` — a cap edit inside `line`/`prose` leaves both guards green

**File:** `internal/grpc/admin_characters_web_parity_test.go:155-167`, `web/src/lib/components/admin/EditCharacterSheet.svelte:55-69`

**Issue:** The Go test maps `line ⇒ shortCap` and `prose ⇒ longCap` by the matched
constructor name, where `shortCap`/`longCap` come from the `const SHORT`/`const LONG`
declarations. It never checks that the constructors actually *use* those constants. Change
`line` to `maxBytes: 90` (or `SHORT - 10`, or a fresh literal) and:

- the Go test still reads `const SHORT = 100`, still maps `line → 100`, still agrees with
  `world.MaxNameLength` → GREEN;
- the surviving TS test ("partitions the paths across exactly two caps … line strictly
  smaller", `EditCharacterSheet.svelte.test.ts`) sees `lineCaps = {90}`,
  `proseCaps = {4000}`, `90 < 4000` → GREEN.

Meanwhile every rendered counter reads `n of 90` while the server refuses at 100. That is
exactly the "the counter warns at one byte count while the server refuses at another"
disagreement the test's own doc comment says it prevents. The two guards, taken together,
still do not cover the value that reaches the DOM. (The *swap* case — `line → LONG`,
`prose → SHORT` — IS caught, by the TS `lineCap < proseCap` assertion.)

**Fix:** parse the emitted value rather than the constructor name — or, cheaper and stronger,
assert in the TS test that the caps are the module's own constants as rendered:

```go
// admin_characters_web_parity_test.go — pin the constructors to the constants.
var (
	adminSheetLineCtorRe  = regexp.MustCompile(`(?s)const line = \([^)]*\): EditableField => \(\{.*?maxBytes: SHORT,.*?\}\);`)
	adminSheetProseCtorRe = regexp.MustCompile(`(?s)const prose = \([^)]*\): EditableField => \(\{.*?maxBytes: LONG,.*?\}\);`)
)
require.Regexp(t, adminSheetLineCtorRe, src,
    "`line` must emit maxBytes: SHORT — the name-to-cap mapping below reads the CONSTRUCTOR NAME, "+
        "so a literal or an arithmetic expression here breaks the link silently")
require.Regexp(t, adminSheetProseCtorRe, src, "`prose` must emit maxBytes: LONG")
```

### WR-07: A prettier-reflowed entry is caught, but reported as an ADMIN-04 scope loss

**File:** `internal/grpc/admin_characters_web_parity_test.go:127-130,191-193`

**Issue:** I confirmed empirically that `adminSheetEntryRe`
(`^\s*(line|prose)\('([^']+)',`) drops an entry reformatted across lines:

```ts
line(
  'profile.pronouns',
  'A label long enough to force a reflow',
),
```

parses as 2 entries out of 3. The `require.NotEmpty(entries)` anti-vacuity precondition does
**not** fire (other entries matched); the drop is caught one assertion later by
`missingFromClient`. So the guard is not vacuous — but the operator reading CI sees
*"the server accepts a writable path the Sheet offers no control for — an admin-reachable
field with no way to reach it, which is an ADMIN-04 scope loss"* for what is a whitespace
change. A misdiagnosis at that severity costs a real investigation.

**Fix:** make the entry regex tolerate the reflow and let the count itself be the guard:

```go
adminSheetEntryRe = regexp.MustCompile(`(?s)\b(line|prose)\(\s*'([^']+)'\s*,`)
```

and add, after the parse, a count check whose message names the real cause:

```go
require.Equal(t, strings.Count(body[1], "line(")+strings.Count(body[1], "prose("), len(entries),
    "an entry in ADMIN_EDITABLE_FIELDS did not parse — a reformat, not a scope change; "+
        "fix the regex rather than the declaration")
```

### WR-08: The range-syntax conversion raises the browser floor with no browserslist target and no note

**File:** all sixteen converted rules; representative: `web/src/lib/components/shell/SectionRail.svelte:172`, `web/src/lib/components/sidebar/Sidebar.svelte:54`

**Issue:** `web/package.json` and `web/vite.config.ts` declare no `browserslist` and no
Lightning CSS `targets`, so Lightning CSS does **not** downlevel: the shipped stylesheet
contains `@media (width>=48rem)` and `@media not all and (width>=48rem)` verbatim (verified
in `web/build/_app/immutable/assets/*.css`). CSS media range syntax requires Safari 16.4+
(Mar 2023), Chrome 104+, Firefox 63+. On anything older, a query containing an unparseable
feature evaluates to *unknown* and never matches — so on those browsers **every** converted
rule is dead: the persistent rail never collapses on a phone, `.mobile-only` never hides on a
desktop, the admin nav never narrows. The pre-conversion `max-width: 767px` /
`min-width: 768px` forms worked everywhere. This is a deliberate-looking trade that no
artifact in the diff names.

**Fix:** either state the floor explicitly (a `browserslist` key in `web/package.json`
documenting Safari ≥ 16.4, which also lets Lightning CSS downlevel automatically if the floor
is later lowered), or add `targets` to the Tailwind/Lightning config so the range form is
emitted alongside a `min-width`/`max-width` fallback.

### WR-09: `columnsAt` waits a fixed 300ms rather than for the transition to settle

**File:** `web/e2e/admin-portal.spec.ts:383,387-388`

**Issue:** `BAND_SETTLE_MS = 300` with `await page.waitForTimeout(BAND_SETTLE_MS)` is a
wall-clock sleep sized against a 180ms `transition: width`. Under CI load — the repo's own
testing notes record Postgres testcontainer drops under exactly that condition — a slow frame
makes the measurement land mid-animation, which the comment says already invalidated one UAT
pass. This is the only new E2E block that gates on a timer.

**Fix:** wait for the property, not the clock — poll until the measured width stops moving:

```ts
async function settledWidth(loc: Locator): Promise<number> {
  let last = -1;
  await expect
    .poll(async () => {
      const w = await loc.evaluate((el) => el.getBoundingClientRect().width);
      const stable = w === last;
      last = w;
      return stable;
    }, { timeout: 5000 })
    .toBe(true);
  return last;
}
```

or listen for `transitionend` on both columns before measuring.

### WR-10: The census allowlist is keyed by whole file, so any future literal in `mediaQuery.svelte.ts` is silently exempt

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:81-100`

**Issue:** The path-key choice is well argued (a `path:line` key fails open on any edit above
it), but the consequence is stated as if it had no cost: *"Nothing else in either file needs
scanning, so the path key gives up no coverage the line keys were buying."* That is true
today and false the moment a second constant is added — `export const TABLET_MEDIA_QUERY =
'(min-width: 1024px)'` in that file is exempt by construction, and the census would report
success. Given the file is *the* home for shared media queries, a second one is likely.

**Fix:** narrow the exemption to the symbol rather than the file:

```go
// allowed only on the DESKTOP_MEDIA_QUERY declaration line itself
if allowed && strings.Contains(line, "DESKTOP_MEDIA_QUERY") { … }
```

The line-drift hazard the comment names does not apply here, because the key is a symbol name
rather than a number.

### WR-11: `CharacterTable.svelte.test.ts` re-copies the rule text and takes the first matching block

**File:** `web/src/lib/components/admin/CharacterTable.svelte.test.ts:245,250`

**Issue:** `src.indexOf('@media (width < theme(--breakpoint-md))')` is a fourth textual copy
of the rule form (the file, the census constant, the census message, and here). A benign
reformat — `theme( --breakpoint-md )`, a line break inside the condition — makes
`expect(start).toBeGreaterThan(-1)` fail with no indication that only the *spelling* moved.
And `indexOf` binds to the first occurrence, so a second sub-md block added above this one
would silently retarget the whole brace-balance parse at the wrong rules.

**Fix:** match the block by a stable anchor inside it rather than by its condition text, e.g.
locate `.rowbtn::after` and walk *outward* to the enclosing `@media`; or export the rule text
from a shared TS constant both the component and the test read.

### WR-12: The census extension set silently skips any language it does not enumerate

**File:** `test/meta/web_phone_band_breakpoint_census_test.go:191`

**Issue:** `scannedExtensions` is `{.svelte, .css, .ts}`. `web/src` today contains only
`.svelte`, `.ts`, `.json`, `.html`, `.css` (verified), so coverage is complete — but a
`.js`, `.jsx`, `.tsx`, `.scss` or `.postcss` file added later is skipped with no signal, and
the `scanned` floor (WR-03) is far too loose to notice. This is the same fail-open shape the
allowlist comment is careful about one level up.

**Fix:** invert the filter — enumerate the extensions to *skip* (`.json`, `.md`, `.png`, …)
and fail the walk on an unrecognized one, or assert the observed extension set matches an
enumerated census the way `bandedViewportRules` does.
