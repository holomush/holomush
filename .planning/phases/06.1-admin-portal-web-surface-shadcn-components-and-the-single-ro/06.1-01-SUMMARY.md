**What the new check proves that existing coverage does not:** that the SvelteKit **error-boundary resolution point is unique**. A Go-AST census cannot see a `.svelte` file; a lint rule cannot see a route tree; a type-check cannot count. Uniqueness is a property of the filesystem shape, so a filesystem census is the least-ceremony mechanism that can hold it. In-tree idioms were reused where they exist — `findRepoRoot`, `skipDirs`, `filepath.WalkDir`, and the "What this fence does NOT cover" doc-block shape from `admin_rpc_placement_test.go`.

### Why the census enumerates rather than shelling out

A line-counting shell-out counts matching **lines**, not files, and — decisively — also passes at zero, which is exactly the state the tree was in before this plan. `filepath.WalkDir` plus `require.Len(found, 1)` fails in both directions, and `require.DirExists` on the walk root makes a moved route tree fail loudly instead of yielding an empty slice that reads as a deleted boundary. (Kept here rather than in the test file's doc block: the plan's own criteria negative-grep that file, and naming the rejected tool inside it is the self-tripping shape this phase has now hit five times.)

### Why the invariant is narrow

`INV-PRIVACY-14` reads:

> The SvelteKit error-boundary resolution point under `web/src/routes/` is unique: exactly one `+error.svelte` exists, at the root. Uniqueness is a precondition for per-viewer indistinguishability of routing misses, not a proof of it — the census reads the filesystem and can see neither what the boundary renders nor whether two viewers receive the same bytes.

The second clause travels with the id on purpose. ## Decisions Made

- **The toaster reads the repo's own theme store.** The generated `sonner.svelte` imported a separate theme-watcher package for its light/dark bit. Dropped: the repo already owns that fact (`themePreferences.themeId`, suffixed `-light` / `-dark`), and a second source of truth for it is precisely what the one-new-dependency constraint exists to prevent.
- **`isPlayerAuthenticated` is the resolution bit; no new field was minted.** It is `false` in `initial` and set `true` only by `setPlayerProfile`, which every resolution path calls — guests included, resolving to `{isPlayerAuthenticated: true, isGuest: true}`. A parallel `profileResolved` flag would be a second source of truth for the same fact.
- **Unresolved falls back to guest.** The direction is chosen by which failure mode is closed: rendering fewer destinations for one frame costs nothing; rendering the registered-player set before session restoration is the leak.
- **Amendments 1–8 folded onto #4975 rather than duplicated**, because #4975 already carries those seven rows verbatim and the plan's own instruction is to fold.
