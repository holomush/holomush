Binding constraints, each of which is a rule the next reader would otherwise break:
- **No reason parameter.** The component takes no prop describing *why* it is rendering. It
  often could know (an RPC denied); if it never has the value, a future change cannot surface it.
- **No path echo.** Echoing `/admin/moderation` confirms the string routed somewhere.
- **No status code, no error message, no `$page.error.message`** rendered anywhere.
- **`/admin` is not in the destination list** and is not added to `SECTIONS`. The rail's `Admin`
  entry is drawn separately, by the rail, from `WebCheckSessionResponse.roles`.
- **It never awaits.** Read the viewer from the client-side `authState` store, exactly as
  `(authed)/+layout.svelte:18` does, and pass it to `visibleSections({ isGuest })` — whose
  signature requires that explicit argument (`sections.ts:63`). **Be precise about where the
  viewer comes from**, because "already-resolved layout data" is not accurate here and would send
  the executor looking for something that does not exist (cross-AI review R-15):
  `web/src/routes/+layout.ts` returns **no** viewer data, the `(authed)` load returns only
  `defaultCharacterId`, and a **root** `+error.svelte` renders *outside* the `(authed)` layout
  entirely — SvelteKit renders only the layouts above the boundary — so `(authed)` layout data is
  unavailable to it for a root routing miss. The store is a module singleton and is readable from
  either position.
- **Derive `isGuest` through the resolution bit, not from `$authState.isGuest` directly**
  (cross-AI review C2-07):

  ```
  const resolved = $derived($authState.isPlayerAuthenticated);
  const isGuest  = $derived(resolved ? $authState.isGuest : true);
  ```

  An earlier revision passed `$authState.isGuest` straight through and required an "unpopulated
  store renders `Home` alone" test. That test could not pass: `initial` is
  `{ isPlayerAuthenticated: false, isGuest: false, … }` (`authStore.ts:25-33`), so an unpopulated
  store is **indistinguishable from a resolved registered player** by `isGuest` alone, and
  `visibleSections({ isGuest: false })` returns **both** workspace entries (`sections.ts:63-67`).
  Worse than failing the test: the initial render would expose the registered-player destination
  set before session restoration — exactly the correlation T-06-17 exists to close.

  **No new state field is needed.** `isPlayerAuthenticated` already is the resolution bit: it is
  `false` in `initial` and set `true` only by `setPlayerProfile`, which every resolution path
  calls — including for a guest, who resolves to `{isPlayerAuthenticated: true, isGuest: true}`.
  Adding a parallel `profileResolved` flag would be a second source of truth for the same fact.
  Do **not** add one, and do not modify `authStore.ts` from this plan.

  The direction of the fallback matters and is deliberate: unresolved is treated as **guest**,
  the *smallest* destination set, because `visibleSections` filters `requiresPlayer` entries out
  for guests. Showing fewer destinations for one frame is not a leak; showing the registered set
  to an unauthenticated viewer is.
- If the store is unresolved (a miss before session restore has run), draw the `Home` link
  **alone**, silently — no spinner, no retry, no "couldn't load your sections" text. A page that
  blocks on a request, or flickers its destinations in, makes render timing a per-viewer signal.
  This graceful degradation is what makes the store's timing immaterial rather than a leak.
- Headings and destination links **wrap**; nothing truncates.
- Copy contains no `HoloMUSH` (INV-6) and the back target is the word `Home`.
- Colour comes from `var(--color-*)`; no hardcoded hex; no amber.
