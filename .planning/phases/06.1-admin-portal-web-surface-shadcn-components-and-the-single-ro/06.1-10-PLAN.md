<objective>
Close G-06.1-6. Plan 06.1-05 moved all sixteen authored rules to CSS media RANGE
syntax. `rg -n 'browserslist|targets' web/package.json web/vite.config.ts` returns
zero, so nothing downlevels them and the shipped stylesheet carries the range form
verbatim — 19 range-form conditions and 0 px-form fallbacks.

A media query containing a feature the browser cannot parse evaluates to `unknown`
and never matches. On a browser below the range-syntax boundary that means the
persistent rail never collapses on a phone, `.mobile-only` never hides on a
desktop, and the admin nav never narrows. The pre-conversion forms worked
everywhere. No artifact in that diff names the trade.

Purpose: the phone-band rules must actually fire on the browsers the product
supports — and which browsers those are must be a decision someone made, not a
side effect of a stylistic conversion.
Output: a declared floor, a check that keeps it declared, and an observation of
what the build actually emits under it.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Choose the web client's declared browser floor</name>
  <decision>Which browser floor does the HoloMUSH web client declare, and does the build downlevel CSS media range syntax to reach below it?</decision>
  <context>
All sixteen authored viewport rules now ship as CSS media range syntax
(`@media (width>=48rem)` and `@media not all and (width>=48rem)`), verified in the
built stylesheet. Range syntax needs Safari 16.4+ (March 2023), Chrome 104+ and
Firefox 63+. Below any of those the rule does not merely degrade — it never
matches, so a phone gets the desktop layout with a persistent rail it cannot
collapse.

There is no declared floor in the repo today, so the question has never been put.
It is a published support contract, not a code detail: it decides who the product
tells people it works for. That is why it is yours rather than the executor's.

Whichever option is chosen, the executor records the choice, then OBSERVES what
`task web:build` actually emits under it rather than asserting what the toolchain
is believed to do.
  </context>
  <options>
    <option id="declare-modern">
      <name>Declare the floor at the range-syntax boundary and ship the range form as-is</name>
      <pros>No build-pipeline change and no second code path. The range form is the correct one — `width &lt; token` and `width >= token` are exact complements at fractional widths, which the retired one-below-the-boundary px pair was not. Smallest stylesheet. Matches where the tree already is.</pros>
      <cons>Browsers older than roughly Safari 16.4 / Chrome 104 / Firefox 63 get a broken responsive layout with no graceful degradation. The floor becomes a real support statement someone may have to defend.</cons>
    </option>
    <option id="downlevel">
      <name>Declare a lower floor and configure the build to emit a min-width/max-width fallback alongside the range form</name>
      <pros>Older browsers keep a working layout. The floor can then be set by product reach rather than by a CSS syntax choice.</pros>
      <cons>Requires a build-pipeline change whose effect must be verified empirically against the emitted CSS — the fallback pair reintroduces the off-by-one at fractional widths that motivated the range form, on exactly the old browsers that get it. Larger stylesheet. A second code path to reason about.</cons>
    </option>
    <option id="defer">
      <name>Declare nothing this round and file the floor as a tracked issue</name>
      <pros>Zero change now.</pros>
      <cons>Leaves G-06.1-6 open and the floor undeclared, which is the state the verifier flagged. Choose only with a filed issue and an explicit acceptance that criterion-adjacent durability stays unresolved.</cons>
    </option>
  </options>
  <resume-signal>Select: declare-modern, downlevel, or defer — and, for the first two, name the exact minimum versions to declare.</resume-signal>
</task>
