# Phase 06.1 Plan 10: Declared browser floor (G-06.1-6) Summary

The browser floor the range-syntax media conditions require is now a decision on the
record — five explicit minimum versions in `web/package.json`, a stated rule for deriving
them, and a meta-test that goes red when the declaration is deleted, emptied, made
relative, or lowered below what the shipped stylesheet demonstrably requires.

## The decision, and where the numbers came from

Task 1 was a blocking `checkpoint:decision`. It was returned to the human, not
auto-decided. Resolution: **`declare-modern`**, anchored on the SvelteKit toolchain's own
declared target.

**The rule** — written into the meta-test's doc block, because JSON admits no comment:
*the floor is the Vite baseline target, raised per-browser wherever a shipped dependency
binds higher.* That is the durable artifact; the numbers below are what it currently
yields.

**Source**, verified in-tree rather than inherited:

```
web/node_modules/vite/dist/node/chunks/node.js:610
const ESBUILD_BASELINE_WIDELY_AVAILABLE_TARGET = [
  "chrome111", "edge111", "firefox114", "safari16.4", "ios16.4"
];
```

`:32827` sets `target: "baseline-widely-available"` as the default and `:32877` resolves
it to that array. `rg 'build\s*:|target' vite.config.ts svelte.config.js` returns nothing,
so no override exists — this is what the build already transpiles JS to.

**Raise:** firefox 114 → **128**. Declared floor:

```json
"browserslist": [
  "chrome >= 111",
  "edge >= 111",
  "firefox >= 128",
  "safari >= 16.4",
  "ios_saf >= 16.4"
]
```

The `>=` spelling is load-bearing: bare `chrome 111` means *only* 111 to browserslist,
while `chrome >= 111` is the floor the key exists to state.

## The floor derivation — every feature classified at its call site

The coordinator's first enumeration stopped at Tailwind; the second added a shadcn/bits-ui
scan and suspected `checkVisibility` would push Safari to 17.4. Both were re-derived here
from the built output. **The suspicion is refuted** — and two entries in the supplied
table dissolve entirely on inspection.

| Feature | Hits | Class | Evidence read at the call site | Binds? |
|---|---|---|---|---|
| `@property` | 59 | **hard** | unguarded; MDN Cr85 / **FF128** / **Sa16.4** / **iOS16.4** | **sets FF + Safari + iOS** |
| `oklch()` | 8 | hard | unguarded | ≤ Cr111 |
| `color-mix()` | 130 | soft | hex fallback emitted first, then `@supports (color:color-mix(in lab, red, red))` | no |
| media range syntax | 24 | hard | Cr104 / FF63 / Sa16.4 | below `@property` |
| `:has()` | 79 | hard | Cr105 / Sa15.4 / FF121 | below |
| `@container` | 6 | hard | Cr105 / Sa16.0 / FF110 | below |
| `Element.checkVisibility()` | 3 | **soft** | `` `checkVisibility` in e `` guard, inside tabbable's opt-in `full-native` display-check mode | **no — refutes Sa17.4** |
| `requestIdleCallback` | 1 | **soft** | `W.requestIdleCallback \|\| W.setTimeout` | no |
| `structuredClone` | 2 | hard | one bare, one in try/catch; Cr98 / FF94 / Sa15.4 | below |
| `Object.hasOwn` | 2 | hard | Cr93 / FF92 / Sa15.4 | below |
| `text-wrap: balance/pretty` | 3 | **soft** | `.text-balance` / `.text-pretty` utilities; degrade to normal wrapping | no |
| `field-sizing: content` | 2 | **soft** | `.field-sizing-content` utility; degrades to fixed-size input | no |
| `popover` | 7 | **n/a** | **not a feature** — every hit is a shadcn design token (`--color-popover`, `.bg-popover`, `.text-popover-foreground`). Built JS has 0 `showPopover`, `hidePopover`, `togglePopover`, `popoverTargetElement`, `popover=` | no |

Two corrections to the supplied enumeration:

- **`Object.hasOwn` is 2, not 25.** The 25 conflates it with the 23 `hasOwnProperty`
  occurrences, which are ES3 and impose no floor. `2 + 23 = 25`.
- **`:has()` (79 hits) was absent from the supplied table** and is the single most common
  version-gated CSS feature in the output. It does not bind, but it was not enumerated.

`@property` is therefore the sole binding constraint, and it lands on Firefox 128 /
Safari 16.4 / iOS 16.4 — so the Safari floor did **not** rise above 16.4 and the
iOS-device support line was not crossed. No stop-and-report was required.

MDN was fetched rather than recalled (`date +%Y` → 2026 first):
`https://developer.mozilla.org/en-US/docs/Web/CSS/@property` →
Chrome 85 / Edge 85 / **Firefox 128** / Safari **16.4** / Safari on iOS **16.4**.

## The census-movement check — required, run, and clean

Run immediately before and after adding the key, with the identical command both sides.
The AFTER build deleted `.svelte-kit/output/client/_app/immutable/assets` first, so it is
a genuine fresh build rather than a cached one.


**No count moved.** Nothing consumes `browserslist` in this toolchain — Vite drives CSS
and JS lowering from `build.target`, and Tailwind v4 does not read the key — so the key is
declarative only. That was verified by observation, not asserted from belief. The guards
06.1-07 and 06.1-08 built over the emitted stylesheet see an unchanged corpus.

The plan's own figure of "19 range-form conditions" is confirmed intact at current HEAD,
but it counts only the band breakpoints. The full stylesheet carries **24**: the extra five
are Tailwind's own `sm:`/`xl:`/`2xl:` utilities (`40rem`, `80rem`, `96rem`) plus one
`(width<=600px)` from a dependency. Tailwind v4 emits range syntax for every responsive
utility, so the range-syntax dependency was never confined to the sixteen authored rules —
reverting them would not have restored old-browser support.

## Deviations from Plan

**1. [Rule 1 — Bug] The doc comment spelled a token its own acceptance grep searches for**
- **Found during:** Task 3, running the acceptance criterion
- **Issue:** the doc block's closing paragraph read "No `// Verifies:` annotation appears
  in this file." The plan's criterion is that
  `rg -n '// Verifies:' test/meta/web_browser_floor_test.go` returns **no match**. The prose
  contained the literal token, so the grep matched line 100 and the criterion **failed on
  the strength of a comment** — while the file genuinely carried no annotation.
- **Fix:** the paragraph was rewritten to "This file carries NO invariant-binding
  annotation of any kind", and a following sentence records *why* it does not spell the
  token, so a future editor does not reintroduce it. The criterion was **not** relaxed.
- **Notable:** this is the same defect class as 06.1-08's deviation 2 (a marker comment
  naming its counterpart's token) and 06.1-07's deviation 4 (prose containing
  `waitForTimeout`). Third occurrence in this phase, hence the pattern entry above.
- **Files modified:** `test/meta/web_browser_floor_test.go`
- **Commit:** `3ca51a3d0`

**2. [Rule 2 — Missing correctness] The floor's truth, not only its shape, is asserted**
- **Found during:** Task 3
- **Issue:** the plan's four named mutations all test the key's *shape* — present,
  non-empty, explicit versions. None catches lowering `firefox >= 128` to Vite's baseline
  `114`, which would publish a support contract the stylesheet cannot honour while every

## Notes for the verifier

- **`downlevel` was rejected on two independent grounds**, both surfaced at the checkpoint.
  Mechanically: `lightningcss` is transitive-only in the pnpm store (`1.32.0`, `1.33.0`)
  and `require.resolve` from `web/` returns `MODULE_NOT_FOUND`, so enabling
  `css.transformer: 'lightningcss'` needs a direct devDependency — which threat
  `T-06.1-10-SC` and the executor's package-install exclusion both forbid without a
  RESEARCH.md audit this phase does not have. Substantively: downlevelling media conditions
  cannot downlevel the 59 `@property` rules, so a browser below the floor would still get an
  unthemed page. A fallback that buys nothing is the `T-06.1-10-03` failure mode.
- **`web/vite.config.ts` is listed in the plan's `files_modified` but was not touched.**
  That is correct under `declare-modern`: the plan scopes the vite.config change to
  `downlevel` only.
- **The meta-test does not read the built stylesheet, by design.** It owns the
  *declaration*; `web_phone_band_breakpoint_census_test.go` owns the authored rules'
  *spelling*. Deleting a banded rule is the census's failure; deleting the floor is this
  one's. The doc block names the neighbour it deliberately does not duplicate.
- **What this plan does NOT prove** is that the declared floor is *correct* — no test can,
  because correctness here is a product decision about who the product says it serves. It
  proves the floor is declared, non-empty, states checkable versions, and is not below what
  the shipped CSS demonstrably requires.
- **The `@property` count is load-bearing for the Firefox raise.** If a future change
  removes every unguarded `@property` from the output, the Firefox floor could legitimately
  drop to Vite's baseline — and `propertyBoundFloors` would then need re-deriving, not
  deleting. The test's failure message says so explicitly.
