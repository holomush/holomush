**Columns.** Six at `>=768px`: `Name`, `Player`, `Status`, `Last active`, `Created`, `Ver`.

**The client never re-sorts.** Render `rows` in the order received. The `never` rows' position

**Row actions.** At `>=768px`, hover reveals **exactly two**: `Edit` and `Retire…` (or

**Specify that markup rather than leaving it to invention** (cross-AI review R-40): a `<tr>`
cannot *become* a `<button>` and a `<button>` cannot legally contain `<td>` elements, so the
naive reading produces invalid markup and an inaccessible row. The pattern is a **primary-cell
button with a row-spanning overlay**: the `Name` cell contains a real
`<button type="button">` carrying the row's accessible name (character name, player, status,
last active); the button gets a `::after { position: absolute; inset: 0; }` pseudo-element
extending its hit area across the row, inside one `@media (max-width: 767px)` block. The `<tr>`
itself gets no handler and no role. Result: valid table semantics at every band, one focusable
control per row, keyboard activation via `Enter`/`Space` for free, and focus returning to that
button when the Sheet closes (the `bits-ui` Dialog contract 06.1-04 relies on).

**The positioned ancestor is the `<tr>`, not the `<td>`** (cross-AI review C2-10). An earlier
revision put `position: relative` on the Name `<td>`; an absolutely-positioned pseudo-element
resolves against its nearest **positioned ancestor**, so `inset: 0` would have covered the Name
cell alone and a tap on `Player`, `Status` or `Last active` would have hit nothing. Put
`position: relative` on the `<tr>` inside the same `@media` block, and leave every `<td>` static.
`position: relative` on a table row is supported in every current engine and is the standard
full-row-overlay technique; the button's `::after` then genuinely spans the row.
