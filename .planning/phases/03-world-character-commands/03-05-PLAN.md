The statement is `UPDATE characters SET last_active_at = $2 WHERE id = $1 AND last_active_at < $2`.
The monotonic guard lives in the PREDICATE — that is what makes the write idempotent under
at-least-once redelivery with no read-modify-write and no lock-ordering exposure. Zero rows affected is
a SUCCESS, not an error: it means either the stored value was already at least as new, or the character
no longer exists.

Do NOT bump `version` and do NOT route through `worldMutator.mutate`. `last_active_at` is an
operational column, not world state. Routing it through the executor would fire the census AST
cross-check (demanding a taxonomy kind for a non-world-state column) and would add a spurious
world-change envelope on every flush.

Write the doc comment to carry three facts a future reader needs and cannot infer: that the value is
BIGINT epoch nanoseconds with `0` as the never-active sentinel per INV-STORE-1; that this is the fourth
sanctioned out-of-world writer under INV-WORLD-4 and the first that deliberately emits NO envelope; and
that the column LAGS real time by up to one flush interval by construction, so any reader needing
real-time accuracy must consult the KV bucket rather than the column. That last sentence is the guard
against the column being mistaken for live presence later.

Take the pairs as a batch so the flusher can drain many keys in one round trip, and make partial
failure explicit — return which ids failed rather than aborting the whole batch on the first error.

Add unit tests for every branch in the behavior list against a real Postgres testcontainer, including
the backwards-timestamp no-op and the missing-character no-op.
