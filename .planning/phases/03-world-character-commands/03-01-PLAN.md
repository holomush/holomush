  <context>
D-32 already settles that this phase mints TWO distinct kinds — that is forced by the census bijection
(`test/meta/world_envelope_census_test.go:84-88` fatals when two commands share a kind) and by

What is genuinely open, and genuinely one-way, is the literal strings and the payload shape. A taxonomy
kind is a published wire contract stamped onto durable outbox and audit rows; once emitted in a
released build it cannot be renamed without a data migration. 03-RESEARCH.md logs the payload shape as
assumption A4: "`{character_id, status}` — a different field set is equally valid but is one-way once
emitted." This checkpoint exists so that choice is confirmed once, before Task 1 emits anything, rather
than discovered later in an audit table.

Same-schema note: both kinds share one payload schema var. The census forbids two COMMANDS sharing one
KIND; it does not forbid two kinds sharing a payload SCHEMA.
  </context>
  <options>
    <option id="option-a">
      <name>Kinds `character_retired` / `character_unretired`, payload `{character_id, status}`</name>
      <pros>Matches the naming of every existing character kind (`character_updated`, `character_deleted`, `character_moved`). `status` carries the new value so a consumer needs no second lookup, and the payload stays new-values-only and erasure-safe per the registry's own rule.</pros>
      <cons>Ships `status` redundantly on a kind whose name already implies it.</cons>
    </option>
    <option id="option-b">
      <name>Kinds `character_retired` / `character_unretired`, payload `{character_id}` only</name>
      <pros>Minimal wire surface; the kind name is the whole signal.</pros>
      <cons>A consumer that batches kinds must map kind-to-status itself, and the payload cannot later carry a reason or actor without a schema-version bump.</cons>
    </option>
