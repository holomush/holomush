<objective>
Give an owner the two edit surfaces: the prose `profile.*` fields and the
in-world `characters.description` column, both over typed RPCs, both with
server-enforced caps, and both guarded by `expected_version`.

Purpose: criterion 4. The description write MUST reach the shipped
`world.Service.UpdateCharacterDescription` rather than a parallel path, and the
profile write calls the domain command 04-09 adds.

Output: the two facade mutation handlers with the closed mask allowlist and the
byte-measured caps, and integration specs proving the row changed and exactly one
envelope committed.

**Scope note — the domain half moved to 04-09.** An earlier revision of this plan
carried a third task adding the `world.Service` profile-attribute write. That work
was under-sized by a whole layer: `world.Service.propertyRepo` is typed
`PropertyReader` (`service.go:104`) and pinned that way by
`TestServiceHoldsOnlyReaderViews` (`fence_test.go:34`), the write-capable
`PropertyRepository` lives only on `worldMutator`, and the world-envelope census
is bidirectional across three registration surfaces. It is now 04-09, at wave 2,
and this plan depends on it.

**Concurrency scope — read the second `must_haves` truth before writing Task 3.**
The profile path gets a genuine CAS. The description path gets a TOCTOU narrowing
only, because the shipped domain command takes no expected-version parameter. That
asymmetry is deliberate, is stated in the truths, and must not be papered over in
the tests.

**Scope addition — a pre-existing domain gap this plan must close (issue #4954).**
An earlier revision asserted that the description write "inherits that path's
validation". It does not, at HEAD. `internal/world/service.go:862` is a bare
`char.Description = description`; `mutator.go:287-291` forwards `char` to
`characterWriter.Update`; `internal/world/postgres/character_repo.go:149-158`
interpolates `char.Description` straight into the UPDATE. `ValidateDescription`
is reachable only from `Character.Validate` (`character.go:124`) and
`Character.SetDescription` (`character.go:102`), and NEITHER runs on that path —
`SetDescription` has zero production callers, though its own doc comment says
application code must use it. So today an over-cap description written through
that command lands in the column.

That is a real codebase bug, not merely a plan defect, and Phase 4 owns it:
ROADMAP criterion 4 requires over-cap input rejected **server-side**, and Task 3's
facade handler is forbidden from re-implementing the check. **Task 2 closes it in
the domain** before Task 3 consumes it. The sibling commands already have the
shape: `Service.UpdateLocation` validates at `service.go:367` before its write.
This is an omission specific to the character path, not a design choice.
</objective>
