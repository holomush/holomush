<objective>
Build the `owner` audience — `ListMyCharacters` and `GetMyCharacter` — on the
shared `playerGate`, and pin the reason the owner audience has to exist: the
`viewer:` principal stays strictly public-facing and never widens a
character-keyed grant to the player behind it.

Purpose: D-69 resolved Phase 2 D-27's deferred half by splitting the audiences
rather than relaxing the derived owner peer. That split is only safe while the
owner path never constructs a `viewer:` principal and the viewer path never
widens — and neither is enforced by anything today. This plan builds the owner
path and registers the invariant that keeps the widening from being reintroduced
as a one-line cleanup.

Output: the owner-audience handlers, `projectOwner`, the alt-linkage regression
test, and the invariant registry brought current.
</objective>

That is the tempting one-line "unification" and it is wrong: `resolveAndGate`
returns `PermissionDenied` for every guest (`sceneaccess_service.go:144-146`,
INV-SCENE-64), so routing `GetCharacterProfile` through it would delete the guest
rung the profile tier model is built on. The owner audience uses `resolveAndGate`;
the public audience uses `resolveViewerIdentity`; they answer different questions
and both stay.

Create `internal/grpc/characteraccess_owner.go` with `ListMyCharacters` and
`GetMyCharacter`.

Gate ordering is the shipped one: `resolveAndGate` first, then `ownedCharacter`
for the single-character read. Both handlers MUST NOT construct a `viewer:`
principal at any point — not for the property enumeration, not for a fallback,
not for a convenience view of the caller's own public profile (D-69). The owner
reaches their own private profile fields through this audience precisely so the
multi-alt asymmetry in the derived owner peer never governs a path anyone depends
on. When enumerating properties for the owner, pass
`world.HumanCaller(access.CharacterSubject(...))` for the owning character's
subject so the grid-side row-keyed policies decide.

Add `projectOwner` to `internal/grpc/characteraccess_projection.go` as the sole
constructor of `OwnCharacter` (01-SPEC section 2.3 — three projection functions,
one per audience, and no handler builds a character-shaped message by struct
literal). It carries the owner-only operational fields and the lifecycle status
that `PublicCharacter` structurally cannot hold. Like `projectPublic`, it omits a
field it has no value for rather than emitting a present-and-empty one.

Do not add a self-detection branch to `GetCharacterProfile`. That RPC returns an
identical projection regardless of who is viewing (D-70): the public profile is
genuinely public, which is also the only way an owner can verify what they are
publishing, and a response whose shape varies by viewer identity is itself the
disclosure channel 01-SPEC section 8.7 exists to close.
