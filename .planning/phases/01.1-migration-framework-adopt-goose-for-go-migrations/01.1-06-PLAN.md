<objective>
Prove criterion 4 — a Go migration registered between two SQL migrations runs in version order and
observes the prior SQL step's effect — and establish the D-08 package seam Phase 2's backfill lands
in, with a guard for the registration hole goose itself cannot see.

Purpose: Phase 2's execution is gated on this capability (D-20/D-21). Proving it on a fixture chain
that mirrors D-21's exact shape (SQL creates the column → Go backfills → SQL `SET NOT NULL` before
the unique index) means Phase 2 inherits a demonstrated mechanism rather than an assumption. The
registration guard exists because `//go:embed migrations/*.sql` never embeds `.go`, so goose's own
"unregistered Go migration" guard cannot fire here — a Phase-2 file that forgets its `init()` is
silently absent from the chain, and every test passes.

Output: the C4/C4b fixture chain, `package migrations` with its blank import, a registration meta-
test, and INV-STORE-11.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Go migration code -> the production schema | a Go migration executes arbitrary Go inside a transaction with DDL authority; unlike SQL it is not reviewable as a static body |
| the goose global registry -> the applied chain | a Go migration is present only if its `init()` ran; the embedded FS cannot corroborate it |
| fixture migrations -> the real corpus | a fixture written into `internal/store/migrations/` would be swept by three separate corpus-wide checks and could reach a real database |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.1-26 | Tampering | a Go migration silently absent from the chain | high | mitigate | `migrations_register_test.go` enforces `init()` registration on every versioned `.go` file, with a pure table-driven core so the guard is non-vacuous while the corpus is empty. goose's own unregistered-Go guard provably cannot fire here (`provider_collect.go:129-147` depends on the file being visible to the source collector, and the embed globs `*.sql`). Registered as INV-STORE-11. |
| T-01.1-27 | Tampering | a non-transactional Go migration applying partially | high | mitigate | `AddMigrationContext` (transactional) is the default; `AddMigrationNoTxContext` requires a `// goose-no-tx: <reason>` comment enforced by the same guard. D-22's collision rollback holds only inside a transaction, so this is a correctness requirement, not a style rule. |
| T-01.1-28 | Tampering | fixture SQL reaching the real corpus | medium | mitigate | The fixture chain is written to a temp dir and served via `os.DirFS`; `WithDisableGlobalRegistry(true)` keeps the real registry out; an acceptance criterion greps for new files under `internal/store/migrations/`. |
| T-01.1-29 | Repudiation | an irreversible down that silently succeeds | medium | mitigate | C4b asserts the down FAILS and that the version remains recorded as applied. A silent no-op down lets an operator run `migrate down`, see success, and believe state reverted — a false guarantee is worse than a refusal (D-09). |
| T-01.1-30 | Denial of service | `//go:embed` failing against a subpackage directory | medium | mitigate | Verified by `task build` immediately after `doc.go` lands, before the guard is written, so a broken D-08 seam surfaces at its cheapest point. Recorded in the SUMMARY either way rather than assumed. |
</threat_model>
