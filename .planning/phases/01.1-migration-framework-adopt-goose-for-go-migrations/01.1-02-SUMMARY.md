## The negative control (required evidence)

A rename would have been the obvious fix and would have been wrong. Under goose a migration is a
SINGLE file carrying both bodies, so handing the whole file to `db.Exec` runs the **down** body
too. Before the accessor existed I pointed the 000053 idempotency spec at the merged
`000053_sessions_location_index.sql` and ran it. The exact failure:

```
• [FAILED] [0.437 seconds]
Migration 000053 sessions location index [It] re-applies the migration's own SQL cleanly when the index already exists

  [FAILED] the index MUST be restored before this spec returns
  Expected
      <string>:
  not to be empty
  In [It] at: internal/store/migrations_sessions_location_index_integration_test.go:196
```

The spec's own final restore step created the index and then dropped it again in the same `Exec`.
The 000052 spec would have done the same to the partitioned parent it had just probed. That
sentence is now in `MigrationSectionForTest`'s docstring, verbatim, because a reader who deletes
it reintroduces the bug.

pgx v5's `Exec` with zero arguments uses the simple query protocol, so a multi-statement merged
file executes silently rather than erroring — which is precisely why this is a *silent*
destructive path rather than a loud one.

## The bookkeeping spec goes RED on the threat it exists for (T-01.1-09)

A row count cannot tell the real corpus from 44 phantom rows filling the unused 21–29 version gap.
I proved the set-equality assertion is the load-bearing half by tampering with the ledger after
`Up()` — deleting real version 53 and inserting a phantom 25, which keeps **all three counts
correct**:

```
[FAILED] the recorded version set MUST equal the embedded version set — a matching count with
different members (e.g. phantom rows filling the unused 21–29 gap) is exactly what this
comparison exists to catch
  Expected
      <string>: "...2,20,25,3,3..."
  to equal               |
      <string>: "...2,20,3,30,3..."
```

The three count expectations (44 at `version_id > 0`, 45 total, `min(version_id) = 0`) all
**passed** under that tamper and only the set equality failed. That is the whole argument for
writing it as set equality, demonstrated rather than asserted.

The embedded side is read via `migrator.PendingMigrations()` **before** `Up()`, on a blank
database, so it is the corpus as the filesystem describes it — derived independently of the ledger
the assertions read back. A precondition asserts it holds 44 entries, so an empty expectation
cannot make the comparison vacuously true.

The `schema_migrations` absence check carries a paired positive control
(`to_regclass('public.goose_db_version') IS NOT NULL`) in the same query. Without it, a typo in the
table name would make the absence assertion pass against any database.

## Deviations from plan

**1. [Rule 1 — Bug in the plan's criterion] `rg -c 'golang-migrate' internal/store/` cannot and
should not return 0.**

Two problems. First, mechanically: `rg -c` prints nothing and exits 1 on zero matches, so the
criterion as phrased can never be *observed* to succeed. Second, and the real issue: 15 references
survive in `internal/store/`, and **every one is deliberate historical or contrastive rationale
landed by plan 01**, not a stale claim that golang-migrate is in use:

| Site | What it says |
|---|---|
| `migrate.go:150` | why `goose.ErrNoNextVersion` is treated as success — "the analogue of golang-migrate's ErrNoChange, which this wrapper has always treated as success" |
| `migrate.go:220` | why the `dirty` return value is retained despite goose having no dirty state |
| `migrate.go:50,76` | why `provIface` exists and why the `pgx5://` scheme rewrite is gone |
| `migrate_embed_test.go:45` | the **failure message** on the gate that forbids split files |
| `migrate_test.go:26,95,174,227,263` | contrastive rationale on five unit tests |

Deleting these deletes the reasons behind live design decisions. `internal/store/migrate.go` is
also not in this plan's `files_modified`. I did not delete them.

The honest property the criterion was reaching for — *nothing describes golang-migrate as the
current engine* — holds, and has a mechanical gate that actually works:
`! rg -q -- 'golang-migrate/migrate' internal/ cmd/ go.mod go.sum` exits 0 (no live import, no
dependency). **A reviewer should confirm my reading of the 15 sites rather than take it on
trust.**

**2. [Rule 1 — same class] The `.up.sql`/`.down.sql` criterion holds for path reads, not for
prose.** `rg -n '\.up\.sql|\.down\.sql' internal/store/*_test.go` returns two hits, both in
`migrate_embed_test.go:23,25` — the doc comment on the test whose whole job is to assert those
names are **gone** (it carries `regexp.MustCompile(`\.(up|down)\.sql$`)` as a negative gate).
Removing the prose would strip the rationale from the guard that enforces the criterion. The
criterion's intent — no test constructs a migration path from those suffixes — is met, verified
with a gate that excludes comment lines:
`rg --no-filename -- '\.up\.sql|\.down\.sql' internal/store/*_test.go | rg -v '^\s*//'` → empty.

**3. [Plan deviation, deliberate] `runMigrations` threads ctx via a pre-flight `pool.Ping(ctx)`,
not through the migration itself.** The plan's truth says ctx is "threaded rather than discarded".
`Migrator.Migrate(uint)` takes no context by design (plan 01 kept the whole method set
context-free), and `internal/store/migrate.go` is not in this plan's scope, so a genuinely
context-bounded migration would have been a production-surface change. `pool.Ping(ctx)` makes ctx
load-bearing for real — a caller whose deadline has expired now fails with its own context error
instead of blocking — and the doc comment states plainly what ctx does *not* bound. Removing
`_ = ctx` without using ctx was not an option: revive's `unused-parameter` is enabled and not
excluded for test files, and renaming the parameter to `_` would have changed the `func` line the
plan requires to stay byte-identical.

`git diff main -- internal/store/testhelpers_test.go` shows no change to the `func` line; all ~12
call sites are untouched.

**4. [Structure] The accessor's unit tests live in a new file, `migrations_section_test.go`, not in
`migrations_export_test.go`.** `files_modified` named only the latter. `export_test.go` files are
conventionally seams only; splitting keeps that. The new file is `package store` with **no** build
tag, so it runs under plain `task test` — an integration tag would have hidden it from the lane
that actually runs it.

## What the accessor does and does not guarantee

It returns the text between `-- +goose Up` and `-- +goose Down` (or after `-- +goose Down`), with
every `StatementBegin`/`StatementEnd` marker line removed so the result is directly `Exec`-able.
The marker stripping is asserted against 000052 — zero markers remain and `DO $$` survives intact,
across all 9 wrapped blocks.

A missing `Up` or `Down` annotation is an **error**, never a whole-file fallback, and both error
paths plus the unknown-direction and unknown-file paths are covered. Annotation matching tolerates
leading whitespace and the spacing after `--`, matching goose's own lenient parse.

It stays in `package store`, in a `_test.go` file, with **no** build tag. That exact combination is
what lets `store_test` specs reach the unexported `migrationsFS` without widening the production
surface, and what lets both untagged and integration-tagged consumers use it (T-01.1-10).
`MigrationSQLForTest` is retained and is still live — the new accessor calls it.
