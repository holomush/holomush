### C4 — Go migration between two SQL migrations, in version order

This is the capability the phase exists to deliver, and it is the best-evidenced criterion in the phase.

`internal/store/migrate_gointerleave_integration_test.go` builds a SQL(1) → Go(2) → SQL(3) fixture chain in a testcontainer, with the fixture SQL written to `suiteT.TempDir()` and **never** under `internal/store/migrations/` (the file says why: that directory is swept by the format meta-test, `lint:no-timestamptz`, and `test/meta/world_sql_fence_test.go`).

**Order is asserted, and asserted twice — the specific trap named in the verification brief is closed:**

1. `sourceVersions(provider.ListSources())` must equal `["sql:1", "go:2", "sql:3"]` **before anything is applied**. The comment states the reason: an apply-order-only assertion passes even when goose collected the Go step last and merely executed it in a lucky sequence.
2. `resultVersions(results)` from `provider.Up(ctx)` must equal the same sequence — "the APPLIED sequence, not just the end state — a chain that ran 1,3,2 would reach the same schema".

**Data dependence on the prior SQL step is asserted, not inferred:** `observedRows` is captured out of the Go migration's closure and initialised to `-1` — a sentinel chosen so that "the Go step never ran" is distinguishable from "ran and saw nothing". It must equal 2, the count migration 1 inserted. The test asserts the count the Go step **READ**, not merely the rows it wrote.

**The chain is Phase 2's exact D-21 shape**, and migration 3 puts `SET NOT NULL` *before* `CREATE UNIQUE INDEX` for a load-bearing reason recorded in the source: Postgres treats NULLs as distinct, so a unique index over an unbackfilled nullable column succeeds and enforces nothing — a green deploy with the guarantee silently absent. `SET NOT NULL` first converts the Go step's execution into a hard precondition.

**The spec was FALSIFIED, twice, and the results recorded** (`01.1-06-SUMMARY.md`):

- Setting `goInterleaveGoVersion = 4` → source assertion RED: `["sql:1","sql:3","go:4"]` vs `["sql:1","go:4","sql:3"]`.
- Because that assertion short-circuits, it alone proves the assertion *observes* order but not that order is *load-bearing*. The source assertion was then neutered and the run repeated → `partial migration error (type:sql,version:3): ERROR: column "normalized_name" of relation "gointerleave_names" contains null values (SQLSTATE 23502)`. Both temporary edits reverted; `rg 'TEMPORARY-RED-EXPERIMENT' internal/store/` returns no hits (confirmed by me).

**C4b (D-09) irreversible down** — asserted by error **identity** (`errutil.AssertErrorCode`, which walks past goose's `*PartialError` via `Unwrap`), not a message substring; and the refused version is asserted to remain recorded, so a refusal cannot also rewind the ledger.
