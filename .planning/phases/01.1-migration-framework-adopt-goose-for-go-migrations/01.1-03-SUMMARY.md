# Phase 01.1 Plan 03: Format and lint guards Summary

Both silent-failure modes this phase introduced now have a check that has been **observed failing
against the broken state**, and both run in the untagged `task test` lane that gates every PR: an
unwrapped `DO $$` body is named by file and line, and a `lint:no-timestamptz` glob that matches
nothing fails at authoring time instead of reporting clean.

## What this plan is the durable answer to

Plan 01 recorded that the byte-equality re-split proof **cannot see annotation placement** — it
strips `StatementBegin`/`StatementEnd` by design, so stripping one still made the prover exit 0.
Plan 01 covered that gap with one-off structural checks that are now gone. `statementBlockViolations`
is what makes that coverage permanent, and it is deliberately scoped to exactly what the
byte-equality proof cannot do: it says nothing about SQL content and everything about whether a
dollar-quoted region sits inside a wrap.

The scanner is **pure** (`name, body string` in, `[]string` out). That is the whole reason a RED was
demonstrable without editing a real migration on disk — the alternative risks leaving the corpus
corrupted, which is a poor trade for evidence.

## Observed baseline census — recorded, NOT asserted

| Measure | Value |
|---|---|
| Files carrying at least one `StatementBegin` wrap | 9 |
| `StatementBegin` / `StatementEnd` totals | 24 / 24 (balanced) |
| Files matching the dollar-quote tag pattern | 9 (identical set) |

Deliberately not an assertion. Pinning it would turn every future legitimate `$$` migration into a
spurious failure — the opposite of what the guard is for. `! rg -q -- '\b(9|17|24|44)\b'
internal/store/migrations_format_test.go` exits 0, so no census literal leaked into the file.

That the tag-matching set and the wrapped set are the **same 9 files** is the corpus-level statement
the guard makes: every dollar-quote in the tree is inside a wrap, and every wrap contains one.

## The bcrypt false positive, covered as a first-class case

`\$([A-Za-z_][A-Za-z0-9_]*)?\$` requires an identifier start. Against
`'$2a$10$N9qo8uLOickgx2ZMRZoMye'` (`000001_baseline.sql:390`) every candidate fails: `$2a$` and
`$10$` have digit-leading tags, and `$N9qo8uLOickgx2ZMRZoMye` has no closing `$`. The naive
`\$[A-Za-z0-9_]*\$` matches `$2a$` and would report line 390 — worse, a *converter* using it would
wrap that line and swallow the rest of the baseline's semicolons into one statement. That reasoning
is in the pattern's docstring, and the case is in the table so deleting the docstring does not delete
the coverage.

## Why static, not a shell-out (restated because it is the whole design)

`task lint:no-timestamptz` cannot distinguish "no violations" from "the glob matched no files": a
`for` loop over zero files runs zero iterations, counts zero violations, and exits 0. A shell-out
therefore **passes the exact failure mode the test exists to catch**. Both new docstrings say this
plainly, alongside the sibling test's second reason — the unit-test CI job has no `rg` on PATH, so a
shell-out would no-op there regardless.

`soleTaskfileLoopGlob` fails on **more than one** matching loop as well as zero. A pin that silently
attaches to the wrong loop is the same class of defect as one that matches nothing.

## Deviations from plan

**1. [Rule 3] The D-13 docstring cannot spell the build-tag token.** Task 1's acceptance criterion is
`rg -n 'go:build' internal/store/migrations_format_test.go` returns zero hits, but the plan's own
`<action>` asks the docstring to explain *why the file carries no tag* — and the natural sentence
contains the token. First draft failed the criterion at line 166 on its own explanation. Reworded to
"carries NO build constraint … and MUST NOT grow one", with a parenthetical stating why the token is
left unspelled. Rationale preserved, criterion met, and no future text gate is defeated by the
sentence explaining the property it checks. (Same class as plan 02's Deviation 2, and resolved the
other way round because here the prose had a rewrite that keeps both.)

**2. [Addition, Rule 2] `soleTaskfileLoopGlob` rejects duplicate loops, which the plan did not ask
for.** The plan said "select the one line containing the prefix". Taking the *first* match would make
the pin silently guard whichever loop happened to come first if a second were ever added — a pin not
observing its subject. Fails with a distinct message naming the count and the globs found.

**3. [Addition] A fifth RED was demonstrated.** The plan requires four. The non-vacuity assertion is
itself a gate, and this phase has already produced four instances of gates that pass while testing
nothing, so it was shown red too (RED 3 above).

No architectural decisions were reached and no checkpoint was hit; the plan ran fully autonomous.
