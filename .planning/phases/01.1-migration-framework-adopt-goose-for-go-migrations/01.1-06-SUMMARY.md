# Phase 01.1 Plan 06: Go/SQL Interleave + the D-08 Package Seam Summary

A Go migration running in version order between two SQL migrations, observing the prior
SQL step's rows inside its own transaction, proven end-to-end on a chain shaped exactly
like Phase 2's D-21 sequence — plus `internal/store/migrations/` turned into a real Go
package whose registration requirement is mechanically enforced from both ends.

## Task 1 — the interleave proof

`internal/store/migrate_gointerleave_integration_test.go` builds a three-step fixture in
`suiteT.TempDir()`, served via `os.DirFS`, with the Go step supplied through
`WithGoMigrations` and `WithDisableGlobalRegistry(true)`. Nothing permanent entered the
real 44-migration chain (D-07), and `git status --porcelain` showed no new file under
`internal/store/migrations/` at any point.

The chain is the D-21 shape: (A) SQL creates `normalized_name` **nullable** and seeds two
rows leaving it NULL; (B) the Go step at version 2 reads those rows and backfills; (C) SQL
applies `SET NOT NULL` **then** `CREATE UNIQUE INDEX`.

Six things are asserted, and the split between them is the point:

| Assertion | What it rules out |
|---|---|
| `ListSources()` order **before** applying | goose collected the Go step last and merely executed it in a lucky sequence |
| applied-result order **after** | a chain that ran 1,3,2 and reached the same end state |
| the row count the Go step **read** (`observedRows == 2`) | ordering without data dependence — this is the property Phase 2's backfill needs |
| `is_nullable = 'NO'` after v3 | (corroboration only; see below) |
| `DownTo(2)` succeeds | — |
| `Down()` from v2 **fails** with its oops code, and v2 is **still recorded as applied** | C4b/D-09: a silent no-op down telling an operator state reverted when it did not |

`observedRows` initialises to `-1`, not `0`, so "the Go step never ran" cannot be confused
with "ran and saw nothing".

Error identity via `errutil.AssertErrorCode(suiteT, downErr, ...)` rather than a Gomega
substring. goose's `*PartialError` implements `Unwrap` (`provider_errors.go:46`), so
`oops.AsOops` walks past it to the fixture's code. `suiteT` is used because `testing.TB`
has an unexported method and `GinkgoT()` therefore cannot satisfy it — the same shape plan
04 used at `migrate_adopt_integration_test.go:351`.

### Falsifiability — the version move (requested by the plan)

`goInterleaveGoVersion` is a named constant precisely so this experiment is one edit.
Setting it to 4:

```
[FAILED] goose must interleave the fixture-supplied Go migration between the two SQL sources by version
Expected
    <[]string | len:3, cap:3>: ["sql:1", "sql:3", "go:4"]
to equal
    <[]string | len:3, cap:3>: ["sql:1", "go:4", "sql:3"]

Ran 1 of 33 Specs in 0.016 seconds
FAIL! -- 0 Passed | 1 Failed | 0 Pending | 32 Skipped
```

The source assertion fires first and short-circuits, so on its own it proves the assertion
observes order but **not** that order is load-bearing. Neutering the source assertion and
re-running with the Go step still at version 4 produced the behavioural consequence:

```
[FAILED] Unexpected error:
    <*goose.PartialError | 0x343497486210>:
    partial migration error (type:sql,version:3): ERROR: column "normalized_name" of
    relation "gointerleave_names" contains null values (SQLSTATE 23502)
    {
        Applied: [ { Source: { Type: "sql", Path: "000001_create_interleave_fixture.sql",
                     Version: 1 }, Direction: "up" } ] ...
```

That is exactly why D-21 puts `SET NOT NULL` before `CREATE UNIQUE INDEX`: it converts the
Go step's execution into a hard precondition of migration 3. A unique index alone would
have **succeeded and enforced nothing**, because Postgres treats NULLs as distinct — a
green deploy with the guarantee silently absent. Both temporary edits were reverted;
`rg -n 'TEMPORARY-RED-EXPERIMENT' internal/store/` returns no hits.

### Proving the spec EXECUTED, by exit code

`gotestsum --format pkgname` suppresses output on success, so green alone shows nothing
about whether the focus matched. Judged by exit code instead, with its own control:


honoured, so exit 0 on the first genuinely means specs ran.

## Task 2 — the D-08 seam and the registration hole

### The embed question, settled by execution

`task build` exit **0** with `internal/store/migrations` as a Go package. `//go:embed
migrations/*.sql` resolves fine against a directory that is itself a package — verified
immediately after `doc.go` landed and before the guard was written, as the plan required,
so a broken seam would have surfaced at its cheapest point. It did not.

### What the guard covers, and the hole the plan did not name

`goMigrationRegistrationViolations(name, body string) []string` is AST-based
(`go/parser` with `ParseComments`) rather than textual. That is not polish: a registration
sitting inside a comment, or parked in a helper that nothing calls, is exactly the shape a
`strings.Contains` scan reports as present. The goose identifier is resolved from the
file's own import block, so an import alias does not evade it.

Eight synthetic cases (the plan asked for six; two were added):

| Case | Expected |
|---|---|
| versioned file, `init()` calls `AddMigrationContext` | clean |
| same, `init()` removed | 1 violation |
| **added:** same, registration commented out inside `init()` | 1 violation |
| `AddMigrationNoTxContext` **with** `// goose-no-tx: <reason>` | clean |
| `AddMigrationNoTxContext` **without** it | 1 violation |
| `doc.go` (no version prefix) | clean, not treated as a migration |
| `helpers_test.go` | skipped |
| **added:** versioned file that does not parse | 1 violation |

**The hole the plan's guard would have left open.** The plan's guard enforces that each
versioned `.go` file registers *itself*. It does not check that anything runs those
`init()`s at all — and the blank import is the strictly easier thing to lose: a tidy pass,
an unused-import sweep, or an editor removing an import with no referenced symbols all
reach it, and none of them touch the migration files. Both failures have the identical
signature (silent absence, green suite), so
`TestExactlyOneBlankImportWiresTheMigrationsPackageIntoStore` was added as a Rule 2
deviation. It is a static AST scan because there is nothing to observe at runtime: with
zero Go migrations registered, an intact blank import and a deleted one produce
byte-identical behaviour.

### RED demonstrations — all three by exit code

**A. The corpus walk fires on an unregistered migration.** A temporary
`internal/store/migrations/000099_red_experiment.go` whose `goose.AddMigrationContext` call
sits in a `register()` helper rather than `init()` (it compiles — Go does not reject unused
functions, which is why this hole is reachable):

```
=== FAIL: internal/store TestGoMigrationRegistrationHoldsAcrossTheMigrationsCorpus (0.00s)
    Error: Should be empty, but was [000099_red_experiment.go: no goose.AddMigrationContext
    registration in init() — a Go migration joins the chain only when its init() registers
    it, and `//go:embed migrations/*.sql` never embeds .go, so goose's own unregistered-Go
    guard cannot fire here. ... See INV-STORE-11.]
    migrations_register_test.go:309: scanned 2 .go file(s) in migrations/, of which 1 are
    versioned migrations
```

**B. The blank-import guard fires when the wiring is removed.** `migrations_register.go`
moved aside:

```
=== FAIL: internal/store TestExactlyOneBlankImportWiresTheMigrationsPackageIntoStore (0.00s)
    Error: "[]" should have 1 item(s), but has 0
    Messages: expected exactly one blank import of
    github.com/holomush/holomush/internal/store/migrations in package store, found 0 ([]).
    Zero means every Go migration's init() stops running and they vanish from the chain
    SILENTLY — goose applies the SQL corpus, counts are correct, and the suite passes.
```

**C. Non-vacuity on an empty scan.** With both `doc.go` and the blank import moved aside,
`migrations/` holds zero `.go` files and the floor fires rather than reading as clean:

```
=== FAIL: internal/store TestGoMigrationRegistrationHoldsAcrossTheMigrationsCorpus (0.00s)
    Error: "0" is not positive
    Messages: no .go file found in migrations/ — the scan is vacuous, not clean;
    migrations is a Go package (D-08) and must contain at least doc.go
    migrations_register_test.go:309: scanned 0 .go file(s) in migrations/, of which 0 are
    versioned migrations
```

An intermediate observation worth recording: removing `doc.go` **alone** does not reach the
floor — `migrations` stops being a package and the blank import breaks the build outright
(`no required module provides package .../internal/store/migrations`). So while the blank
import exists, an empty-directory scan is unreachable in practice; the floor is the
belt-and-braces for the case where both go.

The table cases carry the rest of the non-vacuity argument by construction: the four cases
with `wantCount: 1` use `require.Len(t, got, 1)`, which cannot pass against a scanner that
returns nil. A stubbed predicate turns four subtests red without any corpus involvement.

All temporary files were removed and all moved files restored; `git status --porcelain`
afterwards showed only the four intended new files.

### INV-STORE-11 — shipped `binding: pending`, and why, when `bound` passed

This is a judgement call and it went the conservative way, so the reasoning is recorded in
full.

`binding: bound` with `asserted_by` and a `// Verifies: INV-STORE-11` annotation above the
corpus walk was tried first. The registry meta-tests **accepted it** — `task test --
-run 'TestEveryRegistryInvariantHasBinding|TestProvenanceGuard|TestBoundInvariantsAreGenuinelyAsserted'
./test/meta/` exited 0, 7 tests.

It was nonetheless reverted to `pending`. `TestBoundInvariantsAreGenuinelyAsserted` rejects
only Skip-only placeholders; `.claude/rules/invariants.md` states outright that it "cannot
detect a *partial* binding (a test that asserts only one clause of a multi-clause
invariant — that needs human review)". INV-STORE-11 has two clauses:

1. every versioned `.go` file registers itself in `init()` — applied to a corpus holding
   **zero** such files, so this half cannot currently fail;
2. `package store` blank-imports the directory — genuinely asserted, demonstrated RED (B).

Half a binding is the exact false-green the rule exists to prevent, so the entry is
`pending`, carries no `asserted_by`, and no `// Verifies:` annotation is claimed. The YAML
comment records that `bound` was tried and accepted, so nobody re-derives this. Coverage
issue filed: **holomush/holomush#4906**. Phase 2's `000055` is the first file that makes
the walk bite; flipping to `bound` then is a one-line change.

`owned_paths` gained `migrations_register.go` and `migrations_register_test.go`
(`internal/store/migrations/**` already covered `doc.go`). `docs/architecture/invariants.md`
was regenerated with `go run ./cmd/inv-render` — never hand-edited.

## Deviations from Plan

### 1. [Rule 2 — Missing critical functionality] The blank import was unguarded

Covered above. `TestExactlyOneBlankImportWiresTheMigrationsPackageIntoStore` added.
**Commit:** `ebb78afc1`

### 2. [Rule 1 — Bug] revive `blank-imports` rejected the justification's placement

The first `migrations_register.go` used a bare `import _ "..."` with the justification
above the `import` keyword. revive flagged it: on a non-parenthesized import the doc
comment attaches to the `GenDecl`, not the `ImportSpec`, so revive sees an unjustified
blank import.

```
internal/store/migrations_register.go:24:8: blank-imports: a blank import should be only in
a main or test package, or have a comment justifying it (revive)
```

Fixed properly by moving to a parenthesized block with the comment on the spec — the repo's
own precedent at `migrate.go:20-21` for the pgx driver import. **No `//nolint` was added
and `.golangci.yaml` was not touched.**

### 3. Two extra table cases

`commented-out registration` and `does not parse`. The first is the mention-vs-invoke case
that motivated the AST approach; leaving it untested would have made the choice of
`go/parser` over `strings.Contains` an unverified preference.

### 4. Plan factual note (non-blocking)

The plan cites `errutil.AssertErrorCode` at "14 times in `migrate_test.go`, 29 across
`internal/store/`". Plan 04's summary already corrected these to 12 and 27 by occurrence.
Either way the conclusion the plan drew from them is right: it is the in-package precedent
for error identity, and it was used.
