# Phase 01.1 Plan 04: Adopt Gate Summary

The one-shot golang-migrate → goose bookkeeping cutover, seeding `goose_db_version`
ascending from the embedded FS inside an advisory lock, with both negative controls and the
ordering regression guard demonstrated RED — and one genuine defect caught by those specs.

## Task 1 — checkpoint decision

**Resolution: `option-a`.** Adopt fires from `Migrator.Up()` only. The read-only verbs
(`migrate status`, `migrate version`) do not trigger it.

Confirmed grounding: `cmd/holomush/migrate.go` registers five verbs, and the read paths at
`:35,40` (`Version()` → `PendingMigrations()`), `:72,82` (`Version()` → `AppliedMigrations()`)
and `:207,221` (`Version()`) genuinely reach the bookkeeping table.

### The derivation asymmetry, restated

golang-migrate recorded a **single current version, never the applied set**, so the set has to
be inferred from the embedded filesystem — there is no other source. The inference is
one-directional:

- **Seeding only the recorded high-water version is the unrecoverable direction.**
  `gooseutil.UpVersions` treats every filesystem version below the database's maximum that is
  not recorded as *missing* — a hard error without `-allow-missing`, and a re-application with
  it. Recording only 53 would make goose offer to re-run the other 43 migrations against a
  database where they are already applied.
- **Over-seeding is comparatively harmless.** Versions present in the database but absent from
  the filesystem are silently ignored.

So the seed enumerates all 44 versions and never derives from the single recorded value.

### Queued for plan 07 (operator docs)

> **`migrate status` / `migrate version` against a not-yet-adopted database report version 0
> with 44 pending.** This is expected, not a fault: adopt runs only from `Up()`, so goose's
> ledger is still empty when a read-only verb inspects it. The reading is corrected by the
> first `holomush migrate up` (or the startup auto-migration). Document alongside the D-18
> rollback window in `sandbox-restore.md`.

A second, sharper operator note also belongs there, from the defect below: **running
`migrate status` first is safe** — it creates an empty ledger, but adopt now tops that up
rather than treating it as a completed cutover.

## What was built

`internal/store/migrate_adopt.go` — probe → in-lock emptiness re-check → dirty refusal →
one transaction (create table via `database.Store.CreateVersionTable`, version-0 row, the
derived set **ascending**, `ALTER TABLE ... RENAME`, INFO log, commit).

`Migrator.Up()` returns adopt errors **unwrapped**, so the `MIGRATION_ADOPT_*` code stays the
top-level code. `errutil.AssertErrorCode` reads the top-level code via `oops.AsOops`, so
re-wrapping in `MIGRATION_UP_FAILED` would have made C2c's identity assertion impossible.

## Deviations from Plan

### 1. [Rule 1 — Bug] `migrate status` could permanently disable the cutover

**Found during:** Task 3, C2a. This is the most important finding in the plan.

goose's `ensureVersionTable` (`provider_run.go:331`) runs on **any** versioned operation,
including the read-only ones, and creates `goose_db_version` complete with its version-0
bootstrap row. My first implementation treated *any* row as "already adopted".

Consequence: an operator running `holomush migrate status` on a not-yet-adopted database —
precisely the diagnostic the option-a decision expects them to run before deploying — left
behind an empty-but-existing ledger. The next `Up()` then skipped adopt, found an empty
ledger, and re-ran all 44 migrations against a database that already had the schema:

```
partial migration error (type:sql,version:1):
ERROR: relation "holomush_system_info" already exists (SQLSTATE 42P07)
```

**Fix:** the seeded probe filters on `version_id > 0`; the bootstrap row is inserted only when
absent, so a prior read cannot produce a duplicate version-0 row.
**Pinned by:** a dedicated spec, "still adopts when a status-style read has already created the
ledger", carrying its own positive control (asserting the read really did leave exactly `[0]`).
**Commit:** `3f55da8e1`

Note this defect was reachable **only** because option-a leaves a window between the read and
the adopt. It is not an argument against option-a — option-b would have made the read itself
perform the irreversible write — but it is the concrete hazard that window creates, and it is
now closed and guarded.

### 2. [Rule 2] Added `MIGRATION_ADOPT_LOCK_FAILED`

The plan named four error codes. Lock acquisition failure fits none honestly; folding it into
`MIGRATION_ADOPT_PROBE_FAILED` would have mislabelled it. Added as a fifth.

### 3. [Rule 3] Fixture builds a real schema rather than a bare ledger

The plan's C2a/C2d read as "hand-create `schema_migrations` on a raw database". That cannot
support C2d: a blank database has no tables to roll back, so `Down()` succeeds regardless of
the order it walks, and the ordering guard would prove nothing. `newPreConversionDatabase`
therefore migrates for real, then rewinds the bookkeeping — which is also what a production
database actually looks like on cutover morning.

### 4. [Rule 3] `AdoptForTest` seam added

The plan's "seed at 17, assert the derived maximum is 17" is unobservable through `Up()`,
because the provider immediately applies 18–53 and moves the boundary being asserted. A narrow
`export_test.go` seam runs adopt in isolation. Follows the existing
`MigrationSQLForTest`/`MigrationSectionForTest` convention, including bare error returns.

### 5. RED demonstrated but not committed broken

TDD RED for Task 2 was a compile failure (`undefined: derivedSeedVersions`,
`undefined: errAdoptRefusedDirty`) — recorded below. RED and GREEN were committed together
rather than landing a build-broken commit, per the repo's bisect-safety convention and the
"`task lint` before committing" rule.

### 6. Plan factual drift (non-blocking)

The plan cites "14 sites in `migrate_test.go`, 29 across `internal/store/`" for
`errutil.AssertErrorCode`. Measured by occurrence: **12** and **27**. `DownTo(0)` is named in
the plan's C2d, but no `DownTo` method exists on `Migrator` — the surface is `Down()`,
`Steps(n)`, `Migrate(version)`. C2d uses `Down()`, which is itself `DownTo(ctx, 0)` internally
(`migrate.go:140`).

## Verification — negative controls

### The decisive one: DESCENDING seed

Seed loop temporarily reversed in `migrate_adopt.go`, full adopt focus re-run:

```
Ran 7 of 32 Specs in 8.138 seconds
FAIL! -- 1 Passed | 6 Failed | 0 Pending | 25 Skipped

[FAILED] ledger row 2 (version_id 52) was inserted after version_id 53: the seed ran
DESCENDING. Every count and set assertion still passes in this state; only rollback
order breaks. See INV-STORE-10.
Expected <int64>: 52 to be > <int64>: 53
```

Six of seven specs went RED. This run doubles as proof the specs **execute**: `gotestsum
--format pkgname` suppresses output for passing packages, so a green exit code alone would not
have shown that the focus matched anything.

### The behavioural consequence (plan's requested `partial migration error` text)

The ordering assertion fires before `Down()` is reached, so it alone does not prove the
property is *real*. With the seed still reversed and `assertStrictlyAscending` temporarily
neutered, `Down()` ran against the descending ledger:

```
[FAILED] a full rollback of the adopted database must complete; failure here means the
seed inserted in the wrong order
Expected success, but got an error:
    partial migration error (type:sql,version:2):
    ERROR: relation "characters" does not exist (SQLSTATE 42P01)
    Applied: [ { Source: { Path: "000001_baseline.sql", Version: 1 }, Direction: "down" } ]
```

`Applied` shows goose rolled back **version 1 first** — `ORDER BY id DESC` over a descending
seed yields *ascending* versions — dropping the baseline tables, after which version 2's down
failed. Exactly RESEARCH Pitfall 1, reproduced. Both temporary edits were reverted and
`rg 'TEMPORARY-RED-EXPERIMENT' internal/store/` returns no hits.

### Task 2 prohibition gates

Over the comment-stripped stream (`rg -v '^\s*//'`, 201 of 306 lines): `CREATE TABLE
goose_db_version`, `Sprintf|fmt\.Sprint`, `map\[`, and `slog\.(Info|Warn|Error|Debug)\(` are
all **absent**. Phrased as `! rg -q` rather than `rg -c ... == 0`, because `rg -c` prints
nothing and exits 1 on zero matches, so "returns 0" can never be observed to pass.

All four were then demonstrated RED against a synthetic file containing each shape, which also
confirmed the comment-stripping works (a commented-out DDL line was correctly removed while
the real one was still caught).

### Paired positive controls

- **C2b** asserts the *first* adopt populates the ledger (44+1 rows, ascending) before
  asserting the second changes nothing — otherwise an adopt that never worked would pass.
- **C2c** asserts `goose_db_version` is absent **and** `schema_migrations` retains its original
  name, with error identity via `errutil.AssertErrorCode` (top-level code, not a substring).
- **C2a** asserts the legacy table exists *before* `Up()`, so its later absence is a change
  this code caused.
- **The read-only-verb spec** asserts the read really left exactly `[0]` behind.

## INV-STORE-10 — shipped `binding: bound`

The plan flagged this as unproven ground ("no INV-STORE entry is bound today, and none binds
through Ginkgo") with a `pending` + coverage-issue fallback. **The fallback was not needed.**

The `// Verifies: INV-STORE-10` annotation sits above C2d, which genuinely asserts the ordering.
That the meta-test actually resolves it was verified, not assumed:

- Removing the annotation left `TestBoundInvariantsAreGenuinelyAsserted` **green** — but that is
  the test's designed behaviour (`isPlaceholderOnly` returns false for an empty set); absence of
  an annotation is not its concern. That control tested the wrong thing.
- The correct control: replacing C2d's body with a bare `Skip` produced

  ```
  invariant_registry_test.go:1200: INV-STORE-10: binding: bound but every // Verifies:
  site is a Skip-only placeholder with no assertion — false-green.
  ```

So the meta-test does resolve Ginkgo blocks and does classify this one. `bound` is genuinely
checked. `owned_paths` gained `migrate_adopt.go` and `migrate_adopt_integration_test.go`;
`invariants.md` was regenerated with `go run ./cmd/inv-render` (never hand-edited).
