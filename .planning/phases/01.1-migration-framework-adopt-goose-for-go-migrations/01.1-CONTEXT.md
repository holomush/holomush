# Phase 01.1: Migration framework — adopt goose for Go migrations - Context

**Gathered:** 2026-08-02
**Status:** Ready for planning

<domain>

## Phase Boundary

Replace `golang-migrate` with `pressly/goose` so a **Go migration can run interleaved, by
version, with the SQL ones** — the capability Phase 2's normalized-name backfill (D-21)
requires and golang-migrate structurally cannot provide.

**In scope:** converting the existing migration corpus to goose's single-file format; the
recorded-state cutover from `schema_migrations` to `goose_db_version`; preserving
`holomush migrate` CLI parity and startup auto-migration; proving Go/SQL interleaving;
updating the migration rule doc and meta-tests.

**Out of scope:** Phase 2's actual backfill, its DDL, and the duplicate-detection logic
(D-21/D-22 own those). This phase makes the mechanism possible and proves it; it does not
use it for real work.

</domain>

<decisions>

## Implementation Decisions

### Recorded-state cutover (`schema_migrations` → `goose_db_version`)

- **D-01:** The seeded row set is **derived from the embedded FS at cutover time**: read
  `schema_migrations.version`, then insert one row per embedded migration version `<=` that
  value. An up-to-date database yields **44** rows; a lagging one correctly yields fewer.
  Reuses the existing `allMigrationVersions()` (`internal/store/migrate.go:177`) and handles
  the `000021`–`000029` version gap for free, because it only ever inserts versions that
  exist. Rejected: a hardcoded 44-version list (drifts if a migration lands before the
  cutover ships, and assumes every database is fully up to date).
  - **Why the derivation matters:** golang-migrate records only a *single current version*,
    never the applied *set*, so the set must be inferred — there is no other source.
  - **The failure this avoids:** `gooseutil.UpVersions` treats any filesystem version below
    the DB's max that is not recorded as **missing** — a hard error without
    `-allow-missing`, and **re-applied** with it. Seeding only version `53` would therefore
    make goose offer to re-run 43 migrations. Conversely, versions present in the DB but
    absent from the filesystem are silently ignored, so over-seeding is comparatively
    harmless — the danger is strictly one-directional.
- **D-02:** Adopt is **automatic, guarded by the presence of both tables**: if
  `schema_migrations` exists AND `goose_db_version` is absent/empty, seed and then proceed,
  in one transaction. No operator step in any environment, and criterion 3's startup
  auto-migration keeps working unchanged. Fresh databases (CI, testcontainers, new deploys)
  have neither table and simply run all 44 normally, so adopt only ever fires against an
  existing golang-migrate database. Rejected: an explicit `holomush migrate adopt` verb.
  - **Accepted cost:** the one irreversible write happens **unattended at boot**. This is
    what raises the bar on D-03 and D-05, and what makes D-16's rehearsal load-bearing.
- **D-03:** The seed is wrapped in goose's **`WithSessionLocker`** (Postgres advisory lock),
  and re-reads `goose_db_version` emptiness **inside the lock** before seeding. The loser of
  a two-replica boot race sees a populated table and no-ops — satisfying criterion 2's
  "no-op or refuses". Preserves the concurrency protection golang-migrate's
  `database.Driver` `Lock()`/`Unlock()` provides today, which the swap would otherwise
  silently drop. Rejected: a bare transaction + emptiness check (two replicas can both read
  empty under READ COMMITTED); adding a `UNIQUE` index to `goose_db_version.version_id`
  (modifies goose's own bookkeeping table).
  - **The re-check inside the lock is the load-bearing part** — serializing alone does not
    make the second caller correct, it only makes it later.
- **D-04:** After seeding, the old table is **renamed to `schema_migrations_pre_goose`**
  inside the adopt transaction. Keeps the forensic record (the version cut over from, and
  the `dirty` value at that moment) while making it inert, so the previous binary cannot
  find a live table and start writing to it. Rejected: leaving it untouched (divergence if
  anyone rolls back *and* migrates with the old tool); dropping it (forces full restore for
  any rollback). — **Reversibility:** one-way — undoing it is a manual rename against a live
  database, and only valid within the single deploy window described in D-18.
- **D-05:** When `schema_migrations.dirty = true`, adopt **refuses and aborts boot**, naming
  the dirty version and pointing at the old tooling to resolve it first. A dirty flag means
  the recorded version describes a schema that was never fully applied — seeding from it
  records partially-applied migrations as applied, and goose has no way to detect that
  afterward. Matches the repo's default-deny posture and mirrors D-22's halt-and-report
  shape. Rejected: seeding up to but excluding the dirty version (its partial effects are
  still in the schema, so the re-run may fail mid-adopt, unattended); seeding it with a
  warning (defers judgement to logs nobody reads).
- **D-06:** Adopt performs **no schema verification** — it trusts the version, guarded only
  by D-05. Anything deeper is a schema-comparison engine to build and maintain, and a
  wrong-database mistake surfaces loudly at the first real query. A deliberate simplicity
  call: adopt stays small and readable, which is its own safety property for a one-shot
  irreversible step. Rejected: a cheap sentinel-object check; a full diff against a golden
  dump.
  - **Compensating control:** D-16's rehearsal against restored real data is where drift
    would surface instead. These two decisions are a pair — do not weaken D-16 without
    revisiting D-06.

### Go/SQL interleaving

- **D-07:** Criterion 4's interleaving proof is an **integration test with a fixture chain**
  — a small SQL→Go→SQL chain built in a testcontainer, asserting version order with the Go
  step observing the prior SQL step's effect. Nothing permanent is added to the real
  44-migration chain. Rejected: shipping a throwaway no-op Go migration (migrations are
  permanent and replay on every fresh database forever — buying a junk chain entry to
  satisfy a sentence); hunting for real Go-requiring work (no candidate identified in the
  tree, so it is a research task with a real chance of coming back empty).
  - **Requires a roadmap amendment** — see "Roadmap amendments" below.
- **D-08:** Go migrations live in the **same directory, mixed**:
  `internal/store/migrations/` holds both `000053_x.sql` and `000054_y.go` as package
  `migrations`, blank-imported by `internal/store` so `init()` runs. `//go:embed
  migrations/*.sql` is unaffected — it only globs `.sql`. One `ls` shows the whole ordered
  chain, which is what keeps version order obvious and reviewable. Rejected: a separate
  `gomigrations` package (splits the chain across two directories); registering from
  `internal/store` itself (decouples version from file location). — **Reversibility:**
  costly — moving them later touches the embed directive, the blank import, and every
  migration's package clause.
- **D-09:** A Go migration whose effect cannot be reverted has a **down that returns an
  error** naming why. A silent no-op down lets an operator run `migrate down`, see success,
  and believe state reverted when it did not — a false guarantee is worse than a refusal,
  and matches the repo's fail-closed posture. Rejected: a documented no-op down; forbidding
  irreversible work from being a migration at all (contradicts D-21, whose whole point is
  that the backfill MUST be a migration so ordering is framework-enforced rather than a
  runbook).
  - **Accepted cost:** any test that rolls the whole chain down needs an explicit floor
    version.
- **D-10:** Go migrations are **transactional by default** (`AddMigrationContext`);
  `AddMigrationNoTxContext` requires a comment naming the statement that forbids a
  transaction (e.g. `CREATE INDEX CONCURRENTLY`). This is not merely a style preference —
  **D-22 requires the backfill to roll back and leave the schema at the prior version on
  collision, which only holds inside a transaction.** Mirrors the existing SQL guidance in
  `.claude/rules/database-migrations.md`.

### Converting the corpus

- **D-11:** The 88 files become 44 via a **script plus a mechanical byte-equality proof**: a
  converter merges each pair (one SPDX header, `-- +goose Up` / `-- +goose Down`), flags
  every `$$`-containing body for explicit `StatementBegin`/`StatementEnd` wrapping, then a
  verification step re-splits each converted file and asserts byte-identity against the
  originals **before** they are deleted. Proves the transform across all 44 without anyone
  eyeballing 88 files. Rejected: script plus human-reviewed diff; hand-converting all 44.
  - **Why this is not a mechanical concatenation:** **17 of the 44 migrations contain
    `DO $$ … END $$;` idempotent guards.** goose's default splitter breaks on semicolons, so
    each of those 17 needs `StatementBegin`/`StatementEnd` or it is torn apart mid-body.
    Zero migrations contain `CREATE FUNCTION`/`CREATE TRIGGER` — the repo's no-stored-
    routines rule does hold; these are anonymous blocks.
- **D-12:** New migrations **stay sequential numeric** (`000054`, `000055`, …), and the
  existing 44 are **not renumbered**.
  - **This was challenged.** The proposal was to adopt goose timestamps *and* renumber the
    existing 44 by commit timestamp, so the tree would carry only one scheme. Investigation
    killed it: `000041`–`000044` share one add-commit timestamp
    (`2026-05-23T22:40:42-04:00`, a squash merge), so timestamp renumbering **manufactures
    ordering data** that must be tie-broken by the existing integers anyway. It would also
    (a) break D-01's derivation, since `version <= 53` is meaningless against timestamps and
    would force a frozen old→new mapping at precisely the one unrecoverable step, and
    (b) invalidate by-name citations such as D-25's `000044_pregfo6_gap_timestamps_to_bigint`
    — the same cross-reference breakage GSD's phase-insert forbids, and which this milestone
    itself benefited from when Phase 01.1 was inserted as a decimal.
  - **The framing that resolved it:** staying sequential *is* the one-regime outcome. Only
    switching to timestamps would have created a second regime. — **Reversibility:** one-way
    in practice — changing scheme later means either renumbering (rejected above) or
    accepting two regimes.
- **D-13:** A **meta-test enforces `$$` ↔ `StatementBegin`/`StatementEnd` pairing** across
  `internal/store/migrations/*.sql`, failing CI otherwise. The 17 existing files are its
  first passing fixtures, so it goes green against real data rather than a synthetic case.
  Rejected: documenting the rule only (this is a silent-failure mode — a future `$$`
  migration without the wrapper is torn at semicolons and may apply *partially without
  erroring*, so review is the only gate); a converter-time check with nothing durable.
- **D-14:** The converter is **throwaway** — it and the equality proof run once during the
  PR, the result is recorded in the PR description, and neither is committed. The originals
  remain in git history, so the proof is re-derivable. Avoids leaving a one-shot tool in the
  tree that will rot and read as live tooling to the next person. Rejected: committing it
  under `scripts/`; keeping the verification as a test pinned to a historical commit.

### Proof and rollout

- **D-15:** Criterion 1's proof is a **one-time `pg_dump --schema-only` diff with the
  bookkeeping objects excluded** (`schema_migrations`, `goose_db_version`,
  `goose_db_version_id_seq`), pre-conversion vs post-conversion, which must be empty; the
  bookkeeping end-state is asserted separately (`goose_db_version` present with 44 rows, no
  `schema_migrations`). Recorded in the PR, nothing committed — after this lands there is no
  pre-conversion side to compare against again, so a lasting gate would be drift detection
  wearing this criterion's clothes. Rejected: a committed golden dump plus CI gate;
  diffing whole dumps with an allowlisted delta (pins exact `pg_dump` text for goose's
  table, brittle across goose versions).
  - **Criterion 1 is unsatisfiable as written** — see "Roadmap amendments".
- **D-16:** Rollout to `game.holomush.dev` takes a **fresh `pre-deploy:` Kopia snapshot
  immediately before the cutover deploy, and rehearses on it first** via
  `sandbox-restore.md`'s "Restore path A" (throwaway Postgres, run the new binary's migrate,
  verify the 44 rows, the rename, and the schema). Existing documented procedure, no new
  machinery. Rejected: rehearsing against the most recent existing snapshot (the gap between
  snapshot and deploy is exactly what the rehearsal would not see); treating the integration
  test as sufficient (it proves the mechanism on synthetic data seeded at v53 — only real
  sandbox data reveals actual drift, and per D-06 adopt does not look).
- **D-17:** The **cutover ships alone** — no new migrations in the release that performs it;
  Phase 2's three land in the next one. This keeps the application schema provably unchanged
  across the cutover deploy, which is what makes D-18's surgical rollback possible at all.
  Rejected: shipping Phase 2's migrations alongside (any rollback then means a full restore
  with data loss); enforcing isolation only for the sandbox (deployed sequence would differ
  from the tested one). — **Reversibility:** reversible — a sequencing choice, though
  reversing it forfeits D-18.
- **D-18:** The rollback procedure goes in **`sandbox-restore.md` with an explicit expiry
  note and a tracked removal issue**. Discoverable where an operator in trouble actually
  looks, and self-retiring rather than rotting into advice that silently stops working.
  Rejected: PR description only (nobody troubleshooting a bad deploy reads a merged PR);
  a permanent section with no expiry.
  - **The procedure is valid for exactly one deploy window.** Surgical path: rename
    `schema_migrations_pre_goose` back, drop `goose_db_version`, redeploy the previous
    binary — valid only while D-17 holds and no later migration has landed. After that, full
    snapshot restore is the only path.

### Claude's Discretion

None — every question was answered with an explicit selection. Two options offering
"You decide" were presented and not taken.

## Existing Code Insights

### Reusable Assets

- **`allMigrationVersions()` (`internal/store/migrate.go:177`)** — already parses versions
  from the embedded FS with a cached-once guard. D-01's derivation is reuse, not new
  machinery.
- **Kopia backup service + `pre-deploy:` snapshot tagging** (`docker/postgres-backup/`) —
  D-16's rehearsal needs no new tooling, only an existing documented procedure.
- **`test/meta/` convention** — D-13's pairing guard fits an established habit rather than
  introducing a new kind of test.

### Established Patterns

- **Migrations are embedded at compile time** and applied inline at startup before any
  subsystem starts. Any design that needs a running service before a migration is
  structurally impossible — this is the constraint that created this phase.
- **Idempotent DDL via `DO $$ … END $$;` guards** — 17 migrations use this shape. It is a
  house pattern, not an accident, and D-11/D-13 must accommodate it rather than remove it.
- **No stored routines** — zero `CREATE FUNCTION`/`CREATE TRIGGER` in the corpus; the rule
  in `database-migrations.md` holds.
- **Postgres pinned by digest** (`postgres:18-alpine@sha256:…`) — makes D-15's `pg_dump`
  comparison stable across runs.

### Integration Points

- `internal/store` blank-imports the migrations package so Go migrations' `init()` registers
  them (D-08).
- `internal/bootstrap/migration.go` → `cmd/holomush/core.go:279-282` is where the goose
  provider replaces the golang-migrate instance, and where adopt (D-02) hooks in.
- `cmd/holomush/migrate.go` maps its cobra subcommands onto goose equivalents (criterion 3).

### Corpus facts (verified 2026-08-02)

- **44 migration pairs / 88 files**, all correctly paired, no stray files.
- Versions `000001`–`000020`, then `000030`–`000053` — **a 9-version gap** (21–29). D-01
  handles it by construction; any approach that loops `1..53` would invent phantom rows.
- 17 files contain `DO $$` blocks; 0 contain `CREATE FUNCTION`/`TRIGGER`; 0 contain literal
  `BEGIN;`/`COMMIT;`. `CONCURRENTLY` appears only inside a comment in
  `000052_events_audit_partition.up.sql`, not as an executable statement.

<specifics>

## Specific Ideas

- **"Why do we need two numbering schemes forever?"** — the objection that drove D-12's
  investigation. The answer that satisfied it: staying sequential means a second scheme is
  never introduced, so there is nothing to unify. Renumbering was the wrong fix for a real
  concern.
- **"Can't be exactly identical, migration tracking schema is diff?"** — the observation
  that criterion 1 is unsatisfiable as written, which produced D-15's excluded-object form.
  Downstream agents should treat "byte-identical schema" as meaning *application schema*
  throughout.

</specifics>

## Deferred Ideas

### Roadmap amendments (this phase, one `/gsd-phase --edit 01.1` pass)

These are corrections to Phase 01.1's own ROADMAP entry, **not** future-phase work. They
MUST go through `/gsd-phase --edit 01.1` — never a hand edit of `ROADMAP.md`.

1. **Criterion 1 count:** says "All **49** migration pairs"; the tree has **44** pairs / 88
   files. Phase 2's D-20 sizing note carries the same wrong number.
2. **Criterion 1 guarantee:** "byte-identical" is unsatisfiable — post-conversion has

   as *application schema* byte-identical with bookkeeping objects excluded (D-15).
3. **Criterion 4 wording:** "demonstrated by a real migration" — the chosen proof is an
   integration-test fixture chain (D-07), not a migration in the permanent chain.
