| D-16 pre-deploy rehearsal | **WRITTEN ONLY.** No snapshot was taken, no restore performed, no binary run against restored sandbox data. The three verifications are authored from the adopt gate's actual behaviour (plan 04) and the measured row counts (plan 01), not from an executed run. |

A rehearsal nobody has run is a hypothesis. What *is* executed and green is the adopt mechanism

```
    CREATE TABLE public.foo (id text);"
```

exit 3. So the rule file's and the guide's quoted error text is observed, not remembered. The
container was removed.

## `task migrate:create` — deleted, and why

The plan offered two branches and asked which was taken. **Deleted**, on measurement:

- The target shelled out to the **golang-migrate** CLI with a `command -v migrate` precondition and
  an install hint naming `golang-migrate/migrate/v4/cmd/migrate`. That dependency is gone (plan 01).
- goose's own CLI cannot stand in. `create.go:44` formats sequential versions with
  `seqVersionTemplate = "%05v"` (`fix.go:10`) — **five** digits. The corpus is six, pinned by
  `migrate_embed_test.go:34`'s `^\d{6}_\w+\.sql$`. A goose-generated `00054_foo.sql` fails that test
  on the first run.
- `cmd/goose` additionally imports seven database drivers (mysql, clickhouse, mssql, sqlite3, turso,
  vertica, ydb) that are not in `go.mod`, so it is not a `go run` away either.

A shell-based generator was considered and rejected: any `for f in internal/store/migrations/…; do`
loop added to `Taskfile.yaml` would make `soleTaskfileLoopGlob` (plan 03) find **two** matching loops
and fail — correctly, since a pin that cannot tell which loop it guards is a pin that cannot fail.
The pins were left untouched; `git diff` shows no change to either `lint:no-timestamptz` glob.

The now-unused `MIGRATIONS_DIR` var was removed with it, and `.planning/codebase/STACK.md`'s
reference to it corrected — a var nothing uses is an invitation to re-add the target it served.

Task 2's brief carried two halves that only work together, and both are in
`site/…/operating/how-to/database.md` under the cutover section — the page an operator reads before
a deploy, not a planning artifact:

- **(b)** Running `status` first is **safe**: adopt fires from `Up()` only, and (per plan 04's

mentioned.

The adopt narrative states **45 rows** (44 at `version_id > 0` plus goose's version-0 bootstrap row)

pending migrations", both correct. No third `pg_dump -T` exclusion for `goose_db_version_id_seq` was
added anywhere (plan 01 proved it matches nothing).

## The `$$` failure mode, stated accurately rather than scarily

The rule file and the guide both state it as a two-row table: **loud and atomic** under goose's
default transactional mode (whole migration rolls back, nothing recorded), and **silent and partial**
only under `-- +goose NO TRANSACTION`. Both then say why the distinction is written down: a future
reader who meets only the loud rollback would reasonably conclude the wrapper is decorative, and the
silent variant is one annotation away.

The `ENVSUB` decision is stated as a decision — goose *can* interpolate environment variables into
migration SQL between `-- +goose ENVSUB ON`/`OFF`, and HoloMUSH declines it because a migration's
applied schema must not be a function of who ran it. Documenting it by omission would have left a
config-injection surface declined by accident.

No example in any rewritten file puts a bare `+goose` token inside a *prose* comment. Every
occurrence is a real annotation inside a fenced SQL block, which is copy-safe. Both the rule and the
skill additionally warn about this, since `extractAnnotation`
(`internal/sqlparser/parser.go:127,194`) treats any `--` comment containing the token as an
annotation and hard-errors on an unrecognised one.
