<objective>
Push the phase branch and open a pull request, then wait for a complete continuous-integration
run, so the coverage statuses this phase intends to gate on have somewhere to appear.

Purpose: cross-AI review established that the two remaining coverage plans both require
branch-side evidence that the wave graph never created. One needs the status rollup on this
branch's own head commit; the other needs branch-side coverage reports before it tightens a
threshold. The branch has no upstream and no pull request, so under the normal execute-then-ship
loop neither could obtain its evidence, and both would either stall or quietly fall back to
asserting configuration presence — which is exactly the substitution the phase is trying to
eliminate.

This plan does nothing but create the conditions. It observes nothing and requires nothing; that
is deliberate, because the observation plan's whole value is that it runs against real evidence
and the ruleset edit's whole value is that it runs against an observed status.

Output: an open pull request, a recorded head commit, and a completed continuous-integration run.

Decisions implemented: D-22 (the phase ships as a single pull request — this plan opens that pull
request early as a draft rather than creating a second one). Addresses review concern B4.
</objective>

    HALT and hand control to a human. Every code-changing plan in the phase has landed: the
    coverage measurement chain is repaired, the security-polish changes are in, both package
    coverage floors are backfilled, the session lifecycle matrix and its meta-test are committed,
    and the naming sweep and its ratchet are done. What does not yet exist is any remote-side
    evidence — the branch has never been pushed, so no pull request exists and the coverage service

    This step needs a human because it pushes a branch and opens a pull request: outward-facing
    actions that publish work and notify reviewers.

    Make no observation and no ruleset change here. This plan only creates the conditions; the
    next plan observes what posts, and the one after that asks for the ruleset edit. Keeping those
    three separate is what prevents a status being made required before it has been seen arriving.
  </action>
  <instructions>
    1. Confirm the working tree is clean and you are on the phase branch:

           git status --porcelain
           git branch --show-current

       The first must print nothing. If `task fmt` mutated files during any earlier plan and they
       were not committed, commit them now — uncommitted formatter output is a common cause of red
       continuous integration on an otherwise green branch.

    2. Rebase onto the current mainline, as the repository's landing rules require:

           git fetch origin && git rebase origin/main

       Resolve any conflicts, then re-run the pre-push gate:

           task pr-prep

       Judge it by its exit code and by the result file it names — never by matching a string in
       its output, because its own self-tests print strings that look like failures on healthy
       runs.

    3. Push and open the pull request as a draft:

           git push -u origin HEAD
           gh pr create -R holomush/holomush --draft --fill

       Draft is deliberate: it publishes the branch so continuous integration and the coverage
       service run against it, without signalling that review is wanted while two plans remain.

    4. Do NOT add a continuous-integration skip directive to any commit on this branch, including
       a documentation-only one. The repository's rules record an incident where exactly that left
       required checks with no run for the tip commit and blocked the merge with nothing failing to
       point at.

    5. Wait for the run to complete, then confirm both coverage uploads landed:

           gh pr checks --watch
           git rev-parse HEAD

       Report back the pull request number, the head commit hash, and whether the run completed or
       failed. If it failed, report what failed — that is a finding for this phase, not a reason
       to proceed.

    Do not touch the branch ruleset. Nothing in this step makes any check required.
  </instructions>
