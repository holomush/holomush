<objective>
Establish, from live evidence, that both coverage status contexts actually appear on pull
requests in this repository — and fix the configuration if either does not — before the phase
asks an operator to make them required.

Purpose: making a status required that never posts is a silent deadlock. Every pull request
sits blocked waiting for a check that will never arrive, with nothing failing to point at. This
repository has already suffered that exact failure once, from a different cause, and the
incident is written into its own rules. Independent observation found the patch context posting
and passing on recent merged pull requests, and the project context not appearing in the status
rollup at all. The stated explanation is that the project status only emits when there is a base
to compare against — plausible, but it is an assumption, and it is the assumption the whole
gate rests on.

Output: an evidence table, a corrected configuration if one is needed, and an explicit go or
no-go for the operator action in the final plan.

Decisions implemented: D-04 (make both coverage statuses required within the phase). The
ordering call is mine and is recorded here: this verification runs after the two thinnest-margin
code plans and after the command-package backfill, and the operator action itself moves to the
final plan because the phase ships as a single pull request (D-22), so the only moment live
status evidence exists for this branch is after its own continuous integration has run. That
inverts D-04's literal "require early" while honouring its intent — the gate lands inside the
phase and the tolerance is tightened last — and it eliminates the deadlock risk that requiring an
unobserved status would create.
</objective>

    SUMMARY and change nothing — an unnecessary configuration edit here risks the very deadlock

    If a context does not post, diagnose why from the observed evidence before changing anything.
    The plausible causes are distinguishable: a status configured as informational reports but
    does not gate and may be filtered from the rollup; a status with no base commit to compare
    against does not emit at all on a first-of-its-kind branch; and a status whose upload count
    never reaches the configured threshold is withheld indefinitely. Each has a different fix and
    the wrong fix makes things worse.

    Make the narrowest change that causes the context to post, and leave the threshold value
    alone — tightening it is the final plan's job. Do not raise the upload-count threshold; the
    file's own comment explains that a higher value blocks notification entirely.

    Re-verify by observing a fresh rollup after the change has been pushed and continuous
    integration has completed. A configuration change unverified against a live rollup has not
    established anything, and this plan's entire purpose is to avoid asking an operator to act on
    an unverified assumption.
  </action>
