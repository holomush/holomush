<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| expired session -> new session | Whether state carries across expiry decides what history a returning player may read |
| history floor -> event visibility | The arrival timestamp is the authorization boundary for historical events |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-13-01 | Information Disclosure | history floor inherited across session expiry | high | mitigate | If a post-expiry re-login reused the old arrival timestamp, the player would read history from a period they were not present for. The post-expiry specs assert a bounded history read excludes a pre-session event placed at an exact instant, so an inherited floor fails the test. |
| T-09-13-02 | Information Disclosure | arrival timestamp reset on detach | high | mitigate | Conversely, resetting the timestamp on a mere detach would narrow or shift what a reattaching player sees. The detach specs assert the timestamp is unchanged, which asserting only the status would miss. |
| T-09-13-03 | Denial of Service | reaper sweep correctness | medium | mitigate | A reaper that fails to remove expired rows grows the session table without bound. The reaper specs assert the specific row is not found after expiry rather than counting rows, so a shared-suite concurrent session cannot mask a failure. |
| T-09-13-SC | Tampering | npm/pip/cargo installs | high | accept | No packages installed; no dependency manifest touched. |
</threat_model>
