    <note>Three additions over the superseded form, each closing a way this probe could report success while producing nothing. All three were measured, not assumed.

    Without `set -o pipefail` a failing `go tool cover` is masked by the succeeding `tail`: measured, the pipeline exits 0 against a nonexistent profile. With `pipefail` the same pipeline exits 1. That masking is the defect this addition closes.

    `test -s` catches a profile that was never written — the run can exit 0 and emit no profile if the package selector matched nothing.

    `rg -c '^total:'` asserts the last line is a coverage total rather than a blank line or the residue of a malformed profile. Measured limits of this assertion, stated so nobody over-reads it: a MALFORMED profile makes `go tool cover` exit 2 and is caught by `pipefail`, but a HEADER-ONLY profile (`mode: set` and nothing else) emits `total:\t(statements)\t0.0%` and PASSES this gate. So the gate proves a figure was produced; it does not prove the figure is meaningful. That is acceptable here because this task's product is a recorded starting figure and 0.0% for a package with existing tests is self-evidently wrong to the reader — but do not treat a green gate as evidence the profile is sound. If the recorded total is 0.0%, stop and diagnose rather than recording it as the baseline.

    `rg -c ... &gt;/dev/null` rather than `rg -q`, since `-q` stops at the first match and SIGPIPEs the producer, which under `pipefail` returns 141 on the passing case.</note>
  </verify>

    highest-statement-count function downward until the package total clears 80%. Stop when it
    clears; do not keep going to chase a rounder number.

    Every test asserts an outcome, not merely that a call did not panic. Prefer asserting the
    error's code with the repository's error-code assertion helper over matching substrings of
    the message — string matching on errors is a known weakness in this codebase and adding
    more of it while fixing test quality would be self-defeating. For a validation failure,
    assert both that it failed and that it failed for the reason under test, so a test for a

    naming ratchet landing later in this phase flags, and a test added by this plan becoming a
    hit for that plan would be an own goal. Avoid vague subtest strings for the same reason.

    Add temporary-directory fixtures with the standard test cleanup rather than committing
    certificate fixture files; the package already generates its own material and committing
